Firmware Update Across Three Processors

Worked solution

A model answer to compare against. Yours may differ in names and split; check it covers the same data, checks and failure handling.

Update state diagram

stateDiagram-v2
    [*] --> Idle
    Idle --> Downloading: manifest offered
    Downloading --> Verifying: all images staged
    Downloading --> Idle: download fails
    Verifying --> Idle: bad signature or hash
    Verifying --> Installing: valid, compatible
    Installing --> SafeState: written to inactive slots
    SafeState --> TrialBoot: device idled, switch slots
    TrialBoot --> Confirmed: self-test and comms OK
    TrialBoot --> RolledBack: test fails or timeout
    RolledBack --> Idle: old slots active
    Confirmed --> [*]

Who verifies what

ItemVerified byKey
Manifest: versions, hashes, compatibilityCoordinator Platform signing key
Radio and coordinator imagesCoordinator, then each bootloaderPlatform key
OEM imageCoordinator, then the sandbox bootloader OEM key and platform approval

The radio processor downloads, but never decides. It is untrusted, so the coordinator checks the manifest and every hash itself.

Recovery

Power lost duringOutcome
DownloadStaging incomplete. Old images still active. Resume or restart

Trial bootNot confirmed, so the next boot reverts

Compatibility

  • The coordinator-to-sandbox interface carries a version number.
  • The coordinator supports the current and the previous interface version.
  • The manifest states which combinations are valid. The coordinator refuses any other.
  • Switch order: coordinator first (it understands both), then sandbox, then radio.

The classic failure is a half-applied release: the new coordinator boots, the old OEM driver does not speak its protocol, and the device stops. Plan for overlapping compatibility, not a perfect simultaneous switch.

Anti-rollback

  • Each image carries a security version.
  • The bootloader refuses any image below the value in a monotonic counter, for example in OTP fuses.
  • The counter is raised only after the new image is confirmed. Raise it earlier and a failed update cannot roll back.

The load during the update

Before switching slots, take the device to its safe state, such as zero power, and confirm it. The OEM driver's lease would do this anyway; doing it deliberately makes it predictable.

Point to raise

When does the update run? Thousands of devices rebooting at the same moment is a grid event. Spread updates over a window, and avoid times when the device is committed to a service.

Self-marking checklist

  • A/B slots, with the old image kept until confirmed?
  • Coordinator verifies, not the radio?
  • OEM image needs both OEM and platform approval?
  • Power loss covered at every step?
  • Interface versioning between coordinator and sandbox?
  • Anti-rollback counter raised only after confirmation?
  • Device put into a safe state before switching?
