Answer

Stream it. Never load the whole file.

Approach

  1. Use a streaming (SAX-style) parser. Feed the file in small chunks. The parser emits events and discards each chunk once consumed.
  2. Process each event immediately. Extract the values you need, act on them, and drop the rest. Never build a DOM tree.
  3. Keep state small. Track only the current element path. Memory use depends on nesting depth and the longest token, not on file size.

The file is 2 MB, but the working set is a few kilobytes. Memory use is set by the buffer, the tag stack and the longest token. None of those grow with the file.

Source options

  • External flash or SD card, read through a filesystem such as FatFs or LittleFS.
  • Network or UART, consumed as a byte stream.
  • Internal flash, memory-mapped and read directly.

Hand-rolled state machine Best for a fixed, known schema.

Failure points

RiskMitigation
Long tokens: one text node or attribute larger than the buffer Set a maximum token length. Reject or truncate anything over it.
Deep nesting overflows the tag stack Cap the depth.
Entities and encodings Handle &amp;, character references and UTF-8 explicitly.
Dynamic allocation Avoid malloc. Use static buffers to prevent fragmentation, which matters under FreeRTOS.
Random access Streaming is forward-only. Re-read the file, or store the extracted values.

The most common wrong answer is "compress it" or "add external RAM". Both avoid the question. The point is that the file never needs to be in memory in full.

When streaming is not enough

If the task needs the whole structure in memory, such as XPath queries or tree manipulation, a 1 MB device cannot do it.

Preprocess the XML off-device into a compact binary format, such as CBOR or a packed struct table, and ship that instead.
