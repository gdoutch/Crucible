Edge Module: From Cloud Command to Device

Worked solution

A model answer to compare against. Yours may differ in names and split; check it covers the same data, checks and failure handling.

Downward: the command

LinkData
Cloud → radioMQTT over TLS. A schedule command: type, power 3 kW, end time 06:00, command id, issue time
Radio → coordinatorThe same message, framed over the inter-chip link. The radio does not interpret it
Coordinator (internal)Validate: known type, in range, authentic, not a replay. Store as a schedule entry
Coordinator → sandboxEvery second while the schedule is active: an instantaneous setpoint, +3000 W, with a short lease
Sandbox → batteryThe maker's own protocol, for example register writes over UART, SPI or Modbus

Upward: the telemetry

LinkData
Battery → sandboxMeasured power, state of charge, faults
Sandbox → coordinatorStatus in the SDK's fixed format: power, SoC, fault codes
Grid meter → coordinatorGrid import / export over the dedicated Modbus link
Coordinator → radioValidated, rate-limited telemetry and the command acknowledgement
Radio → cloudMQTT publish

    loop every 1 s until 06:00
        Coordinator->>Sandbox: setpoint +3000 W, lease 5 s
        Sandbox->>Battery: write power register
        Battery-->>Sandbox: measured power, SoC
        Sandbox-->>Coordinator: status
    end
    Coordinator->>Sandbox: setpoint 0 W at 06:00

The key insight: "until 06:00" lives in the coordinator. The OEM driver only ever sees "do this now, for the next few seconds". That keeps the maker's code simple, and keeps scheduling, time and policy in the trusted processor.

The common mistake is a line from the radio processor straight to the OEM sandbox. Every message must pass through the coordinator. That is what "hardware firewall" means.

Why this split

  • The radio is the most exposed part, so it gets no authority. It only moves bytes.
  • The coordinator is the single place that decides. Policy is checked once, in code the platform owns.
  • The sandbox holds device knowledge only. It can be written by a device maker who knows nothing about the cloud.

Point to raise

What does the battery do if the setpoints stop arriving? The lease answers that, but somebody must define the safe state for each device type.

Self-marking checklist

  • All three processors drawn as separate components?
  • No direct link between radio and sandbox?
  • Schedule held in the coordinator?
  • Sandbox receives an instantaneous setpoint, not the schedule?
  • Grid meter drawn into the coordinator?
  • Telemetry path labelled as well as the command path?
