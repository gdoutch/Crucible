Word Frequency With operator[]

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

#include <map>
#include <sstream>
#include <string>

std::map<std::string, int> WordFrequency(const std::string& text)
{
    std::map<std::string, int> counts;
    std::istringstream stream(text);
    std::string word;
    while (stream >> word)
    {
        counts[word]++;
    }
    return counts;
}

Why operator[] needs no branch at all

std::map<K, V>::operator[] is specified to insert a default-constructed V (value-initialised, so 0 for int) the moment it is asked for a key that is not present, and return a reference to that entry either way -- present or freshly created. That is a deliberately different contract from a plain lookup that fails on a missing key: it exists precisely so counts[word]++ is correct on every occurrence of every word, first or hundredth, without the code needing to tell those cases apart itself. The "trap" candidates coming from a language whose map type throws on [] sometimes fall into is over-engineering a get-or-insert helper that std::map already gives you for free.

Why the words come out sorted

std::map keeps its keys in ascending order internally (unlike std::unordered_map, which makes no ordering promise at all) -- iterating it, the way the harness that calls this function does to print the result, visits keys lexicographically without this function needing to sort anything itself. That ordering is a property of the container choice, not something WordFrequency has to implement.

Cost

O(n log k) where n is the number of words in `text` and k the number of distinct ones -- each `operator[]` access is an O(log k) tree lookup on `std::map`. Using `std::unordered_map` instead would trade that for O(1) average per access at the cost of losing the sorted iteration order this function's own contract does not need.
