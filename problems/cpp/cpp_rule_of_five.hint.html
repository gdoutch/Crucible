Rule of Five: An Owning Text Class

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

Five members, and each has one job

copy ctor     allocate size+1, memcpy
copy assign   if (this != &other): allocate new, copy, delete[] old, swap in
move ctor     steal data_/size_, null out the source
move assign   if (this != &other): delete[] old, steal, null out the source
destructor    delete[] data_        (delete[] nullptr is fine)

The two traps that bite hardest: freeing your own buffer before copying from it in a = a, and forgetting to null out the moved-from object so two destructors free the same block. Make c_str() return "" when data_ is null.

Where it goes wrong

Every special member has a way to fail without any compile error. Copy assignment that frees its buffer before copying breaks on a = a. An assignment that overwrites data_ without freeing it leaks. A move that does not null out the source lets two destructors free one block. And a c_str() that returns nullptr for a moved-from object crashes the first operator<< that prints it. The harness prints live= after each scenario: anything other than 0 is a leak or a double free.
