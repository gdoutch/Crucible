A list for order, a map for speed, splice to move

// Get:  find in index; splice the node to order.begin(); return value
// Put:  if present -> update value, splice to front
//       else       -> emplace_front, record iterator in index,
//                     if over capacity: erase back() from index AND list

order.splice(order.begin(), order, it) relinks an existing node to the front in O(1) and leaves every iterator -- including the ones in index -- valid. Most-recent at the front means the victim is always order.back().

Where it goes wrong

The bugs here are bookkeeping bugs. A Get that returns the value without moving the node means a hot key is evicted as soon as enough new keys arrive. A Put on an existing key that behaves like a fresh insert grows the cache or evicts something it should not. And an eviction that pops the list but leaves the key in the map leaves a dangling iterator that a later lookup will happily dereference. Keep the two containers describing exactly the same set of keys after every operation.
