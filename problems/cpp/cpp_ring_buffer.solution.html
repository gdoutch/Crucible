Fixed-Size Ring Buffer (No Heap)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

#include <cstdint>

constexpr unsigned kRingCapacity = 8;

struct RingBuffer
{
    std::uint8_t data[kRingCapacity];
    std::uint8_t head;
    std::uint8_t tail;
    std::uint8_t count;
};

void Init(RingBuffer& rb)
{
    rb.head = 0;
    rb.tail = 0;
    rb.count = 0;
}

bool Push(RingBuffer& rb, std::uint8_t value)
{
    if (rb.count == kRingCapacity)
    {
        return false;
    }
    rb.data[rb.head] = value;
    rb.head = static_cast<std::uint8_t>((rb.head + 1) % kRingCapacity);
    rb.count++;
    return true;
}

bool Pop(RingBuffer& rb, std::uint8_t& value)
{
    if (rb.count == 0)
    {
        return false;
    }
    value = rb.data[rb.tail];
    rb.tail = static_cast<std::uint8_t>((rb.tail + 1) % kRingCapacity);
    rb.count--;
    return true;
}

Why count exists

With only head and tail a ring of eight slots can describe eight different amounts of data in nine situations: after filling it, head == tail; after emptying it, head == tail again. The two states look identical. Production code solves this by wasting one slot, by using free-running indices, or -- as here -- by keeping an explicit count. Keeping it makes the full/empty tests trivial and obviously correct.

Why check before touching anything

A Push that writes data[head] and advances head before noticing the buffer is full overwrites the oldest unread byte and leaves count at the cap -- a silent loss of data that no return value reports. Testing first and returning early makes failure a no-op.

Why no heap

The whole buffer is a plain struct with a fixed array: no allocator, no exceptions, a size known at compile time and a worst-case cost that never varies. That is the property firmware depends on, and why std::vector and std::queue are usually avoided in interrupt paths.

Cost

Both operations are O(1) with no allocation.
