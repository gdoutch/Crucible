Deep-Copying a Struct That Owns a Pointer

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

struct Box
{
    int* data;
    int size;
};

Box CopyBox(const Box& original)
{
    int* data = new int[original.size];
    for (int i = 0; i < original.size; i++)
    {
        data[i] = original.data[i];
    }
    return Box{data, original.size};
}

Why `return original;` is the trap, not a typo

`Box` has no user-defined copy constructor, so copying one -- whether via `return original;`, `Box copy = original;`, or passing one by value -- uses the compiler-generated default: copy every member, field by field. For `size`, an `int`, that is exactly right; there is only one sensible way to copy an `int`. For `data`, an `int*`, "copy the member" means copy the *pointer's value* -- the memory address it holds -- because that address is all a raw pointer actually *is*, as far as the type system is concerned. The compiler has no way to know that this particular pointer is meant to represent ownership of the array it points to, so it treats it exactly like it would treat a pointer that was never meant to be "owned" by anything -- because nothing in `Box`'s definition says otherwise. Two `Box`es sharing one array compiles, links, and runs without any diagnostic, because nothing about it is actually illegal C++; it is only wrong relative to what this specific function is asked to guarantee.

Why the loop copies values, not the pointer

new int[original.size] allocates a second, independent array on the heap, and the loop copies each `int` *value* from `original.data[i]` into the new array's own storage at `data[i]`. After this runs, `data` and `original.data` are two different addresses, pointing at two different blocks of memory that happen to currently hold equal values -- which is the actual definition of "an independent copy", as opposed to "two names for the same thing".

Why `size` is copied too

`Box{data, original.size}` copies `size` directly rather than, say, leaving it default-initialised or recomputing it some other way -- a copy with the right array but a stale or zero `size` would look correct until something (like the harness printing every element) actually reads that field to decide how far to iterate.

Why `original.size == 0` needs no special case

new int[0] is well-defined C++: it returns a valid, unique pointer that owns zero elements. The copy loop's condition, i < original.size, is false immediately when `original.size` is `0`, so the loop body never runs -- the function returns a `Box` with its own (empty) allocation, exactly as it would for any other size, with no `if` needed to detect the empty case specially.

Cost

O(n) in `original.size` -- one allocation and one pass copying each element's value.
