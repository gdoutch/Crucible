Sort an Array In Place

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Insertion sort. Grow a sorted region at the front of the array one element at a time. To absorb the next element, shift every larger element of the sorted region one place right and drop the new value into the gap that opens up.

Invariant: at the top of iteration i, values[0..i-1] is sorted. It contains the same elements it started with, just rearranged.

The code

void sort_values(int *values, int count)
{
    for (int i = 1; i < count; i++) {
        int key = values[i];
        int j = i - 1;

        while (j >= 0 && values[j] > key) {
            values[j + 1] = values[j];
            j--;
        }

        values[j + 1] = key;
    }
}

The four things to get right

1. Save key first

values[i] is the first slot the shifting overwrites — the very first assignment in the inner loop is values[i] = values[i - 1]. Reading the key after that gets you a duplicate of its neighbour and loses the original permanently.

2. The bounds test comes first

j >= 0 && values[j] > key. C evaluates && left to right and stops as soon as the answer is known, so when j reaches -1 the second operand is never evaluated. Swap the two and you read values[-1] — one int before the allocation — on every element that turns out to be the new minimum.

That bug does not usually crash. It reads whatever happens to be in memory, compares it, and mostly gets away with it, which makes it far more dangerous than a segfault.

3. Shift right to left

values[j + 1] = values[j] copies each element into the slot after it, and j descends. Going the other way would overwrite each element before it had been copied, smearing one value across the region.

4. The gap is at j + 1

When the loop exits, j is either -1 or points at an element that is <= key and therefore stays to the key's left. Either way the empty slot is the one after it. Both exits agree, which is why a single values[j + 1] = key handles them.

The last row is the worst case in miniature: the new element is smaller than everything, so the whole sorted region shifts.

> and not >=

With values[j] >= key the loop keeps shifting past elements equal to the key, walking it further left than it needs to go. The array still ends up sorted, so the tests still pass — but two things are lost:

  • Work. The all the same case (7 7 7 7) degenerates from n−1 comparisons to the full quadratic shuffle.
  • Stability. Equal elements end up in reverse order relative to how they started. With bare ints that is undetectable; with records sorted by one field it is a visible bug.

Why the empty and single-element cases need no guard

The outer loop starts at i = 1. With count of 0 or 1, 1 < count is false immediately, the body never runs, and values — possibly NULL — is never dereferenced. Adding if (count < 2) return; is harmless but tells the reader you were not sure.

Cost

InputComparisonsWhy
Already sortedO(n) Every inner loop fails on its first test. This is the already sorted fixed case, and nothing moves.
All equalO(n) Same reason — given > rather than >=.
RandomO(n²) Each element shifts past about half the sorted region.
Reverse sortedO(n²) Every element shifts past the whole region — the worst case.

O(1) extra space in all cases: one int for the key and one for the index.

Quadratic sounds disqualifying, and for large arrays it is. But insertion sort is the right tool more often than its reputation suggests: it is fast on nearly-sorted data, it is stable, it allocates nothing, and its constant factor is tiny. Production quicksorts — including most libc qsort implementations — switch to it once a partition drops below a dozen or so elements.

Wrong turns worth recognising

Calling qsort. It passes every test. It also means you did not write a sort, and it drags in a comparison callback whose own classic bug — return *(int*)a - *(int*)b;, which overflows for large opposite-signed values — is worse than anything in the loop above.

Allocating a second array. "In place" is in the title. A merge sort into scratch memory is a fine algorithm and the wrong answer to this question.

Swapping instead of shifting. Repeatedly swapping the key with its left neighbour is bubble sort's inner loop. It sorts correctly, but it performs three assignments per step where the shift performs one, and it obscures the "open a gap and insert" idea the exercise is about.
