The loop, at a high level

read = 0
while read < enc_len:
    code = enc[read]
    # bounds-check here, before touching anything past enc[read]
    read += 1
    copy (code - 1) bytes from enc[read..] to out, advancing read and out
    # decide here whether a zero belongs on the output

Everything fiddly about this problem lives in that last line's decision, and in the bounds check before the copy.

The bounds check

Before trusting a code byte, you know exactly how many bytes it demands: code - 1 literal bytes must still be available in enc from the current read position. If they are not, the frame is corrupt -- return -1 immediately, before copying anything.

When does a zero get appended?

Almost always -- except in two situations, and it is easy to only remember one of them:

  • the code byte was 0xFF (this block never implies a zero, regardless of position), or
  • this block is the last one in the frame (there is nothing left to read after it, so whatever zero might have followed it in the original data was the frame delimiter, already gone).

Both conditions are checkable from information you already have at that point in the loop: the code value itself, and whether your read position has reached enc_len.

The block that never needed a copy loop at all

A code byte of 1 means zero literal bytes follow -- the copy loop for that block does nothing, and (per the rule above, since 1 != 0xFF) a zero gets appended unless this was the last block. Encoding an originally-empty buffer produces exactly the single byte 0x01: decoding it should walk through one block, copy nothing, and -- because it is also the last block -- append nothing either. Zero bytes out.
