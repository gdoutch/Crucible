Write a Register Field (Read-Modify-Write)

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

The reverse of Extract a Register Field: instead of reading a field out, you are putting one back, without disturbing any bit that is not part of it. That is the read-modify-write pattern, spelled out as three separate steps even though your function only gets to do the "modify" and hand back the result:

  1. Read — the caller already did this; reg is what came back.
  2. Modify — clear the field's old bits, then set its new ones.
  3. Write — return the result; the caller stores it back.

The mask is the same one as before

(width == 32) ? 0xFFFFFFFFu : (1u << width) - 1u — same formula, same reason, as Extract a Register Field. You will use it twice here: once shifted into position to clear the old field, once plain to trim the incoming value down to size.

Two traps, not one

Clear before you set. reg |= (value & mask) << start on its own only ever turns bits on — OR can set a 0 to a 1, but it can never turn a 1 back to 0. If the field currently holds all ones and the new value is all zeros, that line changes nothing. You need an AND first, against the complement of the mask in position, to clear the field's old bits before the OR ever runs.

Mask value, not just reg. Nothing stops the caller passing a value that does not fit in width bits. Shift it into place unmasked and its high bits land on top of whatever field happens to sit above this one — a bug that shows up nowhere near the code that caused it, in a completely different field, which is what makes it nasty to track down on real hardware.

Still stuck? A bigger nudge

Three lines, in this order:

unsigned int mask = /* the width == 32 formula */;

reg &= ~(mask << start);        /* clear the field */
reg |= (value & mask) << start; /* mask value, then set it */

The clear line works because mask << start is ones exactly where the field is and zeros everywhere else; ~ flips that to zeros over the field and ones everywhere else, so ANDing it in clears only the field and leaves every other bit as it was.

Check yourself before you press Go

  • set_field(0xF0, 4, 4, 0) → 0x00, not 0xF0.
  • set_field(0x0F, 8, 4, 0xFF) → 0xF0F, not 0xFF0F — the extra bits in value must not leak upward.
