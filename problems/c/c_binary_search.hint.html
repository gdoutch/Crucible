What you are being asked for

The index of target in an ascending sorted array, or -1. A linear scan gets the right answers and misses the point; the exercise is the halving.

The idea in one sentence

Keep a window of the array that could still contain the target, look at its middle element, and throw away the half that cannot.

Two variables define the window — call them low and high — and everything hinges on what exactly they mean. Pick one meaning and hold to it, because almost every binary-search bug is really an inconsistency between the initialisation, the loop condition and the updates.

The convention that causes the fewest mistakes

low and high are both valid indices, and the window is inclusive at both ends. Then:

QuestionAnswer forced by the convention
Where does high start? count - 1 — the last valid index, not count.
Is a one-element window still worth checking? Yes: low == high names a real element nobody has looked at. So the loop must keep going while low <= high.
After ruling out mid, what is the new window? mid itself is excluded, so mid + 1 or mid - 1 — never mid.

Get any one of those three out of step with the other two and you have either an infinite loop or a missed element.

The infinite loop is the likely failure, not a wrong answer. If the window ever fails to shrink — say you set low = mid instead of mid + 1 — a two-element window can repeat forever. Crucible times each case out separately, so watch for TIMEOUT.

Computing the middle

Write it as low + (high - low) / 2 rather than (low + high) / 2. The two are equal for every input this problem will give you, but the second overflows once the indices get large enough to sum past INT_MAX. It is a famous bug — it sat in the JDK's binary search for nine years — and the safe form costs nothing.

The two edge cases in the fixed tests

  • Empty array. count is 0, so high starts at -1, and 0 <= -1 is false. The loop never runs, nothing is dereferenced, -1 comes back. You should not need an explicit guard — check that you do not.
  • Last element. Finding the value at index count - 1 is where an i < count-style off-by-one shows up.
Still stuck? A bigger nudge 
int low = 0;
int high = count - 1;

while (low <= high) {
    int mid = low + (high - low) / 2;
    if (values[mid] == target) {
        return mid;
    }
    if (values[mid] < target) {
        /* the target, if present, is to the right of mid */
    } else {
        /* ... to the left */
    }
}
return -1;

Fill in the two branches. Each one must move low or high past mid, because mid has just been ruled out.

Check yourself before you press Go

  • Empty array → -1, no crash.
  • Single element, present → 0; absent → -1.
  • First element and last element are both findable.
  • A target smaller than everything, and one larger than everything, both return -1 rather than looping.
