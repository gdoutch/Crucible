Sum of an Array

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Accumulate. Keep one running total, add every element into it, hand it back. There is no cleverness available here and none wanted — the exercise is about the contract rather than the arithmetic: you are given a pointer and a length, and the length is the only thing that tells you where the data ends.

That is the habit worth taking away. A C array does not know how long it is. sizeof values inside this function is the size of a pointer, not of the array the caller allocated. The only reliable bound is count.

The code

int sum_array(const int *values, int count)
{
    int total = 0;
    for (int i = 0; i < count; i++) {
        total += values[i];
    }
    return total;
}

Five lines, and every one of them is doing something:

  • int total = 0; — the identity for addition. Starting anywhere else means the empty case comes out wrong.
  • i < count — a strict less-than, so the last index touched is count - 1. i <= count reads one int past the end of the allocation, which is undefined behaviour and often does not crash, which is worse.
  • values[i] — identical to *(values + i). The const in the parameter is a promise to the caller that you will not modify their array; the compiler holds you to it.

Why the empty case needs no special handling

With count == 0 the loop's condition is 0 < 0, which is false on the very first evaluation. The body never runs, so values is never dereferenced, and total is returned still holding 0.

This is worth pausing on, because it is why the loop is written the way it is. The tempting alternative —

int total = values[0];              /* wrong */
for (int i = 1; i < count; i++) {
    total += values[i];
}

— reads values[0] before anything has checked count. On the empty case values is NULL and the program dies with a segmentation fault. Crucible runs each test case in its own process, so you would see ERROR against empty array and passes elsewhere, which is exactly the fingerprint of a missing zero-length check.

Cost

O(n) time — one pass, one addition per element — and O(1) extra space. Both are optimal: you cannot sum n numbers without looking at all n of them.

Wrong turns worth recognising

Looking for a terminator. There is no '\0' at the end of an int array, and no -1 either. Anything of the form while (values[i] != 0) stops at the first zero element and runs off the end of an array that has none.

Overflow. Summing large ints can overflow, and signed overflow in C is undefined behaviour rather than a wrap-around you can rely on. This problem's generator deliberately caps the values so no correct solution can overflow — but in real code you would sum into a long long, and it is worth noticing that the test data was chosen to keep the question from arising.

Writing main. The harness has one. Your file and the harness are compiled as separate translation units and linked, so a second main is a duplicate-symbol error at link time rather than a compile error — the message points at the linker, not at your line.
