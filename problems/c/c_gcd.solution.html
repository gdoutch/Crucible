Greatest Common Divisor

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Euclid's algorithm, in its remainder form. It rests on one fact:

For b ≠ 0, the common divisors of (a, b) are exactly the common divisors of (b, a mod b).

Why: write a = qb + r. If d divides a and b, then it divides a − qb, which is r. And if d divides b and r, then it divides qb + r, which is a. The two sets contain the same numbers, so they have the same maximum.

That turns "find the greatest common divisor" into "make the numbers smaller without changing the answer", repeated until one of them is zero.

The code

int gcd(int a, int b)
{
    while (b != 0) {
        int remainder = a % b;
        a = b;
        b = remainder;
    }
    return a;
}

Three statements in the loop, and the order of them matters: remainder must be computed from the old a before a is overwritten. Assigning a = b first destroys the value you still need.

Answer: 6. Notice how quickly it shrinks — that is the whole point of the algorithm.

Why it always terminates

For positive b, the C standard guarantees 0 ≤ a % b < b. So the new b is strictly smaller than the old b and never negative: a strictly decreasing sequence of non-negative integers, which cannot go on forever. In fact it is remarkably fast — the worst case is consecutive Fibonacci numbers, and even then the number of steps is logarithmic in the input.

The zero cases, which are the ones being tested

CallWhat happensResult
gcd(0, 0) b is already 0, so the loop never runs. 0
gcd(0, 18) One step: 0 % 18 is 0, so the pair becomes (18, 0). 18
gcd(18, 0) Loop never runs. 18

Two things worth noticing. First, arguments in the "wrong" order fix themselves in a single step, so there is no need to sort them beforehand. Second, gcd(0, 0) is a convention rather than a fact — every integer divides zero, so there is no greatest one — and 0 is the standard choice, being the value that makes gcd behave sensibly in the algebraic identities it appears in.

The loop condition b != 0 is also what keeps a % b from ever executing with a zero divisor. That is not a lucky arrangement; it is the reason the condition is on b rather than on a.

Cost

O(log min(a, b)) divisions, O(1) space. The brute-force alternative — trying every candidate downwards from min(a, b) — is O(min(a, b)), which for gcd(999999937, 2) is the difference between two steps and half a billion.

Variations

Recursive. return b == 0 ? a : gcd(b, a % b); — a faithful transcription of the mathematical statement, and tail-recursive, so optimising compilers turn it back into the loop above. Perfectly good here; the iterative form is preferred in C mostly because tail-call elimination is not guaranteed.

Subtraction instead of modulo. The original form repeatedly subtracts the smaller from the larger. It works, needs no division, and takes a / b steps where the modulo version takes one — so gcd(1000000, 1) becomes a million iterations. Historically interesting, practically a timeout.

Wrong turns worth recognising

Guarding zero by hand. if (a == 0) return b; before the loop is harmless but redundant, and it suggests the author did not trust the loop. Worse is if (b == 0) return 0;, which turns gcd(18, 0) into 0.

Negative inputs. This problem promises non-negative arguments, so nothing here handles them. In general C's % truncates towards zero, meaning -7 % 3 is -1, and the loop can return a negative "greatest" divisor. Real code takes the absolute value of both arguments first — and even that has an edge case at INT_MIN, whose negation does not fit in an int.
