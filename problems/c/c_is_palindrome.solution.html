Palindrome Check

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Two indices, one at each end, walking towards each other. Characters that do not participate in the comparison — spaces, commas, colons — are stepped over rather than removed, so the string is never copied or modified. The filtering and the comparing happen in the same pass.

The code

#include <ctype.h>
#include <string.h>

int is_palindrome(const char *s)
{
    size_t i = 0;
    size_t j = strlen(s);

    while (i < j) {
        if (!isalnum((unsigned char)s[i])) {
            i++;
        } else if (!isalnum((unsigned char)s[j - 1])) {
            j--;
        } else if (tolower((unsigned char)s[i])
                   != tolower((unsigned char)s[j - 1])) {
            return 0;
        } else {
            i++;
            j--;
        }
    }
    return 1;
}

Why j is one past the end

j is an exclusive bound: the window under consideration is [i, j), and the rightmost live character is s[j - 1]. Two things fall out of that choice.

First, the empty string needs no special case. strlen("") is 0, the condition 0 < 0 is false, and the function returns 1 without reading anything. Had j been initialised to strlen(s) - 1, that subtraction on an unsigned size_t would produce SIZE_MAX and the first read would be far outside the buffer.

Second, the price is the - 1 on every access through j. Three of them here, and forgetting one is the most likely way to break this function. Signed int indices with an inclusive j = (int)strlen(s) - 1 are the alternative: no repeated - 1, no unsigned wraparound, at the cost of a cast. Both are defensible; pick one and be consistent.

Why the branches are a chain and not three tests

Only one index moves per iteration unless a real comparison succeeded. That is what the else if chain enforces. Consider "a, a":

Had the skips been written as two independent ifs, the second row would have moved both indices at once, stepping the right-hand one past a character that had never been compared. On this input the answer would still be right; on "a,ba" it would not be.

Termination

Every path through the loop body either returns or strictly increases i or strictly decreases j. The gap j - i therefore shrinks by at least one each iteration and cannot pass zero without the condition failing. A string of nothing but punctuation exhausts itself through the first branch and returns 1.

The <ctype.h> casts

isalnum and tolower take an int whose value must be representable as unsigned char, or be EOF. Plain char is signed on x86 and ARM, so byte 0xC3 arrives as -61 and the call is undefined behaviour — typically an out-of-bounds read of the implementation's lookup table.

The cast is required on both functions and on every call. It is four extra words and it is the difference between correct code and code that happens to work on ASCII input.

Why not clean the string first?

/* the copying approach */
char clean[1024];
size_t n = 0;
for (const char *p = s; *p; p++) {
    if (isalnum((unsigned char)*p)) {
        clean[n++] = (char)tolower((unsigned char)*p);
    }
}
/* then compare clean with its reverse */

Correct, and easier to read. But you have just introduced a fixed-size buffer that the caller's input can overflow, and the only defences are a bound check you must remember to write or a malloc you must remember to free. The two-pointer version has neither failure mode, which is why it is the one worth learning.

Cost

O(n) time — strlen is one pass and the two indices together traverse the string once — and O(1) space. The copying approach is also O(n) time but O(n) space.

Wrong turns worth recognising

Comparing s[j] instead of s[j - 1]. With j exclusive, s[j] on the first iteration is the '\0' terminator. isalnum('\0') is false, so j decrements and the loop limps on — comparing the wrong characters throughout and quietly returning the wrong answer on most inputs.

Using isalpha instead of isalnum. Digits count in this problem. 12321 is a palindrome and isalpha would skip every character of it, returning 1 for anything numeric — including 123.

Lower-casing only one side. Easy to do when the two comparisons are on different lines. Aa would come back 0.
