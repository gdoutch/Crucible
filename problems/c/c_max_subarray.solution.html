Maximum Subarray Sum

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Kadane's algorithm. The trick is to solve a different, easier problem at every position and let the answer to the real one fall out of it.

Let current be the largest sum of any run ending at the element you are looking at. Then currenti = max(values[i], currenti−1 + values[i]), and the answer to the whole problem is the largest current ever computed.

Why that recurrence is complete: any run ending at i either starts at i — in which case its sum is values[i] — or it extends a run ending at i−1. Among all runs ending at i−1, the best one to extend is the best one, since every extension adds the same values[i]. So two candidates, one comparison, and no information from earlier positions needs to be kept beyond that single number.

The code

int max_subarray_sum(const int *values, int count)
{
    if (count <= 0) {
        return 0;
    }

    int best = values[0];
    int current = values[0];

    for (int i = 1; i < count; i++) {
        int extended = current + values[i];
        current = (values[i] > extended) ? values[i] : extended;
        if (current > best) {
            best = current;
        }
    }
    return best;
}

Answer 6, from the run 4 -1 2 1. Row 4 is the instructive one: current falls from 4 to 3 and the algorithm keeps going anyway, because a run with a small dip in it can still grow into the winner. Row 7 is why best exists as a separate variable — current collapses and the answer must survive it.

Why both variables start at values[0]

Starting either one at 0 is the classic error. It silently encodes "the empty run is allowed", which contradicts the requirement to pick at least one element. On the all-negative array -7 the function would return 0 — a sum achievable only by choosing nothing.

Seeding both with the first element states the base case correctly: with one element available, the best run ending there, and the best run anywhere, are both that element. The loop then starts at index 1 because index 0 is already accounted for.

The same reasoning rules out the popular "clamp to zero" variant:

current = current + values[i];
if (current < 0) { current = 0; }        /* wrong for all-negative input */

It is a correct algorithm for a subtly different problem — one where the empty run is a legal answer worth 0.

The empty array

count <= 0 returns 0 before values[0] is read, which matters because values may be NULL. This is the one place the answer 0 is correct, and it is correct by fiat — the problem defines it, since there is no element to pick.

The zeros only case (0 0 0 → 0) is the companion: a real run whose sum happens to be zero. Both must produce 0, by different routes.

One pass, two ints, and it works on a stream — you never need to see an element twice, so the array need not be held in memory at all.

If you also wanted the indices

Track where the current run began, and record it whenever best improves:

int start = 0, best_start = 0, best_end = 0;
for (int i = 1; i < count; i++) {
    if (values[i] > current + values[i]) {
        current = values[i];
        start = i;                    /* restart -- new beginning */
    } else {
        current = current + values[i];
    }
    if (current > best) {
        best = current;
        best_start = start;
        best_end = i;
    }
}

The bookkeeping is where the remaining bugs live, which is why the problem asks only for the sum.

Wrong turns worth recognising

Updating best before current. The order in the loop body is not arbitrary: best must fold in the new current. Reversed, the answer is always one element behind, and the bug hides on any input whose peak is not at the end.

Returning current. It is the best run ending at the last element, which is only the answer when the optimal run happens to finish there.

Overflow. Summing many large ints can exceed INT_MAX, and signed overflow is undefined behaviour. This problem's generator caps the magnitudes so it cannot arise; production code accumulates into a long long.
