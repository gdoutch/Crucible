Parse an Integer

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

A three-phase parser: optional sign, then one-or-more digits, then end of string. Each phase either consumes what it expects or rejects the whole input. The value is accumulated as you go and written out only once every phase has succeeded.

The interesting part is not the arithmetic. It is that the function has two results — did it work and what was the value — and keeps them separate, so that no legal integer has to be sacrificed as an error code.

The code

#include <stddef.h>

int parse_int(const char *s, int *out)
{
    if (s == NULL || *s == '\0') {
        return 0;
    }

    int negative = 0;
    if (*s == '+' || *s == '-') {
        negative = (*s == '-');
        s++;
    }
    if (*s == '\0') {
        return 0;
    }

    long long value = 0;
    for (; *s != '\0'; s++) {
        if (*s < '0' || *s > '9') {
            return 0;
        }
        value = value * 10 + (*s - '0');
    }

    *out = (int)(negative ? -value : value);
    return 1;
}

Phase by phase

The empty check

An empty string has no digits, so it is rejected before anything else happens. The s == NULL test is defensive — the harness never passes null — but it costs one comparison and turns a crash into a clean rejection.

The sign

negative = (*s == '-') stores the result of a comparison directly, which in C is already 0 or 1. The pointer advances past the sign, and because this is if rather than while, a second sign in "--5" is left for the digit loop to reject.

The "sign and nothing else" check

This is the check people leave out. Without it, "-" arrives at the loop with *s == '\0', the loop condition is false on the first evaluation, zero iterations run, and value is still 0 — so the function reports success and hands back 0. The a lone sign test case exists for precisely this.

The general principle: a for loop expresses "zero or more". The grammar says "one or more". The gap between the two has to be closed by an explicit check, either before the loop or by counting digits and testing afterwards.

The digit loop

The loop runs to the terminator and rejects anything that is not a digit on the way. That single arrangement is what enforces the "nothing after the digits" rule — there is no early exit that could leave trailing characters unexamined. "12a" consumes 1 and 2, meets a, and returns 0.

Compare with the shape that gives atoi its behaviour:

while (*s >= '0' && *s <= '9') {    /* stops AT the bad character */
    value = value * 10 + (*s - '0');
    s++;
}
/* ...and if you forget to check *s == '\0' here, "12a" is accepted as 12 */

Both shapes can be made correct. The first is correct by construction; the second is correct only if you remember to add the check.

*s - '0'

C guarantees that '0' through '9' have consecutive, increasing values in every execution character set. Subtracting '0' therefore maps the character to its numeric value portably. No such guarantee exists for letters — on EBCDIC, 'a' to 'z' is not contiguous — which is why c - 'a' is a portability bug and c - '0' is not.

The write, last

*out is assigned on the final line, after every rejection path has been passed. That honours the contract: a caller who ignored the return value still has whatever was in their variable, rather than a half-parsed prefix. Writing as you go — *out = value; inside the loop — would leave 12 in the caller's variable for the input "12a", which is the worst of both worlds.

Why long long for the accumulator

The problem promises every test value fits in an int, so int would pass. Accumulating in long long is still worth doing: signed overflow in C is undefined behaviour, not a wrap-around, and a compiler is entitled to assume it never happens. Given value * 10 + digit on an int, one long input turns the whole function into nonsense the optimiser is allowed to reshape freely. The wider accumulator keeps that off the table for anything up to 18 digits.

A production parser would go further and detect the overflow — that is what strtol does, reporting it through errno == ERANGE. Note also that -value where value is long long handles INT_MIN correctly: 2147483648 is representable there, whereas negating INT_MIN as an int is itself undefined.

Cost

O(n) in the length of the string, O(1) space. One pass, no allocation, no lookahead.

Wrong turns worth recognising

isdigit(*s) without the cast. Same <ctype.h> hazard as elsewhere: the argument must be representable as unsigned char. isdigit((unsigned char)*s) is fine; the explicit <'0' || >'9' range test avoids the question entirely and is locale-independent, which for a decimal parser is a feature.

Accepting whitespace. strtol skips leading spaces; this specification does not. " 42" must be rejected.

Rejecting leading zeros. "007" is a valid way to write 7. The accumulator handles it without help — adding a rule against it is inventing a requirement.
