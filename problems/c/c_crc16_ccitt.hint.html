Compute a CRC-16/CCITT-FALSE Checksum

The shape of the algorithm

One 16-bit register, one byte at a time:

uint16_t crc = 0xFFFF;
for each byte b in data:
    crc ^= (uint16_t)((uint16_t)b << 8);
    repeat 8 times:
        if top bit of crc is set:
            crc = (crc << 1) ^ 0x1021;
        else:
            crc = crc << 1;
return crc;

Every piece of that -- the starting value, XORing the byte into the top half of the register rather than the bottom, and shifting left -- is part of what makes this specifically CCITT-FALSE rather than one of the other CRC-16 variants that share the same polynomial.

Two variants that look almost right

Starting the register at 0x0000 instead of 0xFFFF produces CRC-16/XMODEM -- same polynomial, different checksum. The two only ever agree by coincidence. Check your implementation against an empty input first: CCITT-FALSE returns 0xFFFF unchanged (nothing was ever folded in to move the register away from its start), which is the fastest way to notice a wrong initial value before it gets buried under real data.

Reflecting the bits -- feeding each byte in LSB-first and shifting the register right -- produces a different family of CRC-16 entirely (MODBUS, ARC). CCITT-FALSE never reflects anything: MSB-first in, shift left, top bit decides whether the polynomial gets XORed in.

Prove it against the standard check value

The CRC catalogue defines a reference input for exactly this reason: the nine bytes of the ASCII string "123456789" must produce 0x29B1. If your function does not produce that, something about the bit order or the initial value is off, before you even get to your own test cases.
