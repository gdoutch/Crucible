A Shift-Based Low-Pass Filter (No Floats)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

int iir_update(int previous_output, int sample, int shift)
{
    int delta = sample - previous_output;

    return previous_output + (delta >> shift);
}

Why a shift stands in for a fraction

The ordinary exponential moving average is output += alpha * (sample - output), where alpha is typically something like 0.1 -- move a tenth of the way to the new sample every time. A right shift by k divides by 2^k, which is exactly a fractional multiply by 1 / 2^k -- alpha = 1/16 for shift = 4, alpha = 1/4 for shift = 2, and so on. It only offers powers of two rather than any fraction you like, and in exchange it costs one integer shift instead of a floating-point multiply -- the trade that makes it worth using at all on hardware without an FPU, or in code where floating-point results have to be bit-for-bit reproducible.

The signed-shift trap, worked through

delta is negative whenever the sample is below the current output, and the filter needs to move down by roughly the same fraction it would move up -- delta >> shift on a signed int does that correctly, because C's right shift on a signed negative value is (on every mainstream compiler, the same caveat as the shift-based population count in Count the Set Bits) an arithmetic shift: it copies the sign bit down, so a small negative delta shifts to a small negative correction.

Make delta unsigned instead -- easy to do by accident with earlier bitfield exercises in this set having pushed everything toward unsigned int -- and the same right shift becomes a logical shift: zeros come in from the top instead of copies of the sign bit. A delta of -10, reinterpreted as unsigned, is a number close to 2^32; shifted right by even a couple of bits it is still enormous, and adding it to previous_output does not nudge the filter, it destroys it. This is not a subtle few-percent error -- it is wrong by nine or ten orders of magnitude on the very first sample below the previous output, which is exactly what makes it a good thing to catch in review rather than in the field.

The "stuck filter" property

With shift = 4, any gap smaller than 16 shifts to 0: 5 >> 4 is 0, so a constant sample only 5 away from the current output produces a correction of exactly nothing, forever. The fixed test built around this is not checking for a bug -- it is checking that your implementation reproduces this exact, well-documented behaviour of the formula as specified, because a candidate implementation that "fixes" it (by rounding the shift, say) would then disagree with the reference on this case and fail the test for a different reason: not matching the specification it was asked to implement.

The asymmetry is real: a negative gap of the same size does not get stuck the same way, because C's arithmetic right shift rounds toward negative infinity rather than toward zero -- -5 >> 4 is -1, not 0, so a negative gap always closes by at least one unit per call and eventually reaches zero. A filter built this way converges from below reliably and can stall indefinitely from above, within a band of up to 2^shift - 1 around the target -- worth knowing before choosing this technique for something where sitting permanently a fixed amount short of the target is not acceptable.

Cost

One subtraction, one shift, one addition per sample: O(1) time and space, and -- unlike a floating-point multiply -- identical bit patterns on every platform that implements arithmetic right shift the standard way.
