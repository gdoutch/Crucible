Fixed-Capacity LRU Cache (No Dynamic Allocation)

Build two small helpers first

Almost everything this cache does is one of two operations on the recency list, applied to a slot index it already knows:

  • detach(slot) — remove slot from wherever it currently sits in the list, fixing up whichever neighbours it had.
  • push_mru(slot) — insert slot at the most-recently-used end, fresh.

Every one of lru_get's hit path, lru_put's update path, and lru_put's eviction path is detach, then push_mru, on a slot found a different way each time. Writing that pair once and reusing it is what keeps the three call sites from drifting out of sync with each other.

What detach has to update

p = prev[slot], n = next[slot]
if p exists: next[p] = n
if n exists: prev[n] = p
if slot was mru: mru = p
if slot was lru: lru = n

The last two lines are the ones it is easy to forget, because they only matter when the detached slot was at an end of the list -- which is exactly the case eviction always hits, since it always detaches the current lru.

Trace capacity == 1 through that pseudocode by hand: the only slot is both mru and lru at once, with no prev or next at all. Detaching it should leave the list genuinely empty (mru = lru = -1) for a moment, before push_mru puts the same slot straight back as the cache's only entry again. If your detach only updates one of mru/lru when a slot is both, this is where it shows.

Where a new slot comes from

While count < capacity, a new key claims slot number count and count increments -- slots are claimed in order, once each, forever. Once the cache is full, a new key does not get a slot of its own: it takes over whichever slot is currently lru, after detaching it.
