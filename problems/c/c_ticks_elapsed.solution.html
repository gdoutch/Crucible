Elapsed Ticks Since a Free-Running Counter (MISRA Unsigned Arithmetic)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

#include <stdint.h>

uint32_t ticks_elapsed(uint32_t now, uint32_t start)
{
    return now - start;
}

One line, no branch. It is not a simplification of some longer correct answer — it is the correct answer, for a reason specific to how C defines unsigned subtraction.

Why the subtraction is already correct when it wraps

C defines unsigned arithmetic to wrap modulo 2**32 for a 32-bit type, and that wraparound is well-defined behaviour, not undefined behaviour the way signed overflow is. now - start, computed in uint32_t, is really (now - start) mod 2**32.

Because the hardware counter itself increments and wraps the same way — mod 2**32 — that one expression recovers the true forward distance from start to now regardless of whether now is numerically bigger or smaller than start. Take start = 4294967290 (five ticks from the top), now = 10: the counter climbed 5 ticks to UINT32_MAX, wrapped to 0, then climbed 10 more. now - start in uint32_t is 10 - 4294967290 + 4294967296 = 16 — exactly 5 + 1 + 10, without a single if anywhere in the calculation.

Why the defensive-looking version is worse, not safer

It is tempting to spell the wraparound case out by hand:

if (now >= start) {
    result = now - start;
} else {
    result = (UINT32_MAX - start) + now + 1;
}

This is not more defensive than the one-liner — it is a manual reimplementation of exactly what unsigned subtraction already does, written in a form that is one off-by-one away from wrong. (Is it + now or + now + 1? The counter is zero-based, so getting this wrong by one tick is easy and the test suite is built to notice.) Every fixed test that crosses the wrap boundary is there to catch that fencepost, not to reward writing a branch at all.

It is also tempting to cast to a signed type to "check the sign" of the difference: (int32_t)now - (int32_t)start. This reintroduces the exact failure mode uint32_t was chosen to avoid. The true difference can itself exceed INT32_MAX — the "one tick short of a full lap" test is precisely this case, where the correct elapsed count is 4294967295, nowhere near representable as a signed 32-bit value — and signed overflow on top of that is undefined behaviour, not a negative number with a meaning you can rely on.

Why this is a MISRA problem, not just a bit-twiddling one

Directive 4.6 -- use the sized types from <stdint.h> -- usually reads as a precision-and-portability rule: know exactly how wide your integer is. Here it is also a correctness rule. uint32_t is not an arbitrary label for "an integer that holds tick counts" — it is the type whose specific, defined-overflow arithmetic is what makes now - start the right answer without a special case. Reach for a signed type, or hand-roll the wraparound logic instead of trusting the type, and the correctness this idiom relies on is exactly what gets thrown away.

What the fixed tests are checking

An ordinary interval with no wrap, and now == start giving zero, establish the baseline. A counter that wraps once between the two readings, worked through above, checks the general case. One tick short of a full lap returns UINT32_MAX itself — the largest value the function can produce, and the case a signed cast would corrupt. Reading UINT32_MAX as start and 0 as now checks the wrap boundary exactly, where a hand-rolled branch's fencepost error would show up first.
