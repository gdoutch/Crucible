Remove Duplicates From a Sorted Array

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Two indices over one array. read sweeps every element; write marks the end of the deduplicated prefix being built at the front. Each element is kept — copied to values[write], then write advances — only if it differs from the last value kept. Duplicates are handled by doing nothing, which leaves them behind as read moves past them.

Sortedness is what makes this possible: equal values are adjacent, so "different from the last one kept" is the same test as "not seen before".

The code

int remove_duplicates(int *values, int count)
{
    if (count <= 0) {
        return 0;
    }

    int write = 1;
    for (int read = 1; read < count; read++) {
        if (values[read] != values[write - 1]) {
            values[write] = values[read];
            write++;
        }
    }
    return write;
}

Why writing over the array is safe

write starts equal to read and only ever advances when read does, so the invariant write <= read holds throughout. The slot being written has therefore already been read this iteration or in an earlier one. No live data is ever clobbered.

When write == read the copy is a self-assignment — harmless, and not worth an if to avoid. That is the case for an array with no duplicates at all, where the function walks the whole array writing every element onto itself and returns count.

values[write - 1] or values[read - 1]?

Both pass. values[read - 1] compares with the immediately preceding original element, which on sorted input is equivalent because duplicates are contiguous.

values[write - 1] compares with the last value actually kept, which is the property the function is really maintaining. It keeps working if the input is only grouped rather than fully sorted, and it says what the code means. Prefer it.

The count <= 0 guard is not optional

Without it, write is initialised to 1 and returned for an empty array — claiming one element in an array that has none, and one whose pointer may be NULL. The empty array test case catches exactly this.

This is the cost of the "first element is always kept" shortcut: it assumes there is a first element. The guard is where that assumption is paid for. An alternative that avoids the guard entirely is to start write = 0 and read = 0, keeping an element when write == 0 || values[read] != values[write - 1] — one extra test per iteration in exchange for one fewer special case.

The other fixed cases

all the same (7 7 7 7 7) Every comparison fails, nothing is ever copied, write stays at 1. The extreme case for the compaction: four elements dropped and not one byte moved.

Cost

O(n) time — one pass, one comparison per element — and O(1) extra space. Each element is written at most once.

The alternative that allocates a second array and copies the survivors into it is also O(n) time, but O(n) space plus a malloc that can fail and a free you must not forget. Worse, the result would be in the wrong place: the contract says the caller's array holds the answer, so you would have to copy it back.

Wrong turns worth recognising

Shuffling the tail down on every duplicate. Finding a repeat and memmove-ing the rest of the array left by one is the instinctive "delete", and it turns an O(n) problem into O(n²) — quadratic on an array that is all one value, which is one of the fixed cases.

Zeroing the tail. Clearing the slots beyond write feels tidy but is outside the contract, and it destroys data the caller may still own — the array might be a window into something larger.

Returning the number removed. The function returns how many values remain. 7 7 7 7 7 returns 1, not 4.
