Edit Distance

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

The fewest single-character insertions, deletions and replacements that turn a into b. This is the Levenshtein distance. kitten → sitting is three.

Why greedy fails

Try walking both strings from the front and fixing each difference as you meet it. On kitten/sitting that happens to work. On ab/ba it does not: the first characters differ, so a greedy replace costs 1, then the second pair differs too, so that is 2 — but the true answer is also 2, so even this does not expose it. The real failures come when an early insertion would have re-aligned everything downstream, and a greedy pass cannot see that far.

The fix is to stop making decisions and start computing every prefix answer.

The table

Let d[i][j] be the edit distance between the first i characters of a and the first j characters of b.

The answer you want is d[len_a][len_b], the bottom-right corner. The table has (len_a + 1) × (len_b + 1) cells — the extra row and column are for the empty prefixes, and they are where the whole thing is anchored.

The edges are not zero

Work out d[0][j] for yourself: turning the empty string into the first j characters of b. There is only one way — insert them, one at a time. So the first row counts up: 0, 1, 2, 3… And by the same argument the first column counts down the deletions.

Getting these wrong is the most common way to fail this problem, and the first empty and second empty test cases exist to catch it.

Every other cell is the smallest of three

To reach d[i][j], the last edit you performed was one of exactly three things. Work out what each costs in terms of a neighbouring cell:

  • Delete a[i-1] — you have dealt with one more character of a and none more of b. Which neighbour does that leave you at, and what does the deletion add?
  • Insert b[j-1] — one more character of b accounted for, none of a.
  • Match or replace — one more of each. This one is free if a[i-1] == b[j-1], and costs 1 otherwise.

Take the minimum of the three. That is the entire recurrence.

Mind the indices. d[i][j] is about the first i characters, so the character it concerns is a[i - 1], not a[i]. The table is offset by one from the strings, and mixing the two up is the second most common way to fail this.

Fill order

Each cell depends on the one above, the one to the left, and the one diagonally up-left. So sweep row by row, left to right, and every dependency is already computed.

Two rows are enough

Look again at those three dependencies: none of them is more than one row above. The rows before that are never read again, so there is no reason to keep them. Allocate two rows of len_b + 1 ints, fill the new one from the old one, then swap the pointers and go again.

The full table is fine for these test sizes. The two-row version is not much harder and turns O(n·m) memory into O(m).

Check yourself before you press Go

  • Both empty → 0.
  • hello/hello → 0. The diagonal must cost nothing when the characters match.
  • ""/abcd → 4, and abcde/"" → 5. These are the two edges of the table, read straight off.
  • kitten/sitting → 3.
  • Whatever you allocated, did you free it — on every return path?
Still stuck? A bigger nudge

The recurrence, spelled out:

d[0][j] = j
d[i][0] = i

d[i][j] = min( d[i-1][j] + 1,                        /* delete  */
               d[i][j-1] + 1,                        /* insert  */
               d[i-1][j-1] + (a[i-1] != b[j-1]) )    /* keep or replace */

In the two-row form, previous[] is row i-1 and current[] is row i. Then d[i-1][j] is previous[j], d[i][j-1] is current[j-1], and d[i-1][j-1] is previous[j-1]. Do not forget to set current[0] = i at the start of each row.
