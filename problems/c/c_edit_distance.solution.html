Edit Distance

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Levenshtein distance by dynamic programming. Define

d[i][j] = the edit distance between the first i characters of a and the first j characters of b.

Then every cell is answerable from three neighbours, because whatever the optimal edit sequence for (i, j) is, its last step must be one of exactly three things:

Last stepLeaves you atCost
Delete a[i−1]d[i−1][j]+1
Insert b[j−1]d[i][j−1]+1
Keep or replaced[i−1][j−1] +0 if the characters match, +1 if they differ

Take the cheapest. Because the three sub-problems are strictly smaller, and because each is solved once and reused, the whole table fills in O(n·m) time.

The base cases carry real information

d[0][j] = j: turning the empty string into a j-character string requires j insertions and there is no cheaper way. d[i][0] = i: i deletions. These are not padding — the entire table is built out of them, and a first row of zeros produces answers that are far too small everywhere.

The code

#include <stdlib.h>
#include <string.h>

static int smallest_of(int a, int b, int c)
{
    int smallest = (a < b) ? a : b;
    return (smallest < c) ? smallest : c;
}

int edit_distance(const char *a, const char *b)
{
    size_t len_a = strlen(a);
    size_t len_b = strlen(b);

    int *previous = malloc((len_b + 1) * sizeof *previous);
    int *current = malloc((len_b + 1) * sizeof *current);
    if (previous == NULL || current == NULL) {
        free(previous);
        free(current);
        return -1;
    }

    for (size_t j = 0; j <= len_b; j++) {
        previous[j] = (int)j;
    }

    for (size_t i = 1; i <= len_a; i++) {
        current[0] = (int)i;
        for (size_t j = 1; j <= len_b; j++) {
            int replace_cost = (a[i - 1] == b[j - 1]) ? 0 : 1;
            current[j] = smallest_of(previous[j] + 1,
                                     current[j - 1] + 1,
                                     previous[j - 1] + replace_cost);
        }
        int *swap = previous;
        previous = current;
        current = swap;
    }

    int result = previous[len_b];
    free(previous);
    free(current);
    return result;
}

Bottom right: 3. Reading the diagonal backwards recovers the edits — replace k→s, replace e→i, insert g.

Look at the cell for ki vs si (row 2, column 2). Its three candidates are previous[2] + 1 = 3 (delete), current[1] + 1 = 3 (insert), and previous[1] + 0 = 1 (the is match, so free). The diagonal wins, and the earlier replacement of k is carried forward without being paid for twice.

The two-row optimisation

Every cell reads only previous[j], previous[j-1] and current[j-1] — nothing from more than one row back. So rows 0..i-2 can be discarded as soon as row i-1 is complete.

The mechanics:

  • previous is seeded with row 0 — 0, 1, 2, …, the insertions.
  • Each row sets current[0] = i first. That is the first-column base case, and it must be written before the inner loop, because current[1] reads current[0].
  • At the end of the row the two pointers are swapped, so the row just finished becomes previous and the buffer holding the row before it is recycled as the new current.

Because of that final swap, the answer is in previous and not in current when the loop ends. Reading current[len_b] gives you row len_a - 1, off by one row — which is off by approximately one in the answer, so it passes the empty and identical cases and fails kitten/sitting.

Memory drops from O(n·m) to O(m). The price is that you can no longer walk the table backwards to recover the actual sequence of edits — for that you need the whole thing, or Hirschberg's algorithm, which gets the sequence in linear space by divide and conquer.

The empty-string cases

CasePath through the code
both empty The seeding loop writes previous[0] = 0. The outer loop never runs. previous[0] is returned: 0.
first empty (""/abcd) Outer loop never runs; the answer comes straight from the seeded row — previous[4] = 4. This case is a direct test of the base row.
second empty (abcde/"") len_b is 0, so the inner loop never runs and each row does nothing but current[0] = i. The final previous[0] is 5. This tests the first-column base case, and it is where forgetting current[0] = i shows up.
identical Every diagonal step is free, so the minimum tracks the diagonal from corner to corner and arrives at 0.

Notice that both single-empty cases are handled by the seeding and the base cases alone, with no special-case code. Allocating len_b + 1 entries — never zero — is what makes that work.

Memory discipline

Two allocations, and both are freed on both exits. The failure path uses the fact that free(NULL) is defined to do nothing, so it can release both without checking which one succeeded. Returning -1 for allocation failure is a sentinel the caller here never sees — a distance can never be negative, so it is at least unambiguous.

The free(previous); free(current); at the end frees both buffers regardless of how many times they were swapped: the two pointers always name the two blocks, just possibly the other way round.

Cost

O(n · m) time, O(min(n, m)) space if you also swap the arguments so the shorter string drives the row length — a worthwhile addition not made here.

There is no substantially faster general algorithm; the problem is believed to require quadratic time under the strong exponential time hypothesis. When you only care whether the distance is below some threshold k, the band of cells within k of the diagonal is enough, giving O(k·n).

Wrong turns worth recognising

A first row of zeros. The single most common failure. It encodes "the empty string is free to become anything", and the resulting answers are much too small everywhere. Both empty-string cases catch it immediately.

Indexing the strings with i and j. The table is offset by one from the strings. d[i][j] concerns a[i - 1] and b[j - 1]. Using a[i] reads one character too far — and at i == len_a that is the terminator, which compares unequal to everything and quietly adds replacements.

Plain recursion without memoisation. The recurrence transcribes directly into a three-way recursive call, and it is exponential — the same subproblems are recomputed astronomically often. kitten/sitting would take a noticeable moment; two twenty-character strings would not finish. The table is the memoisation.
