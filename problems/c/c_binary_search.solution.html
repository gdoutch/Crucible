Binary Search

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Maintain a window [low, high] with the invariant: if the target is in the array at all, its index is inside this window. Look at the middle element. Because the array is sorted, comparing it with the target tells you which half of the window still satisfies the invariant, and the other half can be discarded whole.

The window loses at least half its elements every iteration, so an array of a million entries is exhausted in twenty comparisons.

The code

int binary_search(const int *values, int count, int target)
{
    int low = 0;
    int high = count - 1;

    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (values[mid] == target) {
            return mid;
        }
        if (values[mid] < target) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }
    return -1;
}

The three details that have to agree

This is a nine-line function with a reputation for being hard to get right, and the reason is that three separate decisions all encode the same choice. Here the window is inclusive at both ends, so:

DecisionValueBecause
high starts at count - 1 It must be a valid index. count is one past the end.
Loop while low <= high When they are equal the window still holds one unexamined element. Using < skips it — and that element is very often the answer.
Updates mid ± 1 mid has just been compared and is not the target, so it belongs in neither half. Excluding it is also what guarantees the window shrinks.

Termination depends on that ± 1. Suppose you wrote low = mid. With low = 0, high = 1, mid is 0; if the target is larger, low becomes 0 again and the state has not changed. The loop spins forever, and Crucible reports TIMEOUT on that case rather than a wrong answer.

Walking a case

The last element test: 1 3 5 7 9 11 13, target 13.

lowhighmidvalues[mid]Action
06377 < 13 → low = 4
4651111 < 13 → low = 6
66613found → return 6

The last row is the one that matters. With low < high as the condition, the loop would have exited before that third iteration and returned -1 for a value that is plainly in the array. That is why this specific case is in the fixed set.

Why the empty array needs no guard

count is 0, so high is initialised to -1, and 0 <= -1 is false on the first evaluation. The body never runs, values — which may legitimately be NULL — is never dereferenced, and the function returns -1.

The negative high looks alarming but is never used as an index. This is the payoff of the inclusive convention: the empty window is represented naturally, rather than needing a case of its own.

The overflow in the midpoint

low + (high - low) / 2 and (low + high) / 2 give the same answer for every input this problem can produce. They differ when low + high exceeds INT_MAX — which needs an array of more than a billion elements, so roughly 4 GB of ints. Not reachable here; very reachable in a 64-bit service, and this exact bug lived in java.util.Arrays.binarySearch from 1997 until 2006.

high - low is a non-negative difference between two values that both fit, so it cannot overflow; halving it and adding to low lands inside the window by construction. It is the same number of machine instructions. Write it this way out of habit and the question never arises.

Cost

O(log n) comparisons, O(1) space. The iterative form uses no stack; the recursive form is tail-recursive and usually optimised into this loop anyway.

For contrast: a linear scan is O(n). On the 7-element fixed case that is 7 comparisons against 3 — nothing. On a million elements it is a million against twenty.

Wrong turns worth recognising

Returning the wrong "not found" value. Returning low at the end — the insertion point — is what std::lower_bound does and is genuinely more useful, but this problem asks for -1.

Assuming a unique answer. With duplicates, this returns some index holding the target, not necessarily the first. Finding the first is a different algorithm: do not return early on a match; move high = mid - 1 and remember the position, and keep going. The fixed tests here use distinct values, so the distinction never shows — worth knowing before you copy this into something that matters.

Searching an unsorted array. The result is not "slower"; it is meaningless. Binary search's every step is an inference from the ordering. Here the harness guarantees ascending input.
