Validate a CAN Message's Rolling Counter and Checksum

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Two independent checks, both of which have to pass for a frame to be accepted:

  1. Checksum — recompute it from the frame's own contents and compare to what arrived.
  2. Counter — it must be exactly one more than the last accepted frame's counter, wrapping at 16, unless there has not been an accepted frame yet.

Either check failing rejects the frame. The function itself keeps no memory between calls -- last_good_counter arrives as a parameter, supplied by the harness, and the harness is the one that decides whether to update it, based on what you return.

The checksum

unsigned char check = (unsigned char)counter;
for (int i = 0; i < length; i++) {
    check ^= data[i];
}
/* compare check to received_checksum */

The trap the problem is built around

Start the checksum from the counter, not from zero. A checksum over the payload bytes alone catches corruption in the payload, but it cannot tell two frames apart if their payload happens to be identical and only the counter differs -- exactly the case a stale, replayed frame produces. Folding counter into the checksum means a frame with the right payload and the wrong counter no longer has a valid checksum either, closing that gap.

The other trap: do not let a rejected frame move the baseline

The harness only advances last_good_counter when your function returns 1 -- so as long as you always compare against the last_good_counter you were given, rather than keeping any counter of your own, a corrupted or out-of-sequence frame in the middle of a run cannot poison what comes after it. A fixed test sends a good frame, a corrupted one, and then a frame that only makes sense counted from before the corrupted one arrived -- if that last frame is rejected, the baseline was moved somewhere it should not have been.

Watch out, beyond that

  • last_good_counter == -1 means no frame has ever been accepted -- the very first frame's counter is not compared to anything, only its checksum has to be right.
  • The counter wraps: 15 is followed by 0, which is (15 + 1) % 16, not a value one past the end of a valid range.
