Fixed-Capacity LRU Cache (No Dynamic Allocation)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

static void detach(LruCache *cache, int32_t slot)
{
    int32_t p = cache->prev[slot];
    int32_t n = cache->next[slot];
    if (p != -1) { cache->next[p] = n; }
    if (n != -1) { cache->prev[n] = p; }
    if (cache->mru == slot) { cache->mru = p; }
    if (cache->lru == slot) { cache->lru = n; }
}

static void push_mru(LruCache *cache, int32_t slot)
{
    cache->prev[slot] = cache->mru;
    cache->next[slot] = -1;
    if (cache->mru != -1) { cache->next[cache->mru] = slot; }
    cache->mru = slot;
    if (cache->lru == -1) { cache->lru = slot; }
}

static int32_t find_slot(const LruCache *cache, int32_t key)
{
    for (int32_t i = 0; i < cache->count; i++) {
        if (cache->key[i] == key) {
            return i;
        }
    }
    return -1;
}

void lru_init(LruCache *cache, int32_t capacity)
{
    cache->capacity = capacity;
    cache->count = 0;
    cache->mru = -1;
    cache->lru = -1;
}

int32_t lru_get(LruCache *cache, int32_t key)
{
    int32_t slot = find_slot(cache, key);
    if (slot < 0) {
        return -1;
    }
    detach(cache, slot);
    push_mru(cache, slot);
    return cache->value[slot];
}

void lru_put(LruCache *cache, int32_t key, int32_t value)
{
    int32_t slot = find_slot(cache, key);
    if (slot >= 0) {
        cache->value[slot] = value;
        detach(cache, slot);
        push_mru(cache, slot);
        return;
    }

    if (cache->count < cache->capacity) {
        slot = cache->count;
        cache->count++;
    } else {
        slot = cache->lru;
        detach(cache, slot);
    }
    cache->key[slot] = key;
    cache->value[slot] = value;
    push_mru(cache, slot);
}

Why detach and push_mru are worth splitting out

Three different situations end with the same two steps: a cache hit on lru_get, an update-in-place on lru_put, and an eviction on lru_put all detach a slot from wherever it is and push it back on at the most-recently-used end. Writing that pair once and calling it from all three places is not just less typing -- it is what guarantees the three call sites cannot quietly disagree about how "become most recently used" is implemented, which is exactly the kind of drift a hand-inlined version in each function invites.

Why detach checks mru and lru separately, both, unconditionally

A slot being detached might be in the middle of the list (neither check fires), at one end (exactly one fires), or -- with capacity == 1 -- the only node, in which case both fire. Writing if (slot == mru) { mru = p; } else if (slot == lru) { lru = n; } instead of two independent ifs looks equivalent right up until that single-node case, where it silently leaves one of mru or lru still pointing at the slot that was just detached from everything else. The next lookup that trusts that stale pointer walks into a slot no longer linked to anything.

Why eviction detaches before overwriting, not after

lru_put's full-cache branch calls detach(cache, slot) while cache->key[slot] and cache->value[slot] still hold the evicted entry's data. That ordering does not actually depend on the key or value -- detach only reads and writes prev/next/mru/lru -- but doing it before the overwrite keeps the invariant simple to state: by the time a slot's key and value are changed, it is guaranteed to already be out of the list, so push_mru is always inserting a slot that starts from a clean, unlinked state, whether it is brand new or being recycled.

Why a hit has to move the entry, not just read it

The whole point of "least recently used" is that recency is tracked by *use*, and a get that finds a key is a use. A lru_get that only searches and returns leaves stale entries parked at the most-recently-used end forever (nothing ever pulls them back toward eviction) while entries that are actually being read regularly drift toward the least-recently-used end and get evicted out from under active use. The fixed test that reads a key and then fills the cache past capacity is built to catch exactly this: if the read entry is gone afterwards, get did not touch the list.

Cost

O(1) for lru_get and the touch/evict paths of lru_put's bookkeeping -- detach and push_mru only ever follow a fixed number of index links, regardless of capacity. find_slot is O(capacity), a linear scan over at most LRU_MAX_CAPACITY entries; a real high-capacity cache would pair this array with a hash table keyed on the same slot indices to make lookup O(1) too, which changes nothing about the linked-list logic above.
