Multiply Two Q15 Fixed-Point Numbers

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Each Q15 value is really raw / 32768. Multiplying two of them the ordinary way multiplies both the raw integers and both the / 32768 scales, leaving a result scaled by / 32768 / 32768 — one / 32768 too many. Shifting the product right by 15 removes exactly one of them, back down to a single Q15 scale.

Three things the result needs

  1. A wide multiply. Two 16-bit-range values multiplied together need up to 32 bits just for the raw product, before the shift even happens. Do the multiplication in a 64-bit type.
  2. Rounding, not truncation. Add half of what the shift is about to discard — 1 << 14, half of 1 << 15 — before shifting, so the result rounds to the nearest representable value instead of always rounding down.
  3. Saturation. See below.

The trap the problem is built around

Q15's representable range is a little over -1.0 to a little under +1.0 — the largest positive value, 32767 / 32768, never quite reaches 1.0. But -1.0 * -1.0 = 1.0 exactly, which is not representable. q15_multiply(-32768, -32768) is a fixed test for exactly this: the rounded result before any clamping is 32768, one past the top of the 16-bit signed range, and the correct answer is the saturated 32767 — not a value that has silently wrapped around to something negative.

Watch out, beyond the overflow

  • Do the shift after the multiply, on the full-width product — not on either input beforehand. Shifting an input first to "keep it small" throws away exactly the low-order bits the final rounding needs.
Still stuck? A bigger nudge 
long long product = (long long)a * (long long)b;
long long rounded = (product + (1LL << 14)) >> 15;

/* clamp `rounded` to [-32768, 32767] here */

Check yourself before you press Go

  • q15_multiply(16384, 16384) (0.5 * 0.5) → 8192 (0.25).
  • q15_multiply(-32768, -32768) → 32767, the saturated case.
  • q15_multiply(32767, 32767) → 32766, close to the corner but not saturating -- worth checking your saturation logic does not fire when it should not.
