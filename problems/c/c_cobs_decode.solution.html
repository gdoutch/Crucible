Decode a COBS-Framed Serial Buffer

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

int cobs_decode(const uint8_t *enc, size_t enc_len, uint8_t *out)
{
    size_t read = 0;
    size_t written = 0;

    while (read < enc_len) {
        uint8_t code = enc[read];
        if (code == 0U) {
            return -1;                 /* a zero can never appear in enc */
        }
        if (read + (size_t)code > enc_len) {
            return -1;                 /* claims more bytes than remain */
        }
        read++;

        for (uint8_t i = 1U; i < code; i++) {
            out[written] = enc[read];
            written++;
            read++;
        }

        if (code != 0xFFU && read != enc_len) {
            out[written] = 0U;
            written++;
        }
    }
    return (int)written;
}

Why the bounds check comes before the copy, not during it

read + (size_t)code > enc_len is checked once, before a single byte of this block is copied. That ordering matters: a version that instead checked bounds inside the copy loop, byte by byte, would still report the frame as invalid eventually -- but only after already having written some of a corrupt block's bytes into out, on the assumption the rest would follow. A caller that used the return value correctly (checking for -1 before trusting out at all) is unaffected either way, but a caller that read out first and the return value second would see a partially-decoded frame with no indication of where it stopped being trustworthy. Checking the whole block's requirement up front costs nothing extra and removes the question entirely.

The two cases that suppress the trailing zero

code != 0xFFU && read != enc_len is doing two separate jobs joined by one &&, and both matter:

  • code != 0xFFU -- a full 254-byte block never implies a zero. It exists specifically so a run of 254 or more non-zero bytes does not force an invented zero into the stream every 254 bytes; the encoder emits 0xFF precisely when it hits that count without encountering an actual zero to report.
  • read != enc_len -- after advancing past this block's data, if there is nothing left in enc, this was the last block. Its implied zero, if it had one, was the frame delimiter -- already consumed by the layer that handed you enc with the delimiter stripped off. Appending one here manufactures a trailing zero that was never part of the original message.

Getting only one of these right is a believable partial implementation: it passes on short inputs that never reach 254 non-zero bytes in a row and never happen to end exactly on a block boundary, and then produces output one byte too long -- with everything after that point shifted -- the moment a longer or more awkwardly-shaped frame arrives.

Why an all-zero payload round-trips through blocks of exactly code 1

Every original zero byte becomes its own block boundary: a code of 1 (zero literal bytes), followed by the appended zero standing in for the original one -- unless that zero happened to be the very last byte of the message, in which case, per the rule above, nothing is appended and the frame simply ends. Three original zero bytes therefore encode as three consecutive code-1 blocks with the frame's own end supplying the final zero implicitly.

Cost

O(enc_len) — every byte of the encoded input is visited exactly once, either as a code byte or as a literal data byte, with a single output byte written per input byte plus at most one implied zero per block.
