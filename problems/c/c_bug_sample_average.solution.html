Fix the Sample Averager

Worked solution

This page contains the complete answer and explains why each part of it is there.

The defect

A function parameter written as an array is not an array. It is a pointer. sizeof applied to it therefore measures a pointer, and the element count it appears to compute is a property of the machine rather than of the data.

The line that does the damage:

size_t n = ARRAY_LEN(samples);   /* (sizeof(samples) / sizeof((samples)[0])) */

and the fix, which is the whole fix:

size_t n = count;

Or, more honestly, drop n altogether and use the parameter the caller supplied for exactly this purpose:

uint16_t average_samples(const uint16_t samples[], size_t count)
{
    uint32_t total = 0;
    size_t i;

    if (count == 0u) {
        return 0u;
    }

    for (i = 0; i < count; i++) {
        total += samples[i];
    }

    return (uint16_t)(total / count);
}

Why the parameter is a pointer

C has a rule for parameters specifically. A parameter declared with an array type is adjusted, by the compiler, to a pointer to the element type. These three declarations are not merely similar, they are the same declaration:

uint16_t average_samples(const uint16_t samples[], size_t count)
uint16_t average_samples(const uint16_t samples[64], size_t count)
uint16_t average_samples(const uint16_t *samples,   size_t count)

The second one is the cruel one. You may write a size in those brackets, the compiler will accept it, and it will change precisely nothing — not the type, not sizeof, not any bounds check, because there is no bounds check. It is a comment that looks like code.

So inside the function, samples is a pointer, and:

sizeof(samples)      /* the size of a pointer   */
sizeof(samples[0])   /* the size of a uint16_t: 2 */

The division is arithmetic on two sizes that have nothing to do with each other. It yields a constant, and the constant depends on your target:

Targetsizeof pointern comes out as
x86-64 PC (Windows or Linux)84
32-bit Cortex-M, AVR32, x8642
8-bit AVR, MSP430 small model21

Which is worth sitting with for a moment. This defect averages four samples on the developer's desk and two on the board, and on a small part it averages one sample and calls it a filter. A bug whose behaviour changes between the host build and the target build is one of the more expensive kinds to chase, and this is one line of entirely reasonable-looking code.

Reading the failures backwards

Every failing number in the suite is now predictable. The harness's buffer is at file scope, so it starts as all zeros, and anything the function reads past count is a clean 0 rather than stack litter — which is why these came out the same on every run:

Two of those rows read past the end of the data. The block held three samples and the function read four. Nothing crashed, nothing was reported, and the answer was merely wrong — the ordinary outcome of a small overrun, and the reason small overruns survive so long in the field.

The two cases that passed

four samples, truncated. The buffer length happened to equal the constant the machine produced, so the wrong count and the right count were the same number. The test passed. It would have passed on the day the code was written, on the day it was reviewed, and in every regression run since — and it would have started failing the moment someone cross-compiled it for the target, where the constant is 2.

That is why it is in the suite. A test that passes for the wrong reason offers no protection and looks exactly like a test that passes for the right one.

Constant input hides it too, which the randomised "all reading N" case demonstrates: the mean of some identical readings is the mean of all of them. If the bench test for this filter was "tie the input to a reference voltage and check the reading", it passed.

Watch the randomised noisy case as well. Averaging the first four of twenty noisy samples about a steady level gives an answer a few counts away from the true mean — plausible, in range, and indistinguishable from the filter simply doing less smoothing than you hoped. Wrong answers that look right are the ones that ship.

Your compiler may or may not have told you

GCC and Clang have a warning for this exact expression, and it is on by default under -Wall:

warning: division 'sizeof (const uint16_t *) / sizeof (const uint16_t)'
does not compute the number of array elements [-Wsizeof-pointer-div]

MSVC has no equivalent. Crucible builds C with -Wall -Wextra on GCC-like compilers and /W3 on MSVC, so whether this problem handed you the answer in the build pane or told you nothing at all came down to which compiler was on the machine. If you got the warning: that is the lesson, and it is a better one than the puzzle. Read the build output first, every time.

It is also an argument for building the same source with a second compiler in CI even when you only ship one. They do not warn about the same things.

What else would you flag in this function?

The defect is fixed, but a review would not stop there.

  • The array-shaped parameter. const uint16_t samples[] promises a size relationship the language does not enforce. Writing const uint16_t *samples is the same code and tells the truth, and several coding standards for safety-related software require the pointer spelling for that reason. Keeping the pointer and the count next to each other in the signature is the real contract.
  • ARRAY_LEN is not the villain. The macro is correct and useful — at the point where the array is actually declared. The problem is that it silently accepts a pointer and returns nonsense. A macro that cannot be misused is better: GCC and Clang can be made to reject the pointer case with a __builtin_types_compatible_p guard, and C11's _Static_assert can be pressed into similar service. If your codebase has one ARRAY_LEN, hardening it protects every call site at once.
  • No check on samples. A null pointer with a non-zero count dereferences immediately. Whether that deserves a guard or a documented precondition is a real design decision, but it should be a decision rather than an omission.
  • No upper bound on count. The accumulator is uint32_t and the samples are 12-bit, so it takes about a million samples to overflow. Fine here, and fine only because of facts stated nowhere in the code. One line of comment, or a _Static_assert tying the accumulator width to the maximum block size, turns an accident into an invariant.
  • The truncating divide. Deliberate, and specified — but on a filter it is a downward bias of up to one count on every block, which accumulates if the result feeds anything integrating. Rounding to nearest is (total + count / 2u) / count. Choose on purpose.
  • The cast to uint16_t. Safe, because a mean of 12-bit values is a 12-bit value. Worth a moment's thought all the same: an explicit narrowing cast is the programmer asserting something, and the assertion here rests on the 0…4095 range that the comment mentions and the code does not enforce.

The general lesson

sizeof is answered at compile time, from the type of the expression. It never looks at a value and never follows a pointer. If a length must be known at run time, it has to be carried at run time — which is what the count parameter was already doing.

Any time you see sizeof applied to something that arrived through a parameter, be suspicious. It is right when the thing is a real array in the same scope, and it is wrong — quietly, portably, without a crash — the moment that array has been passed to somebody.
