Decode a Multiplexed CAN Signal Group

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

int32_t can_mux_decode(const uint8_t *frame, int32_t length,
                       int32_t *out_a, int32_t *out_b)
{
    if (length < 1) {
        return -1;
    }
    uint8_t mux = (uint8_t)(frame[0] & 0x0FU);

    if (mux == 0U) {
        if (length < 5) {
            return -1;
        }
        uint32_t raw16   = (uint32_t)frame[1] | ((uint32_t)frame[2] << 8);
        uint32_t word    = (uint32_t)frame[3] | ((uint32_t)frame[4] << 8);
        uint32_t field12 = word & 0x0FFFU;
        int32_t signed12 = (int32_t)field12;
        if ((field12 & 0x0800U) != 0U) {
            signed12 -= 4096;
        }
        *out_a = (int32_t)raw16;
        *out_b = signed12;
        return 0;
    }

    if (mux == 1U) {
        if (length < 3) {
            return -1;
        }
        *out_a = (int32_t)(int8_t)frame[1];
        *out_b = (int32_t)(frame[2] & 0x01U);
        return 1;
    }

    return -1;
}

Why the multiplexor is masked before anything branches on it

frame[0] & 0x0FU happens exactly once, before the first comparison against it. The alternative -- checking frame[0] == 0 and frame[0] == 1 directly -- is indistinguishable from the correct version on every frame whose byte 0 happens to have a zero high nibble, which is most hand-written test data and most frames a lazy fuzzer produces. It fails specifically on the frames a real bus actually sends, where the reserved high nibble is not guaranteed to be zero (it might carry a protocol version, a rolling counter, or genuinely be don't-care noise) -- exactly the case the fixed test with a 0x10 first byte is built to catch.

Why length is checked per branch, not once at the top

A single blanket check like length < 8 at the top of the function would be both too strict and not protective enough: it rejects perfectly valid, shorter mux-1 frames that never needed byte 4 at all, and it says nothing about a mux-0 frame that is 4 bytes long -- one byte short of what mux 0 specifically needs. Checking each branch's own requirement, right before that branch starts indexing further into frame, is what keeps "how many bytes does this reading need" and "how many bytes do we actually have" tied to the same decision.

The 12-bit sign extension, one bit at a time

field12 is computed by masking first (word & 0x0FFFU) -- the top 4 bits of the 16-bit word are padding, not extra magnitude or an extended sign, and including them in either the value or the sign test would make a padding bit that happens to be set silently corrupt the result. The sign test itself (field12 & 0x0800U) looks at bit 11 -- the top bit of the 12-bit field, once it has already been isolated -- not bit 15 of the original word. Subtracting 4096 (1 << 12) from the unsigned 12-bit value when that bit is set is the standard two's -complement widening trick, generalised from the familiar 8-bit "subtract 256" version to whatever field width is actually in play.

Why the 8-bit case gets to skip the manual arithmetic

(int32_t)(int8_t)frame[1] does the same job the 12-bit case does by hand, but for a width the language already has a name for: casting an unsigned byte to int8_t reinterprets its bit pattern as two's complement, and the subsequent cast to int32_t sign-extends it, both defined behaviour in C. There is no width between 8 and 32 bits that C has a built-in signed type for, which is exactly why the 12-bit field above needs the mask-then-subtract approach spelled out instead.

Cost

O(1) -- a fixed, small number of comparisons and byte reads regardless of which branch is taken, with no loop over the frame at all.
