Rotate an Array Left

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

A left rotation by k splits the array into two blocks — A = the first k elements, B = the rest — and produces BA from AB. The blocks swap places and each keeps its internal order.

There is an identity that does exactly that with nothing but reversals:

reverse(reverse(A) · reverse(B)) = B · A

Reversing the concatenation of two reversed blocks un-reverses each block and exchanges their positions in one operation. Three reversals, no extra memory, every element touched at most twice.

The code

static void reverse_range(int *values, int from, int to)
{
    while (from < to) {
        int temp = values[from];
        values[from] = values[to];
        values[to] = temp;
        from++;
        to--;
    }
}

void rotate_left(int *values, int count, int shift)
{
    if (count <= 0) {
        return;
    }

    shift %= count;
    if (shift == 0) {
        return;
    }

    reverse_range(values, 0, shift - 1);
    reverse_range(values, shift, count - 1);
    reverse_range(values, 0, count - 1);
}

reverse_range takes inclusive bounds — hence the two - 1s — and is static because nothing outside your file should be able to call it. Your file and the harness are separate translation units, so a non-static helper puts a symbol into the link that could collide with one of the harness's.

Walking it through

1 2 3 4 5, shift = 2:

StepRangeArray after
start—1 2 | 3 4 5
reverse the first block[0, 1]2 1 | 3 4 5
reverse the second block[2, 4]2 1 | 5 4 3
reverse everything[0, 4]3 4 5 | 1 2

Which is 1 2 3 4 5 rotated left by two. The final reversal is doing double duty: it undoes both block reversals and moves the blocks past each other.

The two guards, in this order

count <= 0 first

shift %= count with count == 0 is integer division by zero — undefined behaviour, and on x86 a SIGFPE that kills the process. Crucible runs each case in its own process and translates the signal, so you would see ERROR against empty array with a message about the arithmetic fault while every other case passed.

This is the whole reason the empty-array case is in the fixed set with a non-zero shift (0\n3\n): a solution that reduces before checking fails here and only here.

shift == 0 second

After the reduction, zero means "no rotation needed" — either the caller asked for none, or they asked for a whole number of complete turns. Without this guard the first call becomes reverse_range(values, 0, -1), whose loop condition 0 < -1 is false, so it happens to do nothing… and then the second and third reversals reverse the whole array twice, which also happens to do nothing. So it would actually still be correct — but only by luck, and the explicit early return says what is meant and skips the work.

Why the modulo is required, not an optimisation

With shift = 7 on a five-element array, the unreduced code would call reverse_range(values, 0, 6) — reading and writing two ints past the end of the allocation. Not a wrong answer: memory corruption. The shift equal to the length fixed case (4\n1 2 3 4\n4\n) sits right on the boundary where an unreduced shift first goes out of bounds.

Cost

O(n) time — the first two reversals together touch every element once, the third touches every element again, so about n swaps in total — and O(1) extra space: one int temporary.

ApproachTimeExtra space
Three reversalsO(n)O(1)
Copy shift elements aside, slide, copy backO(n)O(shift)
Rotate by one, shift timesO(n · shift)O(1)
Juggling / cyclic replacementO(n)O(1)

The juggling algorithm moves each element straight to its final home by following cycles, and needs gcd(count, shift) starting points to cover them all. It is optimal in element moves and considerably harder to get right — the reversal trick gets the same complexity class from three calls to a five-line helper.

Wrong turns worth recognising

Rotating right instead of left. The reversal order is the same; what changes is the split point. Left by k splits at k; right by k splits at count - k. Getting this backwards passes the shift of zero and full turn cases and fails everything else.

Exclusive bounds in the helper. If reverse_range takes [from, to) then the three calls lose their - 1s. Mixing the two conventions — inclusive helper, exclusive call sites — produces an array that is almost right, with one element out of place at a block boundary.

Negative shifts. Not possible here: the problem promises shift >= 0. Worth knowing that C's % truncates towards zero, so -1 % 5 is -1, not 4. Code that accepts negative shifts needs shift = ((shift % count) + count) % count.
