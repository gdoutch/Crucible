Write a Register Field (Read-Modify-Write)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Clear the field's old bits, then OR the new ones in — and mask the new value first, so only its low width bits can ever reach the register:

unsigned int set_field(unsigned int reg, int start, int width,
                       unsigned int value)
{
    unsigned int mask = (width == 32) ? 0xFFFFFFFFu : (1u << width) - 1u;

    reg &= ~(mask << start);
    reg |= (value & mask) << start;
    return reg;
}

Walking it through

set_field(0xB5, 2, 3, 0x6) — write 110 into a 3-bit field at bit 2 of 0xB5 (1011 0101):

The clear step zeroed exactly bits 2-4 and left the rest of 0xB5 untouched — the 1011 in the top nibble and the 01 at the bottom both survive unchanged. The set step then had a clean field to write into.

Trap 1: clearing before setting is not optional

Drop the clear line and keep only reg |= (value & mask) << start, and the function still passes any test where the field starts at zero — OR into zero is indistinguishable from assignment. It fails the moment the field is not already zero and the new value has a 0 where the old value had a 1, because OR can only ever turn bits on.

set_field(0xF0, 4, 4, 0) is the test built around exactly this: field 1111, new value 0000. The clear step gets 0x00; skip it and the answer comes back 0xF0, unchanged, because there was nothing in an OR-only version capable of turning those bits back off.

Trap 2: mask the incoming value, not only the register

reg |= value << start; — dropping just the & mask on value — passes any test where value already fits in width bits, which is most of them if you are testing your own code with values you picked. Nothing in the type system stops a caller handing over something wider.

set_field(0x0F, 8, 4, 0xFF) is built to catch it: the field is 4 bits at position 8, and value is a full byte, 0xFF. Masked, only 0xF goes into the field and the answer is 0x0F0F. Unmasked, all eight bits of 0xFF land at position 8, and bits 12-15 — a field this call was never supposed to touch — pick up ones they should not have, giving 0xFF0F.

The mask formula, once more

Both operations lean on the same mask as Extract a Register Field, for the same reason: (1u << width) - 1u is undefined at width == 32, because the shift amount reaches the type's own bit width. set_field(reg, 0, 32, value) — a whole-register overwrite — is a legitimate call, so the special case has to be there:

unsigned int mask = (width == 32) ? 0xFFFFFFFFu : (1u << width) - 1u;

At width == 32 the clear step becomes reg &= ~0xFFFFFFFFu, which is reg &= 0 — the whole register is discarded — and the set step ORs in value untouched. The two lines still do the right thing; they just needed a mask that was actually 0xFFFFFFFF to do it with.

Cost

Four operators, no loop, regardless of width: O(1) time and space.
