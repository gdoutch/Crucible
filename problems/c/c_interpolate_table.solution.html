Linear Interpolation Over a Calibration Table

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

int interpolate_table(const int *xs, const int *ys, int n, int x)
{
    if (x <= xs[0]) {
        return ys[0];
    }
    if (x >= xs[n - 1]) {
        return ys[n - 1];
    }

    int i = 0;
    while (i + 2 < n && xs[i + 1] < x) {
        i++;
    }

    long long dy = (long long)(ys[i + 1] - ys[i]);
    long long dx = (long long)(xs[i + 1] - xs[i]);
    long long num = dy * (long long)(x - xs[i]);

    return ys[i] + (int)(num / dx);
}

Finding the interval

The loop walks forward while the next breakpoint is still below x, stopping as soon as it is not. Because the two clamp checks above already ruled out x being outside the table entirely, the loop is guaranteed to land on an i with xs[i] <= x <= xs[i + 1]. The i + 2 < n guard stops it walking past the last valid pair when x sits in the final interval.

The overflow, worked through

Take the fixed test built around it: a table from (0, 0) to (100000, 100000), queried at x = 50000. The natural formula's middle term is (100000 - 0) * (50000 - 0) = 5,000,000,000 — already past INT_MAX (2,147,483,647) before the division that would bring it back down to a sensible size ever runs. Computed in a plain int, that multiplication is signed integer overflow: undefined behaviour, not a wraparound you can rely on for a consistent wrong answer, let alone the right one.

Casting each operand to long long before multiplying keeps the whole calculation in 64-bit arithmetic, where 5,000,000,000 is an entirely ordinary number. Dividing it by 100000 gives 50000, which fits back into the int the function returns without difficulty — only the intermediate product was ever the problem.

Why the division truncates

C's / on two integers truncates toward zero. The fixed test built around this uses a table from (0, 0) to (3, 10): at x = 1, the formula computes 10 * 1 / 3, which is 3 — not 3.33 rounded up, down, or to the nearest integer, just C's ordinary truncating division. If a calibration curve wanted rounding it would say so; absent that, truncation is the value the reference solution -- and every test -- expects.

Clamping instead of extrapolating

Returning ys[0] or ys[n - 1] for anything outside the table's x-range is a deliberate choice, not a shortcut: a calibration table only describes the region it was measured over, and drawing the line on past its ends is a guess a real system should not make silently. Clamping says "I do not know, use the nearest thing I do know" instead.

Cost

The interval search is O(n) in the number of breakpoints — fine for the small calibration tables this kind of code actually works with. A table large enough for that to matter would use a binary search instead, the same trade Binary Search makes explicit; nothing here changes the interpolation formula itself, only how fast the right interval is found.
