Linear Interpolation Over a Calibration Table

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

#include <stdint.h>

int32_t interpolate_table(const int32_t *xs, const int32_t *ys, int32_t n, int32_t x)
{
    int32_t result;

    if (x <= xs[0]) {
        result = ys[0];
    } else if (x >= xs[n - 1]) {
        result = ys[n - 1];
    } else {
        int32_t i = 0;

        while ((i + 2 < n) && (xs[i + 1] < x)) {
            i++;
        }

        {
            const int64_t dy = (int64_t)(ys[i + 1] - ys[i]);
            const int64_t dx = (int64_t)(xs[i + 1] - xs[i]);
            const int64_t num = dy * (int64_t)(x - xs[i]);

            result = ys[i] + (int32_t)(num / dx);
        }
    }

    return result;
}

Why it is shaped like this, not like the plain-C version

The interpolation logic underneath is identical to the ordinary version of this problem -- clamp, clamp, scan for the interval, widen, divide. What is different is the shape MISRA C:2012 asks for:

  • Directive 4.6 (use the sized types) rules out int and long long. int32_t carries the table's values and index; int64_t is the type the multiply gets widened into. Both need <stdint.h>.
  • Rule 15.5 (a single point of exit) rules out the two early returns the plain version uses for clamping. Here, all three cases assign to result and the function returns it once, at the end. The clamp/clamp/interpolate structure becomes an if / else if / else instead of a guard clause followed by the main body.
  • Rule 10.x (no implicit essential-type conversions) means every crossing between int32_t and int64_t -- widening into dy/dx/num, then narrowing the quotient back down for result -- carries an explicit cast rather than relying on the compiler to insert one.

Finding the interval

The loop walks forward while the next breakpoint is still below x, stopping as soon as it is not. Because the two clamp checks above already ruled out x being outside the table entirely, the loop is guaranteed to land on an i with xs[i] <= x <= xs[i + 1]. The i + 2 < n guard stops it walking past the last valid pair when x sits in the final interval. It lives inside the else branch rather than before the clamp checks, because Rule 15.5's single-exit shape means the clamp cases and the interpolation case are now mutually exclusive branches of one if chain rather than a sequence of guard clauses.

The overflow, worked through

Take the fixed test built around it: a table from (0, 0) to (100000, 100000), queried at x = 50000. The natural formula's middle term is (100000 - 0) * (50000 - 0) = 5,000,000,000 — already past INT32_MAX (2,147,483,647) before the division that would bring it back down to a sensible size ever runs. Computed in a plain int32_t, that multiplication is signed integer overflow: undefined behaviour, not a wraparound you can rely on for a consistent wrong answer, let alone the right one.

Casting each operand to int64_t before multiplying keeps the whole calculation in 64-bit arithmetic, where 5,000,000,000 is an entirely ordinary number. Dividing it by 100000 gives 50000, which fits back into the int32_t the function returns without difficulty — only the intermediate product was ever the problem, and Rule 10.x is exactly the rule that forces the cast to be explicit rather than implicit at every one of these crossings.

Why the division truncates

C's / on two integers truncates toward zero. The fixed test built around this uses a table from (0, 0) to (3, 10): at x = 1, the formula computes 10 * 1 / 3, which is 3 — not 3.33 rounded up, down, or to the nearest integer, just C's ordinary truncating division. If a calibration curve wanted rounding it would say so; absent that, truncation is the value the reference solution -- and every test -- expects.

Clamping instead of extrapolating

Returning ys[0] or ys[n - 1] for anything outside the table's x-range is a deliberate choice, not a shortcut: a calibration table only describes the region it was measured over, and drawing the line on past its ends is a guess a real system should not make silently. Clamping says "I do not know, use the nearest thing I do know" instead.

Cost

The interval search is O(n) in the number of breakpoints — fine for the small calibration tables this kind of code actually works with. A table large enough for that to matter would use a binary search instead, the same trade Binary Search makes explicit; nothing here changes the interpolation formula itself, only how fast the right interval is found.
