Multiply Two Q15 Fixed-Point Numbers

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

int q15_multiply(int a, int b)
{
    long long product = (long long)a * (long long)b;
    long long rounded = (product + (1LL << 14)) >> 15;

    if (rounded > 32767) {
        return 32767;
    }
    if (rounded < -32768) {
        return -32768;
    }
    return (int)rounded;
}

Why the shift is 15, and why it happens after the multiply

A Q15 value raw represents raw / 32768, and 32768 is 2^15. Multiplying two Q15 raw integers multiplies the real numbers they represent, but it also multiplies the two 2^-15 scale factors together into one 2^-30 scale — the product is "too small" by a factor of 2^15 relative to a single Q15 value. Shifting right by 15 divides by exactly that factor, landing back on a 2^-15 scale: an ordinary Q15 number again.

This only works if the shift happens on the full-width product. Pre-shifting either a or b before multiplying — a tempting way to "keep the numbers small" — throws away the low bits of that operand permanently; the final answer is missing precision no amount of care in the rest of the function can put back.

Rounding, worked through

3 * 5 = 15, and 15 as a Q15-scaled product represents 15 / 32768, a number small enough that plain truncation rounds it to 0 either way here — but the mechanism matters for larger products where truncating and rounding disagree. Adding 1 << 14 before shifting is adding exactly half of 1 << 15, the amount the shift is about to discard: a value sitting past the halfway point of what gets thrown away pushes the sum over the next shift boundary, rounding up; short of halfway, it does not. This is the standard round-to-nearest trick for a right shift, and it is the difference between a filter whose answers are quietly biased low by up to half a unit and one that is not.

The saturating corner, worked through

q15_multiply(-32768, -32768): the true product, -32768 * -32768, is 1,073,741,824. Adding the rounding term and shifting right by 15 gives exactly 32768 — representing 1.0, which the mathematics says is correct (-1.0 * -1.0 = 1.0) and Q15 simply cannot hold, because its largest representable value is 32767 / 32768, a little under 1.0. Returned as a plain 16-bit signed value with no clamp, 32768 would wrap to -32768 — the smallest representable value, exactly backwards from the true answer's sign. Clamping to 32767 instead is saturation: the answer is wrong by the smallest amount Q15 can be wrong by, in the correct direction, rather than wrong by the largest amount possible in the wrong one.

The neighbouring fixed test, 32767 * 32767, is there to show saturation firing only where it needs to: (32767/32768)^2 is still just under 1.0, so that product rounds to 32766 and returns unclamped. Saturating logic that fires too eagerly is as wrong as logic that never fires at all.

Cost

One multiply, one shift, two comparisons: O(1) time and space. In production DSP code this is usually a single saturating multiply instruction (many DSP-oriented cores have one built in); the point of writing it out in plain C is seeing exactly what that instruction is doing on your behalf.
