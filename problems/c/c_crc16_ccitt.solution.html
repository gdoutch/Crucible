Compute a CRC-16/CCITT-FALSE Checksum

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

uint16_t crc16_ccitt_false(const uint8_t *data, size_t length)
{
    uint16_t crc = 0xFFFFU;
    for (size_t i = 0U; i < length; i++) {
        crc = (uint16_t)(crc ^ (uint16_t)((uint16_t)data[i] << 8));
        for (int bit = 0; bit < 8; bit++) {
            if ((crc & 0x8000U) != 0U) {
                crc = (uint16_t)((uint16_t)(crc << 1) ^ 0x1021U);
            } else {
                crc = (uint16_t)(crc << 1);
            }
        }
    }
    return crc;
}

Why 0xFFFF, and why it matters more than it looks like it should

A CRC's initial value only ever does one job: it is what the register holds before any data has influenced it. For most inputs that fact is invisible, because a handful of XOR-and-shift rounds against real data sweeps the starting value's contribution away long before the loop ends. It stops being invisible at the one input where nothing happens at all -- an empty buffer. crc16_ccitt_false(data, 0) never enters the loop, so whatever the register started at is exactly what comes back. CCITT-FALSE returns 0xFFFF there; an implementation that initialised the register to 0 -- correctly implementing CRC-16/XMODEM instead -- returns 0x0000. Both are real, standard CRC-16 variants. Only one of them is the one this problem asks for, and the empty-input case is what tells them apart without needing nine bytes of test data to do it.

Why the byte goes into the top of the register

crc ^= (uint16_t)data[i] << 8 places the incoming byte in bits 8-15 of the 16-bit register, not bits 0-7. That is what makes the following eight left-shifts process the byte's bits from the most significant one down to the least significant one: each shift moves the current top bit (originally the byte's own top bit, first time through) out where it decides whether 0x1021 gets folded in, then promotes the next bit up to take its place. Feeding the byte in at the bottom instead, or shifting right instead of left, computes a real CRC-16 -- just a reflected one, matching a different named variant (MODBUS/ARC-family) that starts from a different init value and reads the final register differently besides.

The promotion MISRA would flag

data[i] is uint8_t. In data[i] << 8 it is promoted to int before the shift happens at all -- ordinary C integer promotion, invisible at the value level here because the result (at most 0xFF00) fits in a 32-bit int with room to spare. The explicit casts back to uint16_t at each step are not decoration: they are what make the truncation back down to a 16-bit register a stated fact about the code rather than something the reader has to reconstruct from the types of two operands. This is exactly the shape MISRA's essential type model exists to make a reviewer stop and check on every occurrence, rather than trust by pattern-matching against the times it was harmless.

Checking it against the standard

The CRC catalogue's check value for this variant is crc16_ccitt_false("123456789") = 0x29B1. It is a fixed test in this problem's suite for the same reason it is the reference value the whole CRC community checks new implementations against: a disagreement here means the bit order or the initial value is wrong, not that some edge case was missed.

Cost

O(length) — eight shift-and-maybe-XOR rounds per input byte, no lookup table, no allocation. A table-driven implementation trades this loop for one XOR and one table read per byte, at the cost of a 256-entry table computed from the same polynomial; it produces identical output, byte for byte, to the bit-by-bit form above.
