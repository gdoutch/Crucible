GPIO Set/Clear/Toggle (Read-Modify-Write)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

enum gpio_op { GPIO_SET, GPIO_CLEAR, GPIO_TOGGLE };

unsigned int gpio_apply(unsigned int reg, enum gpio_op op, unsigned int mask)
{
    switch (op) {
        case GPIO_SET:
            return reg | mask;
        case GPIO_CLEAR:
            return reg & ~mask;
        case GPIO_TOGGLE:
            return reg ^ mask;
        default:
            return reg;
    }
}

Three operations, three operators, no state of your own to manage — the harness keeps the running register value and feeds it back in as reg on the next call.

Why each operator is the right one

OperationOn a masked bitOn every other bit
reg | maskforced to 1unchanged (OR with 0 is a no-op)
reg & ~maskforced to 0unchanged (AND with 1 is a no-op)
reg ^ maskflippedunchanged (XOR with 0 is a no-op)

All three share the same shape: an operator that is a no-op against 0, applied everywhere the mask is 0, so "every other bit" is untouched by construction rather than by carefully avoiding it.

The trap: AND with the mask, not its complement

reg & mask — leaving out the ~ — looks plausible if you are thinking "AND selects the bits I care about". It does, but that is backwards for a clear operation: it keeps only the pins that are both in the mask and currently high, and drops every pin outside the mask down to 0 as a side effect, which is the one thing a clear operation must never do to an unrelated pin.

The fixed test that catches it runs SET 0xF then CLR 0x5 against a register that starts at 0. After the SET, reg is 0xF (1111). The correct clear, 0xF & ~0x5, drops bits 0 and 2 and keeps bits 1 and 3: 0xA. The backwards version, 0xF & 0x5, keeps only bits 0 and 2: 0x5 — which also happens to look like a plausible answer on its own, so it is the printed trace as a whole, not any single number, that gives the mistake away.

Walking the trace

StepOperationRegister
start—00000000
1SET 0000000F0000000F
2CLR 000000050000000A
3TOG 0000000300000009

Step 3 flips bits 0 and 1 of 0xA (1010): bit 0 goes 0 → 1, bit 1 goes 1 → 0, giving 1001 — 0x9.

Beyond the exercise: why real GPIO ports avoid this pattern

Every operation here is a read-modify-write: the CPU reads the register, computes the new value, and writes it back — three separate steps, not one atomic one. If an interrupt handler touches the same register between the read and the write, its change is silently overwritten when the write finally happens, because neither side knew about the other's in-flight update.

This is exactly the problem many microcontrollers design around. STM32 parts, for instance, give a GPIO port a second register, BSRR, that is write-only: writing a 1 to bit n sets pin n, writing a 1 to bit n+16 clears it, and the write itself is the only step — there is no read to race against. The read-modify-write dance in this exercise is the general-purpose fallback for registers that do not offer that shortcut, which is most of them; it is worth recognising when you are looking at one that does.

Cost

One operator per call, O(1) time and space, regardless of how many operations the trace runs.
