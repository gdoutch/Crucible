Decimal to Roman Numeral String

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Treat the six subtractive pairs as values in their own right rather than as exceptions. Then the numeral system has thirteen building blocks, not seven, and converting a number is a plain greedy walk: take the largest block that fits, append it, subtract, repeat.

Everything awkward about Roman numerals — IV instead of IIII, CM instead of DCCCC, the three-repeat limit — disappears into that one table. There is no fix-up pass because there is nothing left to fix.

The code

#include <stddef.h>

/* Every value that can start a numeral, largest first -- the six subtractive
 * pairs sitting in the order their values demand.
 */
static const struct {
    int value;
    const char *symbol;
} ROMAN[] = {
    { 1000, "M"  }, { 900, "CM" }, { 500, "D" }, { 400, "CD" },
    {  100, "C"  }, {  90, "XC" }, {  50, "L" }, {  40, "XL" },
    {   10, "X"  }, {   9, "IX" }, {   5, "V" }, {   4, "IV" },
    {    1, "I"  },
};

void to_roman(int value, char *out)
{
    size_t count = sizeof ROMAN / sizeof ROMAN[0];

    for (size_t i = 0; i < count; i++) {
        while (value >= ROMAN[i].value) {
            for (const char *symbol = ROMAN[i].symbol; *symbol != '\0'; symbol++) {
                *out++ = *symbol;
            }
            value -= ROMAN[i].value;
        }
    }

    *out = '\0';
}

Why greedy is correct here

Greedy algorithms are usually where you have to be careful — the greedy choice is often not the optimal one. (Making change with coins of 1, 3 and 4 is the standard counter-example: greedy gives 6 = 4 + 1 + 1, three coins, when 3 + 3 is two.)

It works here because the thirteen values are not an arbitrary set. Between each plain symbol and the next one up sits the subtractive pair that covers the gap, and the result is that at most three of any row can ever be needed. There is no configuration where declining a large block and taking several smaller ones does better — the block that would let you do that is already in the table.

Which is the same statement as the historical rule "no symbol four times in a row". The rule and the table are two descriptions of one fact, and encoding the table means the rule needs no enforcement.

Descending order is load-bearing. Put 900 CM after 500 D and 900 matches the D row first, producing DCCCC. Greedy is only greedy against a list that is actually sorted, and nothing in the code checks that it is — it is a property of how the table was typed.

Walking a case

1994, the a year test:

1000 MyesM994
1000 Mno—994
900 CMyesCM94
500 D, 400 CD, 100 Cno—94

50 L … 5 Vno—4
4 IVyesIV0

MCMXCIV. Three of the six subtractive pairs in one number, each produced by an ordinary row of the table.

Note that once the value reaches zero the remaining rows all fail their while immediately, so the loop runs to the end doing nothing. Adding if (value == 0) break; would save a handful of comparisons and is not worth the line.

The string building

*out++ = *symbol

Post-increment on the destination: write the byte at out, then advance. out is a parameter — your own copy of the caller's pointer — so moving it is free and invisible to them. There is no separate index and no need to know how much has been written so far.

The inner for walks the symbol to its own terminator, which handles one-character and two-character symbols with the same code. Writing *out++ = ROMAN[i].symbol[0]; if (ROMAN[i].symbol[1]) … also works and puts the length of the symbols into the algorithm, where it does not belong.

The terminator

*out = '\0'; — after the loops, once, and not post-incremented. This is the whole reason the function's contract is "a null-terminated string" rather than "some characters".

By that point out points at the first unwritten byte, which is exactly where the terminator goes. It is the only write in the function that does not advance the pointer, because nothing follows it.

The harness prefills its buffer with '?' and checks for a '\0' within sixteen bytes, so a missing terminator is reported as UNTERMINATED instead of printing sixty-four question marks and whatever came after. That check lives in the harness for the same reason the safety monitor does in Level Crossing Interlock — the thing being tested does not get to decide whether it passed.

Why sixteen bytes

The longest numeral in 1–3999 is 3888 = MMMDCCCLXXXVIII, fifteen characters — and it is the only value in range that long. Fifteen plus a terminator is sixteen, so the buffer is not a round number chosen for comfort; it is the exact bound. The longest numeral in range fixed case is there to sit on it.

Cost

O(1), and worth stating precisely: the table has thirteen rows, the inner loop runs at most three times per row, and each iteration writes at most two characters. So the whole function is bounded by a constant regardless of the input — there is no n here, only a value with a fixed maximum.

The table costs about 200 bytes of read-only data.

Other shapes of answer

Per-digit lookup. Four small tables — thousands, hundreds, tens, units — indexed by the decimal digit, then concatenated: HUNDREDS[9] is "CM". It is arguably clearer, it is a straight O(1) with no loops at all, and it costs four tables of ten strings instead of one of thirteen rows. Equally good; pick whichever you would rather explain.

strcat in the loop. Works, and re-walks the whole string from the start on every append to find its end. Quadratic in the output length — irrelevant at fifteen characters, and the habit that makes string building slow everywhere else. It also requires out[0] to be a terminator before the first call, which the caller has not promised.

Wrong turns worth recognising

Emitting the plain symbols and patching afterwards. The approach the table exists to avoid. It needs six rewrite rules applied in the right order, in place, on a string you are also still appending to.

MMMIM for 3999. The intuition that any smaller symbol may precede any larger one. It may not — the six pairs are the entire set of legal subtractions, so 999 is 900 + 90 + 9 (CMXCIX) and never 1000 − 1. A table containing only the six cannot express the mistake, which is the point.

if instead of while on the inner step. Passes 1, 4, 1994 and every value whose digits are all below 2 or exactly 4/9 — and fails on 3, which needs III. The three in a row fixed case exists for it.

Losing the start of the buffer. Advancing out is right; advancing it and then needing the beginning again is not. This function never needs to look back, which is what makes the walking pointer safe. If yours does, that is a sign a fix-up pass has crept in.
