Reverse a Linked List

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Walk the list once, turning each next pointer to face backwards as you pass it. The list is conceptually split in two at all times: a reversed prefix behind you, headed by previous, and an untouched suffix ahead, headed by head. Each iteration moves one node from the front of the suffix to the front of the prefix.

Invariant: previous points at the reversed list of everything already visited; head points at the original list of everything not yet visited. When the suffix runs out, previous is the answer.

The code

#include <stddef.h>

struct node {
    int value;
    struct node *next;
};

struct node *reverse_list(struct node *head)
{
    struct node *previous = NULL;

    while (head != NULL) {
        struct node *next = head->next;
        head->next = previous;
        previous = head;
        head = next;
    }

    return previous;
}

The four statements, and why the order is forced

#StatementWhy it must be here
1next = head->next The only surviving reference to the rest of the list. Line 2 destroys the original.
2head->next = previous The actual reversal — one pointer turned round. Must come after 1 and before 3, since 3 overwrites previous.
3previous = head The current node joins the reversed prefix. Must come after 2.
4head = next Step into the suffix, using the pointer saved in 1.

Swap 1 and 2 and the list is gone. head->next now points backwards, so next receives a node you have already processed; the loop turns round and walks the prefix, and every node from the third onwards becomes unreachable. Depending on where the pointers land you get truncated output, a cycle that never terminates, or a segmentation fault — three different symptoms of one reordering.

Watching it run

The list 1 → 2 → 3 → NULL:

IterationpreviousheadLinks after the body
startNULL11→2→3→NULL
112NULL←1   2→3→NULL
223NULL←1←2   3→NULL
33NULLNULL←1←2←3

The loop exits with head == NULL and previous on node 3 — the original tail, now the head. Reading forward from it gives 3 → 2 → 1 → NULL.

Why previous starts at NULL

Two jobs from one initialisation.

First, it terminates the reversed list. On the first iteration the original head's next is set to previous — so the node that used to be first becomes the one whose next is null, which is precisely what being last means. Get this wrong and the final node points at itself or at rubbish, and anything walking the list runs forever.

Second, it is the answer for the empty list. head is NULL, the loop condition fails immediately, and previous is returned unchanged. No guard needed.

The other two fixed cases

CaseWhat happens
one node One iteration. next is NULL, head->next is set to NULL (it already was), previous becomes the node, head becomes NULL. The node comes back unchanged, which is correct — and it exercises the assignment of previous into next without any real relinking.
two nodes The smallest list where a link genuinely changes direction, and the smallest one that catches a solution which returns head instead of previous.

Why not copy the values?

/* the answer that passes and misses the point */
int buffer[1000];
int n = 0;
for (struct node *p = head; p; p = p->next) { buffer[n++] = p->value; }
for (struct node *p = head; p; p = p->next) { p->value = buffer[--n]; }
return head;

Same printed output, and wrong in every way that matters:

  • It needs O(n) memory, and that fixed buffer is a bug waiting for a longer list.
  • It only works because the payload is a copyable int. Real nodes carry payloads that are large, or owned by someone else, or referred to by other pointers — and moving values between nodes breaks all of that.
  • It does not reverse the list. It reverses the data, and leaves the structure exactly as it was.

The recursive version

struct node *reverse_list(struct node *head)
{
    if (head == NULL || head->next == NULL) {
        return head;
    }
    struct node *new_head = reverse_list(head->next);
    head->next->next = head;     /* the node behind me now points at me */
    head->next = NULL;           /* and I might be the tail */
    return new_head;
}

Elegant, and it needs both base cases: NULL for the empty list and head->next == NULL so the recursion has something to return. The line head->next->next = head is worth staring at — at that moment head->next is the node that was after us and is now, in the reversed list, the node before us.

The cost is O(n) stack frames, so a long list overflows the stack. The iterative version is O(1) space, which is why it is the one to write.

Cost

O(n) time — every node visited exactly once — and O(1) space: three pointers, no allocation.

Wrong turns worth recognising

Returning head. It is NULL when the loop ends. The harness prints nothing and every non-empty case fails identically — which at least makes it easy to spot.

Allocating new nodes. The caller owns this memory and will free the list you return. A fresh list leaks the original; freeing the original hands back pointers into released memory.

Declaring struct node differently from the harness. Your file and the harness are separate translation units that agree on the layout only because both declarations match. Reorder the members and the two disagree about where next lives — it compiles cleanly, links cleanly, and reads garbage at runtime. Copy the struct exactly as the problem statement gives it.
