Validate an Untrusted Command Frame

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Every byte read is preceded by the check that makes it safe. Unknown means rejected. Failure changes nothing.

int validate_command(const uint8_t *frame, size_t len, uint32_t *last_counter)
{
    if (len < 6) {
        return -1;
    }
    size_t paylen = frame[1];
    if (len != 2 + paylen + 4) {
        return -1;
    }

    switch (frame[0]) {
    case 0x01: {
        if (paylen != 2) {
            return -3;
        }
        int32_t value = (int16_t)(uint16_t)(((uint16_t)frame[2] << 8) | frame[3]);
        if (value < -7000 || value > 7000) {
            return -4;
        }
        break;
    }
    case 0x02:
        if (paylen != 1) {
            return -3;
        }
        if (frame[2] > 3) {
            return -4;
        }
        break;
    case 0x03: {
        if (paylen != 2) {
            return -3;
        }
        uint32_t value = ((uint32_t)frame[2] << 8) | frame[3];
        if (value > 10000u) {
            return -4;
        }
        break;
    }
    default:
        return -2;
    }

    const uint8_t *c = &frame[2 + paylen];
    uint32_t counter = ((uint32_t)c[0] << 24) | ((uint32_t)c[1] << 16)
                     | ((uint32_t)c[2] << 8) | (uint32_t)c[3];
    if (counter <= *last_counter) {
        return -5;
    }
    *last_counter = counter;
    return 0;
}

Every read, and what protects it

ReadMade safe by
frame[1]len >= 6
frame[2], frame[3]len == 2 + paylen + 4, and paylen checked per type
The four counter bytesThe same length equation, with paylen now known to be right

The check len != 2 + paylen + 4 cannot overflow, because paylen is at most 255. If the length field were 16 or 32 bits wide, you would write it as paylen != len - 6 after the len >= 6 check, which cannot overflow either.

The traps

Updating the counter too early. If a frame is range-checked after the counter is stored, one out-of-range frame with counter 100 locks out every legitimate frame below it. An attacker needs no key to do this. The test "a rejected frame does not move the counter" exists for this.

The signed 16-bit conversion. frame[2] << 8 | frame[3] is an int between 0 and 65535. It is only negative after the cast to int16_t. Skip the cast and 0xFFFF is 65535, which fails the range check, when it should be -1, which passes.

Allow-list, not block-list

The default case rejects. A type nobody has thought about is refused rather than passed through. A block-list has to anticipate every bad input. An allow-list only has to describe the good ones.

Where this sits in a real design

This is the semantic layer of a firewall. Before it come framing and authentication, which prove who sent the frame. This layer decides whether the content is something the device is willing to do, with this value, now. Note that the counter check only means something once the frame has been authenticated. An unauthenticated counter proves nothing.
