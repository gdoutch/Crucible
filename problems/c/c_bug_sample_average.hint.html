Fix the Sample Averager

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Not to write an averaging filter — you could do that in your sleep, and the one in the editor is nearly right already. You are being asked to find out why a function that looks correct returns an answer that is much too low, and to fix it without rewriting it.

This is the everyday version of the skill: the code compiles, it has a test, the test passes, and the product is wrong.

Start by measuring the error, not by rereading the code

Rereading code you have already read tends to produce the same understanding you had the first time. The failing cases hand you actual numbers, so use them:

Samples inTrue meanWhat it reports
8, rising 100…800450250
3, all about 10001001750
1, reading 512512128

Three questions worth putting to that table before you go any further:

  • 250 is the mean of which samples, exactly? Not a random subset — write out the front of the block and try the obvious groupings.
  • The block of one sample is the loud one. 512 becomes 128, which is 512 divided by four. Where would a four come from, when the only number in that test case is a one?
  • 1001 becoming 750 says the same thing from the other side. What would have to be sitting after the end of a three-sample block for the answer to land there?

Where to look

The loop is correct. The accumulator is wide enough. The cast on the way out is fine for 12-bit data. The zero guard is right.

That leaves one line, and it is the line that decides how many samples get averaged. Everything the function does after that point is faithfully carrying out an instruction it was given wrongly.

The suspicious thing about that line is that it never mentions count. The caller went to the trouble of telling this function how many samples there are. Ask yourself what the function is using instead, and whether that thing can possibly know.

The idea you may be missing

A parameter written with square brackets —

uint16_t average_samples(const uint16_t samples[], size_t count)

— looks like an array, and reads like an array, and is indexed like an array. But C has a rule about what a parameter of array type actually becomes, and it is not the rule most people carry around in their head. Look it up, or work it out from the numbers above; both routes end in the same place.

The clue in the bug report is doing real work, too: "worked fine in the previous release, when the sample buffer lived inside the filter module." The same expression, on the same-looking thing, gave a different answer before the refactor. That is not superstition — it is the rule.

Still stuck? A bigger nudge

Stop reasoning and print it. Add this as the first statement in the function:

printf("n = %zu, count = %zu\n", n, count);

(You will need #include <stdio.h> at the top, and n has to be computed before you print it. Take the line out again before you submit — the tests compare stdout exactly.)

Run it against several of the failing cases. count changes; n does not. It is the same value every single time, on data of every length, which is only possible if it was never derived from the data at all.

Then print sizeof(samples) on its own and ask what type has that size on your machine.

When you think you have it

  • The fix is one line. If you are deleting the macro, rewriting the loop or changing the signature, you have gone further than the defect goes.
  • Check four samples, truncated still passes. It passed before your change as well — understanding why is most of the lesson here.
  • Check no samples still returns 0 and does not divide by zero.
