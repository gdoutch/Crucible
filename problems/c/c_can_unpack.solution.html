Unpack a CAN Signal (Intel Byte Order)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

long long can_unpack(const unsigned char payload[8], int start_bit, int length,
                     int is_signed, int scale, int offset)
{
    unsigned long long raw64 = 0;
    for (int i = 0; i < 8; i++) {
        raw64 |= (unsigned long long)payload[i] << (8 * i);
    }

    unsigned long long mask = (1ULL << length) - 1ULL;
    unsigned long long field = (raw64 >> start_bit) & mask;

    long long raw;
    if (is_signed) {
        unsigned long long sign_bit = 1ULL << (length - 1);
        if (field & sign_bit) {
            field -= (sign_bit << 1);
        }
        raw = (long long)field;
    } else {
        raw = (long long)field;
    }

    return raw * (long long)scale + (long long)offset;
}

Three stages: assemble the bytes into one 64-bit value, extract and sign-extend a field from it, then apply the engineering-unit conversion. The middle stage is Extract a Signed Sensor Reading unchanged in every detail except the width.

Byte order, worked through

raw64 |= (unsigned long long)payload[i] << (8 * i) places payload[0] at bit position 0 — the least significant byte of the assembled value — and each following byte 8 bits higher. That is what "Intel byte order" means for a multi-byte CAN signal: the first byte in the payload is the low byte, the same convention x86 uses for an integer in memory.

Take the fixed test with payload bytes 0x34, 0x12 and a 16-bit unsigned field starting at bit 0. Assembled correctly, raw64's low 16 bits are 0x1234 — byte 0 (0x34) contributes the low byte, byte 1 (0x12) the high byte, giving 4660. Assemble the bytes in the other order — byte 0 shifted to the top — and the same two bytes read back as 0x3412, 13330: every bit was taken from the right place in the array, and the answer is still wrong, because the array itself was walked in the wrong direction.

Extraction and sign extension, unchanged

Once raw64 exists, everything else is exactly the pattern from the two earlier register problems, just at 64 bits: shift the field down, mask it to length bits, and if the top bit of the field (not of raw64) is set, subtract 2^length — computed as sign_bit << 1, the same trick as before. Nothing about working in 64 bits changes any of that reasoning; the field itself is never wider than 32 bits here, so none of it comes anywhere near needing the width == 32 special case the register problems needed for their own masks.

Scale and offset, and why the return type is long long

raw * scale can overflow a 32-bit int on its own, independent of anything to do with bit widths. The fixed test with a full 32-bit raw value (0xFFFFFFFF, which fits comfortably in an unsigned int) and a scale of 1000 produces 4,294,967,295,000 — nowhere near representable in 32 bits, comfortably representable in the 64-bit return type the function already has. Casting scale and offset to long long before the arithmetic is what keeps the whole expression in that wider type throughout, rather than computing part of it in int and only widening at the very end, by which point the overflow has already happened.

What this leaves out

Real DBC files also support **Motorola (big-endian)** byte order, where start_bit is numbered from the most significant bit of the most significant byte and counts in a zig-zag that very few people get right from memory on the first try. This exercise only covers Intel byte order deliberately — it is the more common of the two in practice, and the mechanics above (assemble, extract, sign-extend, scale) are identical either way; only the bit-numbering convention for start_bit changes.

Cost

A fixed 8-iteration loop to assemble the bytes, then a handful of bitwise operators: O(1) time and space, independent of length.
