Classify a Diagnostic Fault Code (MISRA Switch Rules)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

#include <stdint.h>

int32_t classify_fault(int32_t code)
{
    int32_t severity;

    switch (code) {
        case 0:
            severity = 0;
            break;
        case 101:
        case 102:
        case 103:
            severity = 1;
            break;
        case 201:
        case 202:
            severity = 2;
            break;
        case 301:
            severity = 3;
            break;
        default:
            severity = -1;
            break;
    }

    return severity;
}

The table, as a switch

CodeMeaningSeverity
0no fault0
101coolant temp sensor1
102MAF sensor1
103O2 sensor1
201injector circuit2
202fuel pump circuit2
301brake actuator fault3
anything elseundocumented-1

case 101: case 102: case 103: stacks three labels with no statement between them, so all three run the same severity = 1; and share its break. That is the one kind of "fallthrough" Rule 16.3 permits: there is nothing to fall through past, only a shared destination for several distinct values. A clause that runs a statement and then omits its own break — letting execution continue into the next clause's code — is the kind the rule forbids.

Rule by rule

  • Rule 16.4 (every switch has a default) is what makes -1 the answer for everything not in the table, including values nobody thought to write a test for. Without it, a code the switch does not recognise falls through the whole statement having assigned severity nothing, and the final return severity; reads an indeterminate value — not a wrong answer so much as no defined answer at all.
  • Rule 16.3 (every clause ends with an unconditional break) is what stops a typo turning case 201: into a clause that silently also runs case 202:'s code. Every clause above states its own break, even the stacked ones, even default.
  • Rule 15.5 (advisory: a single point of exit) is why the switch assigns to severity instead of returning directly from each clause. One return, after the switch, reading a variable every reachable path has by then written.

Why a range check is the wrong shape

The documented codes cluster — three sensor codes in the 100s, two actuator codes in the 200s — and it is tempting to collapse that into range comparisons: if (code >= 100 && code < 200) severity = 1; and so on. It reads shorter, and it is wrong: 150 is inside 100-199 but was never documented, and the range check would classify it as a warning anyway. One of the fixed tests queries 150 for exactly this reason.

A switch on the exact documented values does not have this failure mode, because it cannot silently accept a code nobody enumerated — anything not spelled out as a case falls all the way through to default. The discipline the MISRA rules impose here is not incidental to avoiding the bug, it is what avoids it.

What the fixed tests are checking

Every documented code returns its documented severity, in table order. 150 — between the sensor and actuator ranges but undocumented — comes back -1, catching a range-based implementation. -42 and 302 confirm negative codes and codes past the last documented one both land in default without special handling. A run of several codes in one input confirms each query is classified independently of the ones before it.
