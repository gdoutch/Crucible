Decode a Modbus RTU Read Response

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Six checks in a fixed order, then one conversion. Each check makes the next one safe.

After this check passesYou may now read
1. len >= 5The last two bytes (the CRC) and frame[0], frame[1]
2. CRC goodEverything else. The frame is intact
6. len == 9frame[3] to frame[6]

CRC-16/MODBUS

static uint16_t crc16_modbus(const uint8_t *data, size_t len)
{
    uint16_t crc = 0xFFFFu;
    for (size_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (int bit = 0; bit < 8; bit++) {
            if ((crc & 1u) != 0u) {
                crc = (uint16_t)((crc >> 1) ^ 0xA001u);
            } else {
                crc = (uint16_t)(crc >> 1);
            }
        }
    }
    return crc;
}

This is the reflected form: bits are processed least significant first, so the polynomial 0x8005 appears as 0xA001. Initial value 0xFFFF, no final XOR. Check value: the CRC of the ASCII bytes "123456789" is 0x4B37.

The function

int modbus_read_response(const uint8_t *frame, size_t len,
                         uint8_t expected_addr, int32_t *value_out)
{
    if (len < 5) {
        return -1;
    }
    uint16_t received = (uint16_t)(frame[len - 2] | (frame[len - 1] << 8));
    if (crc16_modbus(frame, len - 2) != received) {
        return -2;
    }
    if (frame[0] != expected_addr) {
        return -3;
    }
    if ((frame[1] & 0x80u) != 0u) {
        return -4;
    }
    if (frame[1] != 0x03u) {
        return -5;
    }
    if (len != 9 || frame[2] != 4) {
        return -6;
    }
    uint32_t raw = ((uint32_t)frame[3] << 24) | ((uint32_t)frame[4] << 16)
                 | ((uint32_t)frame[5] << 8) | (uint32_t)frame[6];
    *value_out = (int32_t)raw;
    return 0;
}

The CRC is sent low byte first, unlike every other 16-bit value in Modbus. Getting this backwards makes every good frame fail, so it is found quickly. The quieter mistakes are reading frame[3] before checking the length, and putting the address check before the CRC check.

Why the CRC comes before the address

A corrupted frame has no trustworthy address. If you compared the address first, a noisy frame would be reported as "wrong device", which sends the debugging in the wrong direction. Integrity first, then meaning.

Word order is configuration in the real world

Here the high word comes first. Meters differ, and some send the low word first. A real driver makes the word order a setting, and the commissioning step confirms it against a known load.

Sign

The raw 0xFFFFFFFB is -5 when read as int32_t. Build it in uint32_t so every shift is well defined, then convert once at the end.
