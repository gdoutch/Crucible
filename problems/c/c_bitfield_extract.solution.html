Extract a Register Field

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Shift the field down to bit 0, then mask off anything else that came down with it. Two operators, in that order:

unsigned int extract_field(unsigned int reg, int start, int width)
{
    unsigned int mask = (width == 32) ? 0xFFFFFFFFu : (1u << width) - 1u;

    return (reg >> start) & mask;
}

Walking it through

Take extract_field(0xD6, 2, 4) — bits 2-5 of 0xD6. In binary, 0xD6 is 1101 0110:

StepValueBinary
reg0xD61101 0110
reg >> 20x350011 0101
mask (width 4)0x0F0000 1111
result0x050000 0101

Shifting right by 2 walks bits 2-5 down to bits 0-3, dragging bits 6-7 along underneath them. The mask throws those away, leaving exactly the four bits that made up the field.

The mask, and why width == 32 needs its own line

(1u << width) - 1u is the standard way to build "N ones in a row", and it is correct for every width from 1 to 31. At width = 32 it breaks, because 1u << 32 shifts a 32-bit value by an amount equal to its own bit width — which C makes undefined, not merely "big". There is no guaranteed result at all, let alone a useful one.

On the compiler this app builds submissions with, the shift instruction the compiler emits takes its count modulo 32 in hardware, so 1u << 32 behaves like 1u << 0, giving 1u. Subtract one and the "mask" is 0: every bit of the field gets thrown away instead of kept, and a width-32 read of any register comes back 0. That is a real, reproducible failure on this toolchain, not a hypothetical one — which is exactly why it is worth routing around rather than relying on: a different compiler, a different optimisation level, or a future compiler version is free to do something else entirely with the same undefined shift.

The fix is to stop asking the shift to cover a case it cannot:

unsigned int mask = (width == 32) ? 0xFFFFFFFFu : (1u << width) - 1u;

reg >> start never has this problem on its own. The precondition guarantees start < 32 whenever width is at least 1, so the shift amount for the register itself never reaches 32 — only the mask calculation, which shifts by width rather than start, can hit the boundary.

Why right-justify at all

The alternative would be to return the field still sitting at its original bit position — reg & (mask << start) — but that pushes the shifting onto every caller, and it means a 1-bit field comes back as either 0 or 1u << start rather than a plain 0 or 1. Right-justifying once, here, is the same work done in one place instead of at every call site.

Cost

Two operators, no loop: O(1) time, O(1) space, for any width up to the full register.

A wrong turn worth recognising

Looping a bit at a time instead of shifting once. It is possible to extract a field by testing and copying one bit per iteration, and it gives the right answer — but it hides the two-operator shape that makes this pattern recognisable everywhere else it shows up, including in Write a Register Field, which builds directly on the mask computed the same way here.
