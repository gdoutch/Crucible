Unpack a CAN Signal (Intel Byte Order)

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Three steps, each one you already know from earlier problems in this set:

  1. Turn 8 separate bytes into one 64-bit number.
  2. Extract and, if signed, sign-extend a bit field from it — exactly Extract a Signed Sensor Reading, just 64 bits wide instead of 32.
  3. Scale it: raw * scale + offset.

The only genuinely new step is the first one, and it is one line:

unsigned long long raw64 = 0;
for (int i = 0; i < 8; i++) {
    raw64 |= (unsigned long long)payload[i] << (8 * i);
}

The trap the problem is built around

Intel byte order means byte 0 is the least significant byte, the opposite of how you would read a number written on paper. In the loop above, payload[0] ends up at bits 0-7 — the bottom of the 64-bit value — and payload[7] ends up at bits 56-63, the top. Build it the other way around (payload[0] shifted highest) and every multi-byte signal comes out as a completely different number, even though each individual bit was read from the right place in memory.

A fixed test with two non-zero bytes, 0x34 then 0x12, catches this directly: the correct 16-bit value is 0x1234 (4660); read the bytes the other way and you get 0x3412 instead.

The other trap, from further up the chain

raw * scale needs to happen in a wide type for the same reason the mask calculations in the earlier register problems did — a 32-bit raw value times even a small scale is already bigger than INT_MAX. The function returns long long precisely so there is somewhere for that product to live; do the multiplication in it, not in int.

Check yourself before you press Go

  • Bytes 34 12 at start_bit = 0, length = 16, unsigned: 4660, not 13330.
  • A field that straddles a byte boundary (start_bit not a multiple of 8) still extracts correctly — the byte-order assembly and the bit-field extraction are two separate, independently correct steps.
