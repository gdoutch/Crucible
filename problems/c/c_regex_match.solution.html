Match a Simplified Regular Expression ('.' and '*')

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

#include <stdbool.h>

static bool match_from(const char *s, const char *p)
{
    if (*p == '\0') {
        return *s == '\0';
    }

    bool first_match = (*s != '\0') && ((*p == *s) || (*p == '.'));

    if (*(p + 1) == '*') {
        return match_from(s, p + 2)
            || (first_match && match_from(s + 1, p));
    }
    return first_match && match_from(s + 1, p + 1);
}

bool regex_match(const char *s, const char *p)
{
    return match_from(s, p);
}

Why the base case comes first

*p == '\0' is checked before anything else touches *(p + 1). That ordering is load-bearing, not stylistic: a C string's terminating '\0' is a real, readable byte, but there is nothing *after* it to read, and *(p + 1) once p already points at the terminator reads past the end of the pattern's allocation. Handling "pattern exhausted" as the very first check means every later line can assume *p is a real pattern character, and that *(p + 1) -- whether it exists or is the terminator -- is safe to read.

Why first_match checks *s != '\0' up front

An atom cannot match a character that is not there. Computing first_match once, before branching on whether a * follows, keeps that "nothing left in s" case from needing to be re-derived separately in both branches below it -- both the plain-match branch and the star branch's "consume one more" option read the same first_match, and both are correctly `false` the moment `s` runs out.

Why the star branch recurses on the same `p`, not past it

match_from(s + 1, p) -- not p + 2 -- is what lets a run of `a`s any length match `a*`. Each recursive call in that branch consumes exactly one character of `s` and asks the identical question again: "does `a*` (still) match what is left?" The other call, match_from(s, p + 2), is the *only* place that skips past the atom and its `*` -- representing zero repetitions -- and it is tried unconditionally, not just as a fallback after the other branch fails. Both have to be tried, in an `||`, because a pattern like `a*a` needs the zero-repetitions branch to eventually let the second `a` in the pattern have a character to match against.

Why matching is a full match, not a prefix search

There is no code anywhere in this function that stops early because `p` ran out while `s` still has characters left over -- `match_from` only returns `true` from the base case, which explicitly requires `*s == '\0'` too. That single line is the entire difference between this and a `search`-style "does `p` occur somewhere in `s`" check: `regex_match("aa", "a")` reaches the base case with `p` exhausted and `s` still pointing at the second `'a'`, and returns `false` there.

The overlapping-subproblems issue, and what to do about it

This recursive form is correct, and fast enough for modest inputs -- but it is not memoised, so a pattern chaining several `*` groups can call `match_from` on the same `(s, p)` pair through more than one recursive path, redoing work each time. The fix, without changing the logic above at all, is to memoise on `(s, p)` (or equivalently on the two integer offsets into the original strings) and return a cached answer on a repeat visit -- turning the same recursion into a bottom-up or top-down dynamic-programming solution with the each-pair-computed-once guarantee that name implies.

Cost

The recursion above is exponential in the worst case without memoisation, because both branches of a star group can recurse into overlapping sub-ranges of `s` and `p`. Memoised on the (s, p) position pair, it becomes O(len(s) * len(p)) states, each doing O(1) work beyond its own recursive calls -- the standard bound for this problem, and the one worth aiming for once the recursive shape above is proven correct.
