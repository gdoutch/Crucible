Check Whether a Sensor Reading Is In Range (MISRA Essential Types)

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

#include <stdbool.h>
#include <stdint.h>

bool in_range(int32_t value, int32_t low, int32_t high)
{
    return (value >= low) && (value <= high);
}

That is the whole function. The interesting part of this problem is not the logic — two comparisons and an && is about as simple as C gets — it is ruling out the one-line version that looks even simpler and is wrong.

The bug hiding in the readable version

"Is value between low and high" reads naturally as one chained comparison:

return low <= value <= high;

C's relational operators are left-associative, so this parses as (low <= value) <= high: the result of the first comparison — 0 or 1 — is what gets compared against high, not value.

Trace it through low = 10, value = 5, high = 20: 10 <= 5 is 0, and 0 <= 20 is 1 — true. The function reports a reading of 5 as inside [10, 20], and it does this for essentially any positive high, regardless of what value actually is: as long as high >= 1, the second comparison is 0 <= high or 1 <= high, both of which are true. The chained form is not subtly wrong at the edges — it is always true for any range with a positive upper bound, which is most of them.

Why MISRA rules this shape out at the type level

low <= value has essential type Boolean: its only possible values are 0 and 1, standing for false and true, not for a quantity. high has essential type signed. MISRA's essential type model treats those as different categories that a relational operator is not allowed to mix — a conforming static analyser flags (low <= value) <= high before the program ever runs, because the left operand of that second <= is not a signed value being compared to another signed value, it is a Boolean being compared to one. The rule is not enforcing a style preference here; it is refusing to compile the exact shape that produces this bug.

Writing the two comparisons out in full and joining them with && sidesteps this because && expects two Boolean operands and that is exactly what (value >= low) and (value <= high) are — no essential-type mismatch, and no way for the expression to mean anything other than "both of these are true."

bool, not int

The return type is bool from <stdbool.h> rather than an int that happens to hold 0 or 1. It costs nothing extra here — the expression is already Boolean — but it means the function's signature states what its result means instead of leaving a reader to infer "oh, this int is really a flag" from the name.

What the fixed tests are checking

Two tests are built directly around the chained-comparison trap: a value below the range and a value above it, both of which the broken formula reports as true. The rest cover the ordinary edges — both bounds inclusive, a single-point range where low == high, and negative bounds behaving the same way positive ones do.
