Compute the Parity Bit

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Fold the word in half against itself with XOR, five times, until one bit is left carrying the parity of all 32:

int even_parity(unsigned int value)
{
    unsigned int v = value;

    v ^= v >> 16;
    v ^= v >> 8;
    v ^= v >> 4;
    v ^= v >> 2;
    v ^= v >> 1;
    return (int)(v & 1u);
}

Why XOR-folding preserves parity

XOR of two single bits is 1 exactly when the two bits differ -- which means the XOR of a whole row of bits is 1 exactly when an odd number of them are 1. That is the definition of parity, applied one XOR at a time instead of one bit of counting at a time.

v ^= v >> 16 lines the top half of the word up against the bottom half and XORs each pair together. Bit 0 of the result is bit0 XOR bit16; bit 1 is bit1 XOR bit17; and so on. The parity of those 16 pairs, each collapsed to one bit, is the same as the parity of the original 32 bits, because XOR is associative and commutative -- it does not matter what order the bits get combined in, only that every bit gets combined exactly once.

Repeating the halving -- 16 bits down to 8, 8 down to 4, 4 down to 2, 2 down to 1 -- carries the same invariant down at each step. After the last fold, bit 0 alone holds the XOR of all 32 original bits.

31 is odd, so the answer is 1 -- and it falls out of five XORs without ever counting anything.

The more obvious route, and why this one is faster

The straightforward answer reuses Count the Set Bits directly:

return count_set_bits(value) & 1;

That is completely correct -- parity is nothing more than the population count's lowest bit. It is also doing more work than the question asks for: Kernighan's loop there runs once per set bit, so a value with many bits set costs many iterations to learn a single bit of information. XOR-folding costs exactly five operations regardless of how many bits are set, because it never needs to know the count, only whether it was odd.

Why unsigned int, and why this fold in particular tolerates it less strictly than it looks

value is unsigned int for the same reason it is in Count the Set Bits: a right shift on an unsigned value always brings in zeros from the top. Keeping the working variable unsigned int too is the safe habit to have, and it is the version written above.

Worth knowing, if you are curious rather than just being careful: this particular fold happens to come out right even with a signed working variable, because the extra 1 bits an arithmetic right shift copies down from the sign bit always arrive in a range this fold XORs together an even number of times, which cancels them out of the final parity. That is a property of this exact five-step halving pattern, not a general licence to mix signed shifts into bit-manipulation code -- the popcount loop in Count the Set Bits has no such protection, which is why it is built around unsigned int deliberately rather than by luck.

Both are O(1) for a fixed-width type. In production, __builtin_parity(value) (GCC, Clang) compiles to a single hardware parity instruction where the target has one -- the right answer at work, and, as with the population count it is built on, not the point of writing it out here.
