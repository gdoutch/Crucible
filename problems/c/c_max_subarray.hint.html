Maximum Subarray Sum

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

The largest total obtainable from a contiguous run of elements. Contiguous means no gaps — you pick a start and an end, not a subset. The run must contain at least one element, unless the array is empty, in which case the answer is 0.

Start with the case that decides everything

Look at the fixed test single negative element: the array is -7 and the expected answer is -7, not 0.

That one line rules out the most common wrong solution — the one that clamps a running total at zero and returns zero when everything is negative. Because you must pick at least one element, an all-negative array's answer is its least bad element. Get that straight before writing anything.

The brute force, and what it wastes

Try every start, every end, sum each range: O(n³). Keep a running sum as the end moves: O(n²). Both pass these tests. Both recompute information they already had.

Kadane's question

Here is the reframing that collapses it to one pass. Instead of asking "what is the best run anywhere", ask a smaller question at each position:

What is the best run that ends exactly here?

That has a beautifully short answer, because a run ending at position i has only two possible shapes:

  • it is just values[i] on its own; or
  • it is the best run ending at i−1, extended by values[i].

There is no third option — extending anything other than the best run ending at i−1 would be worse by definition. So you take whichever of the two is larger, and that is a single comparison. Carry it forward, and separately remember the largest such value you have ever seen.

Two variables. One pass.

Making it concrete

Walk -2 1 -3 4 by hand, filling in "best run ending here":

ivalues[i]best ending hereWhy
0−2−2nothing to extend
111−2 + 1 = −1 is worse than starting fresh
2−3−21 + −3 = −2 beats starting fresh at −3
344−2 + 4 = 2 is worse than starting fresh

The best ever seen is 4. Notice the pattern: whenever the running value would drag you below the element itself, you abandon the past and start again from the current element.

Details

  • What do the two variables start at? Not zero — that is the same clamping bug in disguise. Both start at values[0], and the loop begins at index 1. Which means…
  • …the empty array must be handled first, before you touch values[0]. count may be 0 with values == NULL, and the answer is 0.
  • Zeros only is a fixed case: 0 0 0 → 0. It should fall out naturally.

int best = values[0];         /* best seen anywhere */
int current = values[0];      /* best run ending at i */

for (int i = 1; i < count; i++) {
    /* current = the larger of: values[i] alone,
                                current + values[i] */
    /* best = the larger of: best, current */
}
return best;

Two comparisons in the body, and the order matters: update current first, then fold it into best.
