Count the Set Bits

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Remove one set bit at a time and count how many times you had to do it. The trick that makes it a two-line loop is Kernighan's:

value & (value - 1) is value with its lowest set bit cleared, and nothing else changed.

The code

int count_set_bits(unsigned int value)
{
    int count = 0;

    while (value != 0) {
        value &= value - 1u;
        count++;
    }

    return count;
}

Why the identity holds

Take any non-zero value. Write it as some prefix, then its lowest 1, then a run of k zeros:

value       =  P 1 0 0 0
value - 1   =  P 0 1 1 1      borrow ripples through the zeros
value & ...    P 0 0 0 0

Subtracting one has to borrow, and the borrow propagates right-to-left through the trailing zeros — turning each of them into a 1 — and stops at the first 1 it meets, turning that into a 0. The prefix P is untouched.

AND the two together: the prefix survives (it is identical in both), the lowest set bit is gone (1 & 0), and the trailing zeros stay zero (0 & 1). One bit removed, exactly.

A concrete pass over 0b10110000 (176, three bits set):

Three iterations for three set bits, whatever their positions.

The unsigned in the signature is load-bearing

Everything above depends on the arithmetic being unsigned. Two of the fixed test cases exist to break code that lets the value become signed.

4294967295 — every bit set. That value does not fit in a signed 32-bit int. Assign it to one and you get -1. Now consider the alternative shift-based loop written with a signed variable:

int v = value;              /* -1 */
while (v != 0) {
    count += v & 1;
    v >>= 1;                /* stays -1 on every mainstream compiler */
}

Right-shifting a negative signed value is implementation defined. Every compiler you are likely to meet performs an arithmetic shift, which copies the sign bit down from the top — so -1 shifted right is -1. The loop never terminates. Crucible runs each case in its own process with a time limit, so you get TIMEOUT on that one case and passes on the small ones, which is the signature of this exact mistake.

2147483648 — bit 31 alone. The smallest value whose top bit is set. Signed, it is INT_MIN, and the same arithmetic shift drags ones down from the top: the count comes back as a number much larger than 1 rather than hanging. A different symptom of the same cause.

Kernighan's loop sidesteps the whole issue because it never shifts — but keep the type unsigned regardless. Note the 1u in value - 1u: with value already unsigned int the plain 1 would be converted anyway, so the suffix is documentation rather than necessity. It costs nothing and it tells the next reader that the unsignedness is deliberate.

The shift version, done correctly

int count_set_bits(unsigned int value)
{
    int count = 0;
    for (int i = 0; i < 32; i++) {
        count += (value >> i) & 1u;
    }
    return count;
}

A fixed 32 iterations, no loop-termination question to get wrong, and branch-free. Perfectly acceptable — it is just doing 32 units of work where Kernighan's does one per set bit.

Note count += ... & 1u rather than an if. The masked expression is already 0 or 1, so adding it directly is both shorter and, on a modern CPU, faster for avoiding an unpredictable branch.

All O(1) for a fixed-width type, all O(1) space. In production you would write __builtin_popcount(value) (GCC/Clang) or std::popcount (C++20), which compile to a single POPCNT instruction. That is the right answer at work and the wrong answer here, where the exercise is the bit manipulation itself.

Wrong turns worth recognising

Dividing by two instead of shifting. For unsigned values value /= 2 is equivalent and the compiler emits the same shift. For signed negative values it is not equivalent — division truncates towards zero, arithmetic shift rounds towards negative infinity — which is one more reason the type matters.

Using % and / as a decimal habit. value % 2 to get the bit and value / 2 to advance works, and it obscures that this is a bit problem. The bitwise operators say what you mean.
