Primes up to N

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

The sieve of Eratosthenes, and its defining feature is what it does not do: it never tests a number for primality. It keeps a flag per number, walks upwards, and every time it reaches a number that has not been crossed out it declares it prime and crosses out all of its multiples.

The reasoning is airtight. When the walk arrives at v, every prime below v has already crossed out all of its own multiples. So if v is still standing, no prime below it divides v — and a composite number always has a prime factor below itself. Therefore v is prime.

The code

#include <stdlib.h>

int primes_up_to(int n, int *out)
{
    if (n < 2) {
        return 0;
    }

    char *composite = calloc((size_t)n + 1, sizeof *composite);
    if (composite == NULL) {
        return 0;
    }

    int found = 0;
    for (int value = 2; value <= n; value++) {
        if (composite[value]) {
            continue;
        }
        out[found++] = value;
        for (long long multiple = (long long)value * value;
             multiple <= n;
             multiple += value) {
            composite[multiple] = 1;
        }
    }

    free(composite);
    return found;
}

Two things to notice. From 7 onwards the inner loop never runs at all: once value² > n, there is nothing left to mark. And the primes land in out in ascending order automatically, because the outer loop visits the numbers in order — no sorting step is needed.

Why the inner loop starts at value * value

The natural first multiple is 2 · value. But every multiple k · value with k < value has a factor smaller than value, and that smaller factor — or a prime dividing it — already had its turn in the outer loop and already crossed the number out. The first multiple that cannot have been reached that way is value · value.

Concretely, when value is 7: 14 fell to 2, 21 fell to 3, 28 fell to 2, 35 fell to 5, 42 fell to 2. The first new casualty is 49.

The overflow, which is the real trap

Written as int multiple = value * value;, the multiplication is performed in int. Once value exceeds 46340 the product exceeds INT_MAX, and signed overflow in C is undefined behaviour — not a wrap to a negative number you can reason about. In practice you get a large negative value, the condition multiple <= n is true, and composite[multiple] writes to memory far before the allocation.

Note carefully where the cast goes:

ExpressionVerdict
(long long)value * value Correct. The first operand is widened, so the second is promoted to match and the multiplication happens in 64 bits.
(long long)(value * value) Useless. The int multiplication overflows first; the cast widens the damage.

Keeping multiple itself a long long matters too: multiple += value must not overflow either, and the loop exits on the first value above n, which for n near INT_MAX is a number that does not fit in an int.

The alternative is to stop the outer loop early — for (int value = 2; (long long)value * value <= n; value++) for the crossing-out phase, then collect the survivors in a second pass. Same arithmetic care required, one more loop.

Memory

  • calloc, not malloc. "Not crossed out" is the starting state, and calloc zeroes the block. malloc hands you whatever was in that memory, and a stray non-zero byte would silently omit a prime.
  • char, not int. One byte per number instead of four. For n = 10 million that is 10 MB against 40 MB — and the sieve is memory-bound, so the small array is also the faster one.
  • (size_t)n + 1. The cast happens before the addition, so the arithmetic is done in size_t. Indices run from 0 to n inclusive, hence the + 1; slots 0 and 1 are never used and are not worth the index arithmetic to reclaim.
  • sizeof *composite rather than sizeof(char). It re-derives the size from the variable, so changing the type cannot desynchronise the allocation.
  • free before returning. One allocation, one release, on every path that allocated. Here that is the single successful return, because the failure path returns before allocating and the null-check path has nothing to release.

The n < 2 guard

It has to come first, and not only because the answer is zero. With n = -5, reaching calloc((size_t)n + 1, 1) converts the negative to a huge size_t and asks for roughly 18 exabytes — which fails, so the null check catches it, but only by luck. Rejecting the input up front is the honest version. Three of the five fixed cases — zero, one and negative — take this path.

Cost

O(n log log n) time — near-linear; the log log factor comes from summing n/p over the primes p up to n — and O(n) space for the flags.

Trial division, testing each number against every candidate divisor up to its square root, is O(n√n). For n = 1,000,000 that is the difference between a few milliseconds and several seconds.

Wrong turns worth recognising

Trial division dressed up as a sieve. Allocating the flag array and then filling it by testing each number for primality gets the memory cost of a sieve and the running time of trial division.

Off-by-one at the top. The problem says "up to and including n". Both the allocation (n + 1 slots) and the loop bound (value <= n) depend on it. The two fixed case catches a solution that stops at n - 1.

Leaking the scratch array. An early return from the middle of the loop — say a bounds check you added — that skips the free. One allocation per call, and this function may be called once per test case.
