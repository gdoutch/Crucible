Merge Two Sorted Arrays

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

The classic two-finger merge — the inner half of merge sort. Keep a position in each input. The smallest value not yet emitted is necessarily at one of the two positions, because everything behind them is already emitted and everything ahead of them is larger. Compare, take the smaller, advance that finger.

When one array is exhausted the comparison has nothing to compare against, and the rest of the other array is already sorted and already larger than everything emitted — so it is copied straight across.

The code

void merge_sorted(const int *a, int count_a,
                  const int *b, int count_b,
                  int *out)
{
    int i = 0, j = 0, k = 0;

    while (i < count_a && j < count_b) {
        out[k++] = (a[i] <= b[j]) ? a[i++] : b[j++];
    }
    while (i < count_a) {
        out[k++] = a[i++];
    }
    while (j < count_b) {
        out[k++] = b[j++];
    }
}

The one-line body is dense but honest. Written out:

if (a[i] <= b[j]) {
    out[k] = a[i];
    i++;
} else {
    out[k] = b[j];
    j++;
}
k++;

Both forms are fine. The post-increments in the compact version are safe here because each variable is modified once in the expression and the assignment sequences the write to out[k] — but if you have to think about it, write the long form.

Six values in, six out. Note the fourth row: both fronts are 4, and both 4s appear in the output. A merge does not deduplicate.

Why <= rather than <

On a tie, <= takes from a — the first array. Both choices produce correctly sorted output, so no test here can tell them apart. The difference is stability: when merge sort splits a sequence, a holds the elements that came earlier. Preferring a on equal keys preserves their original relative order; taking from b reverses it.

With bare ints equal values are indistinguishable and nothing is observable. Sort records by surname and it becomes very observable indeed. <= costs nothing, so make it the habit.

Why the drain loops are separate

The main loop's condition is a conjunction: it stops the moment either array is finished. It cannot copy the remainder itself, because doing so would mean reading past the end of the exhausted array.

Exactly one drain loop does any work — whichever array still has elements — and the other's condition is false on first evaluation. Both must be written because you cannot know in advance which. The first empty and second empty fixed cases exercise one each, with the main loop never running at all.

memcpy would do the drains faster:
memcpy(out + k, a + i, (size_t)(count_a - i) * sizeof *out);
Correct, and worth it in a real merge sort. The loop is clearer at this size, and it handles the zero-remaining case without a special check.

The NULL question

An empty array's pointer may be NULL. Every read of a[i] or b[j] in this function sits inside a condition that has already established the corresponding count is positive, so a null pointer is never dereferenced. Test the count, never the pointer — a non-null pointer to a zero-length array is perfectly legal, and if (a != NULL) would happily read from it.

The both empty case runs all three loop conditions once, fails all three, and writes nothing. out is untouched, which is right — zero values were merged.

Cost

O(n + m) time and O(1) extra space (the output buffer belongs to the caller). Every element is compared at most once and copied exactly once.

The alternative — concatenate then sort — is O((n+m) log(n+m)) and throws away the ordering the inputs already had. That is the real lesson here: the inputs being sorted is information, and a merge is what spending it looks like.

Wrong turns worth recognising

Advancing both fingers on a tie. Feels efficient, drops a value. The output ends up one element short and everything after the tie is shifted, which reads as a mysterious truncation.

Using || in the main loop condition. while (i < count_a || j < count_b) keeps going after one array is exhausted and then compares a[i] past its end. It often works by accident, reading whatever is next in memory, and fails unpredictably.

Merging into one of the inputs. Not possible here — they are const — but the general trap is real: merging in place overwrites values you have not yet read. The standard trick when the destination is one of the sources is to fill it from the back, largest first, where the free space is.
