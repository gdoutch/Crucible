Fix the Analogue Output Correction

Worked solution

This page contains the complete answer and explains why each part of it is there.

The defect

Subtracting a larger unsigned value from a smaller one does not go negative. It wraps around to the top of the type's range. dw is uint32_t, so 0u - 3000u is not -3000 — it is 4294964296, a perfectly ordinary, perfectly valid uint32_t.

The line that does the damage:

dw -= AO_OFFSET;   /* underflows whenever dw < AO_OFFSET */

and the fix, which is the whole fix — guard the subtraction so it can only ever run when it is safe:

uint16_t scale_analogue_output(uint16_t raw)
{
    uint32_t dw = raw;

    dw *= AO_GAIN;
    if (dw > AO_OFFSET)
    {
        dw -= AO_OFFSET;
    }
    else
    {
        dw = 0u;
    }
    dw /= AO_SCALE;

    if (dw > AO_FULL_SCALE)
    {
        dw = AO_FULL_SCALE;
    }

    return (uint16_t)dw;
}

When raw * AO_GAIN would leave the correction below zero in real terms, the corrected value is simply 0 — the DAC value for "as low as this output goes" — instead of whatever the wraparound happened to leave lying around for the clamp to find.

Walking raw = 0 through both versions

StepBuggyFixed
dw = raw00
dw *= AO_GAIN00

Both columns reach the clamp. Only one of them is being clamped for a real reason. The buggy column is not "off by a bit" or "rounding the wrong way" — it hands the final if a value nowhere near the true answer, and the if does exactly what a bounds check is supposed to do with a value that big: pin it to the maximum.

Why the band is four counts wide, not one

The subtraction is safe exactly when raw * AO_GAIN > AO_OFFSET, i.e. raw > AO_OFFSET / AO_GAIN = 3000 / 990 ≈ 3.03. Integer raw values 0, 1, 2 and 3 all fall short of that; 4 is the first one past it. That is the entire reason the test suite's underflow band is 0..3 and clears at exactly 4 — it falls straight out of the two constants, not out of anything special about zero. A bench calibration with a smaller offset, or a steeper gain, would narrow that band; it would not remove it.

The case that keeps this out of a debugger

Nothing crashes. There is no invalid read, no invalid write, no division by zero, no signed-overflow undefined behaviour. Every operation in the buggy function is fully defined by the C standard and does precisely what the standard says it will do. A debugger will show you a dw full of nines and a clamp firing exactly as written — both true, and neither one wrong. The defect is not in any single line's behaviour; it is in what the second line was allowed to hand the fourth.

It is also why the usual safety net does not catch it. UndefinedBehaviorSanitizer's overflow checks exist for exactly this shape of bug — but they trigger on signed overflow, which is undefined behaviour, not on unsigned wraparound, which the standard defines and which plenty of real code (checksums, free-running tick counters, hash mixing) relies on deliberately. -fsanitize=unsigned-integer-overflow exists precisely because the default build tooling will not flag this for you.

The readings that pass either way

4095 and 4200 come out at 4095 whether or not the fix is applied, and that is worth sitting with rather than shrugging off. The correction's gain is a shade under 1 (990/1000), so a legitimately-computed value never actually reaches full scale within the 12-bit input range in this design — the clamp is there for the input that runs a little past nominal (rounding slop from an earlier stage, say), not for anything inside the calibrated range. That clamp firing correctly, on realistic data, on every test run anyone ever wrote against this function, is a big part of why the defect survived review: the one piece of code near the bug that gets regularly exercised by real signals was never the piece that was wrong.

What else would you flag in this function?

The defect is fixed, but a review would not stop there.

  • There is only ever an upper-bound check. Nothing in the original function ever asks "did this go too low?" — every failure mode this arithmetic can produce resolves, structurally, to "value too big → clamp to max." A subtraction is not the only way to trigger that; any future change to this correction that can underflow will fail the same silent way, and clamp the wrong direction, until someone adds a matching lower bound.
  • dw's width was never the issue. Making it a wider or narrower unsigned type changes nothing about whether this bug exists — 16, 32 and 64-bit unsigned subtraction all wrap the same way. If your first instinct on seeing this class of bug is "use a bigger type," that instinct is worth unlearning; the fix is a comparison before the subtraction, not a wider container for the wrapped result.
  • Truncating division, more than once. Both dw /= AO_SCALE here and any prior stage that scaled raw down by division round toward zero. Each one is a small, one-directional bias, and biases from separate truncating divides in the same pipeline can compound differently depending on the input's scale — worth measuring on the bench rather than assuming they cancel out.
  • The magic numbers. 990, 3000 and 1000 read as arbitrary without the comment explaining the fixed-point scaling. A _Static_assert tying AO_SCALE to the number of decimal digits in the calibration constants, or simply naming the real gain and offset in the comment (as this one does), is the difference between a reviewer being able to check the arithmetic and a reviewer taking it on faith.

The general lesson

Unsigned wraparound is not a bug in itself — it is well-defined, and plenty of code (a free-running tick counter's elapsed-time calculation, for one) relies on it correctly. It becomes a bug the moment a computation reaches a subtraction that can wrap on inputs the rest of the system considers completely ordinary, and nothing downstream is written to tell "wrapped" apart from "large and legitimate." The fix is never a wider type. It is knowing, at the point of every unsigned subtraction, whether the minuend can be smaller than the subtrahend — and if it can, checking before you subtract, not after.
