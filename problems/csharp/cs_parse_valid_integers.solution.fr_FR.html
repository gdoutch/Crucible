Ne garder que les entiers valides

Solution détaillée

Cette page contient la réponse complète et explique pourquoi chaque partie s'y trouve.

Le code

public static List<int> ParseValidIntegers(List<string> tokens)
{
    var result = new List<int>();
    foreach (var token in tokens)
    {
        if (int.TryParse(token, out int value))
        {
            result.Add(value);
        }
    }
    return result;
}

Pourquoi c'est toute la fonction, et rien de plus

int.TryParse, appelé sans argument NumberStyles, implémente déjà exactement la règle que cet exercice spécifie : un signe optionnel en tête, un ou plusieurs chiffres décimaux, des espaces optionnels autour, et un résultat qui tient dans 32 bits. Chaque cas limite que l'énoncé mentionne -- la tolérance aux espaces, la limite de débordement à int.MaxValue et int.MinValue, le rejet des points décimaux et de la notation hexadécimale -- est le comportement propre, déjà correct, de TryParse. Le seul travail de cette fonction est d'aiguiller ce verdict vers ou en dehors de la liste de résultats, pas de le redécider.

L'alternative séduisante en apparence -- try { result.Add(int.Parse(token)); } catch (FormatException) { } -- produit les mêmes réponses, mais paie chaque jeton rejeté au prix de lever et capturer une exception, et fait appel à la gestion d'exceptions pour modéliser quelque chose qui n'a rien d'exceptionnel : un jeton qui n'est pas un nombre est un résultat parfaitement ordinaire et attendu pour un filtre dont le seul but est de distinguer les deux types de jetons. TryParse existe précisément pour que cette distinction n'ait jamais besoin d'une exception.

La limite de débordement, dans les deux sens

int.MinValue vaut -2147483648, et c'est un int parfaitement valide -- TryParse l'accepte. Un de plus vers le négatif, -2147483649, et un de plus que int.MaxValue (2147483648), échouent tous les deux : non pas à cause de leurs chiffres, mais parce que la valeur qu'ils désignent ne tient pas dans 32 bits signés. Un cas de test fixe vérifie les deux valeurs limites des deux côtés précisément parce qu'une vérification de plage écrite à la main est un endroit facile pour se tromper d'une unité, et TryParse ne se trompe jamais.

Coût

O(n) dans le nombre de jetons -- une tentative d'analyse par jeton, aucune allocation au-delà de la liste de résultats elle-même.
