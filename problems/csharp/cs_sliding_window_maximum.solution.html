Sliding Window Maximum

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

public static int[] SlidingWindowMaximum(int[] values, int windowSize)
{
    var result = new int[values.Length - windowSize + 1];
    var deque = new LinkedList<int>();   // indices; values decreasing front-to-back

    for (int i = 0; i < values.Length; i++)
    {
        while (deque.Count > 0 && deque.First.Value <= i - windowSize)
        {
            deque.RemoveFirst();
        }
        while (deque.Count > 0 && values[deque.Last.Value] <= values[i])
        {
            deque.RemoveLast();
        }
        deque.AddLast(i);

        if (i >= windowSize - 1)
        {
            result[i - windowSize + 1] = values[deque.First.Value];
        }
    }
    return result;
}

Why every index is added and removed from the deque at most once

Each index enters the deque exactly once, via AddLast. From there it leaves in exactly one of two ways: evicted from the back by a later, at-least-as-large value before it ever reaches the front, or evicted from the front once the window slides past it. Either way, once it is gone, it is gone for good -- nothing ever re-adds an index. That is what bounds the total work across the whole function: n insertions and at most n removals, rather than the O(n · windowSize) a fresh rescan of every window would cost.

Why the eviction check is <=, not <

An index whose value is merely tied with the newly-arriving one is already redundant: the new one will outlast it in the window (it arrived later, so it ages out later), so the older, tied value can never be the sole maximum again once the newer one exists alongside it. Evicting on <= keeps the deque as small as the actual distinct "still might matter" values, rather than accumulating equal-valued indices that a strict < would let sit there unread. Both versions compute the correct maximum -- a tie does not change which value is biggest -- but only the <= version keeps the deque's size bounded by the shape of the data rather than by how many ties happen to occur in it.

Why front eviction happens before back eviction

Both checks run every iteration, in this order, because they are answering different questions about different ends of the deque: "has the window moved past this index" (front) has nothing to do with "is this index's value now redundant" (back), and doing the front check first means a stale index is never mistakenly read as the window's current maximum, even for the one iteration it would otherwise have survived.

Cost

O(n) total -- each of the n elements is pushed onto the deque exactly once and popped at most once, from either end, both O(1) operations on a LinkedList<T>. Contrast with the O(n · windowSize) of rescanning every window from scratch.
