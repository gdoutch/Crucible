Binary Search With an Insertion-Point Convention

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

public static int BinarySearchInsertionPoint(int[] sortedValues, int target)
{
    int low = 0;
    int high = sortedValues.Length - 1;

    while (low <= high)
    {
        int mid = low + (high - low) / 2;
        if (sortedValues[mid] == target)
        {
            return mid;
        }
        if (sortedValues[mid] < target)
        {
            low = mid + 1;
        }
        else
        {
            high = mid - 1;
        }
    }
    return ~low;
}

Why low is exactly the insertion point when the loop ends

Two invariants hold throughout the loop, maintained by which bound moves on each comparison: every index strictly less than low holds a value known to be less than target, and every index strictly greater than high holds a value known to be greater. The loop keeps narrowing that gap until low and high cross -- low == high + 1 -- at which point low is the first index the "known greater" region begins at, which is precisely where target would have to go to keep everything before it smaller and everything from that point on no smaller. That holds whether low lands in the middle of the array, at 0 (target belongs before everything), or at sortedValues.Length (target belongs after everything) -- the same invariant produces the right answer at both ends without a separate check for either.

Why the complement, and why it round-trips

~x for a non-negative x is defined as -x - 1 -- not -x. That extra -1 is what makes every non-negative index map to a *distinct* negative number, including 0: ~0 == -1, unambiguously different from a genuine "found at index 0" result of 0, whereas -0 == 0 would collide with it outright. The same shift is also what makes the encoding reversible in the other direction: a caller holding a negative result can recover the insertion index with a second complement, ~result, because ~(~x) == x for every integer x -- complementing twice cancels out exactly. This is the same convention Array.BinarySearch and List<T>.BinarySearch use, which is the whole reason it is worth matching rather than inventing a different not-found signal.

Cost

O(log n) in the length of `sortedValues` -- each comparison discards half of what remains to be searched.
