Interleave Two Sequences, Lazily

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

public static IEnumerable<int> Interleave(IEnumerable<int> a, IEnumerable<int> b)
{
    using var ea = a.GetEnumerator();
    using var eb = b.GetEnumerator();
    bool aHasMore = ea.MoveNext();
    bool bHasMore = eb.MoveNext();

    while (aHasMore || bHasMore)
    {
        if (aHasMore)
        {
            yield return ea.Current;
            aHasMore = ea.MoveNext();
        }
        if (bHasMore)
        {
            yield return eb.Current;
            bHasMore = eb.MoveNext();
        }
    }
}

Why two independent flags, not one shared loop variable

aHasMore and bHasMore are tracked separately because the two sequences finish independently -- one might still have a thousand elements left when the other runs dry after two. Folding them into a single "keep going" condition checked with && answers a different question than the one this exercise asks: it stops the whole interleave the moment the shorter sequence is exhausted, discarding everything left in the longer one. The || in the loop condition, paired with the two independent ifs inside it, is what lets each side keep contributing for exactly as long as it has something left, with no dependency on the other side's state.

Why this has to be GetEnumerator() and `MoveNext()`, not two `foreach` loops

A foreach loop owns its enumerator for the loop's entire body and cannot yield control back to an outer context mid-iteration to let a *different* sequence take its turn -- there is no way to write "advance a by one, then pause, then advance b by one" using foreach on either sequence alone. Pulling the enumerators out by hand is what makes "one step from each, alternating" expressible at all: each MoveNext() call advances exactly one side, exactly one element, and the method's own state (which side goes next) lives in the local variables between calls -- which is also precisely what the compiler's generated state machine for yield return exists to preserve across pauses.

Why the enumerators are wrapped in using

IEnumerator<T> extends IDisposable, and a caller is free to stop enumerating the interleaved result before it runs to completion -- taking only the first three elements with .Take(3), say. using var ea = ...; guarantees ea's (and eb's) `Dispose()` runs when the iterator itself is disposed, whether that happens because it ran to completion or because a caller walked away early; for a plain in-memory sequence like a List<int> this has nothing real to clean up, but the same code interleaving two sequences backed by open files or network streams would leak a handle per abandoned enumeration without it.

Cost

O(n + m) where n and m are the two sequences' lengths -- each element from each source is visited exactly once, and nothing is buffered: the whole sequence is produced lazily, one element per MoveNext() on the result.
