Keep Only the Valid Integers

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

public static List<int> ParseValidIntegers(List<string> tokens)
{
    var result = new List<int>();
    foreach (var token in tokens)
    {
        if (int.TryParse(token, out int value))
        {
            result.Add(value);
        }
    }
    return result;
}

Why this is the whole function, and no more

int.TryParse, called with no NumberStyles argument, already implements exactly the rule this exercise specifies: an optional leading sign, one or more decimal digits, optional surrounding whitespace, and a result that fits in 32 bits. Every edge case the statement calls out -- whitespace tolerance, the overflow boundary at int.MaxValue and int.MinValue, the rejection of decimal points and hex notation -- is TryParse's own, already-correct behaviour. The whole job of this function is routing that verdict into or out of the result list, not re-deciding it.

The tempting-looking alternative -- try { result.Add(int.Parse(token)); } catch (FormatException) { } -- produces the same answers, but pays for every rejected token with the cost of throwing and catching an exception, and reaches for exception handling to model something that is not exceptional at all: a token that is not a number is an entirely ordinary, expected outcome for a filter whose whole purpose is telling the two kinds of token apart. TryParse exists specifically so this distinction never needs an exception.

The overflow boundary, both directions

int.MinValue is -2147483648, and it is a perfectly valid int -- TryParse accepts it. One more negative than that, -2147483649, and one more positive than int.MaxValue (2147483648), both fail: not because of anything about their digits, but because the value they name does not fit in 32 bits signed. A fixed test checks both boundary values on both sides specifically because a hand-rolled range check is an easy place to be off by one, and TryParse never is.

Cost

O(n) in the number of tokens -- one parse attempt per token, no allocation beyond the result list itself.
