Total Area Through an Interface

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

public static double TotalArea(List<IShape> shapes)
{
    double total = 0;
    foreach (var shape in shapes)
    {
        total += shape.Area();
    }
    return total;
}

Why this needs no knowledge of Circle or Rectangle at all

shape.Area() is a virtual dispatch through the IShape interface: at runtime, the call lands on whichever concrete type's Area() actually implements it, decided by the object's real type, not by the compile-time type of the shape variable (which is just IShape, and stays that way throughout this function). That is precisely what makes this function correct for a type it has never heard of -- a hidden third implementation, say, with its own formula for its own Area() -- with zero changes required here. A function that instead asks "is this a Circle? is this a Rectangle?" has reimplemented the interface's own dispatch by hand, badly: it only recognises the types someone remembered to check for, and a fixed test's undocumented third shape exposes exactly that gap.

Why an empty list needs no special case

total starts at 0, and foreach over an empty list simply never executes its body -- the function returns 0 without an explicit check, the same way a sum over zero elements always should.

Cost

O(n) in the number of shapes -- one virtual call to Area() per shape, no allocation.
