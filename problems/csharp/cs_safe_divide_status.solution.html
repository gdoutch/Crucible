Division With Two Distinct Failure Modes

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

public static (DivideStatus Status, int Value) SafeDivide(int a, int b)
{
    if (b == 0)
    {
        return (DivideStatus.DivideByZero, 0);
    }
    if (a == int.MinValue && b == -1)
    {
        return (DivideStatus.Overflow, 0);
    }
    return (DivideStatus.Ok, a / b);
}

Why integer division overflow-checks even when nothing else does

C#'s checked/unchecked contexts govern whether +, - and * on integers throw on overflow or silently wrap -- unchecked is the default, and under it those three operators wrap without complaint. Division does not follow that rule: int.MinValue / -1 throws System.OverflowException whether the surrounding code is checked or not, because the .NET runtime's division instruction itself faults on that specific input at the hardware level -- there is no silently-wrapped answer for it to fall back to the way there is for addition or multiplication. That is what makes catching the exception after the fact strictly worse than checking for it up front: the fault has already happened, unconditionally, by the time a catch block would see it.

Why the two failure modes get two different enum values

b == 0 and a == int.MinValue && b == -1 are entirely different questions with entirely different answers -- one is about the divisor alone, the other about a specific pairing of dividend and divisor. Reporting both as the same status (or catching a general exception and mapping every case of it to DivideByZero because that is the more familiar name) throws away information a caller might reasonably want: "there is no mathematical answer" and "the answer exists but does not fit in 32 bits" are different problems, and a caller deciding how to recover benefits from knowing which one it is.

Why the order of the two checks does not actually matter here

b == 0 and b == -1 are mutually exclusive -- no input can trigger both checks, so the two ifs could be swapped without changing the function's behaviour on any input. They are written zero-check first here simply because it is the more familiar case to read first, not because the ordering carries any logical weight.

Cost

O(1) -- two comparisons and, on the ordinary path, one division.
