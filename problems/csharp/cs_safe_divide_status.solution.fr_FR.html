Division avec deux modes d'échec distincts

Solution détaillée

Cette page contient la réponse complète et explique pourquoi chaque partie s'y trouve.

Le code

public static (DivideStatus Status, int Value) SafeDivide(int a, int b)
{
    if (b == 0)
    {
        return (DivideStatus.DivideByZero, 0);
    }
    if (a == int.MinValue && b == -1)
    {
        return (DivideStatus.Overflow, 0);
    }
    return (DivideStatus.Ok, a / b);
}

Pourquoi la division entière vérifie le débordement alors que rien d'autre ne le fait

Les contextes checked/unchecked de C# gouvernent le fait que +, - et * sur des entiers lèvent une exception en cas de débordement ou débordent silencieusement -- unchecked est la valeur par défaut, et sous ce régime ces trois opérateurs débordent sans se plaindre. La division ne suit pas cette règle : int.MinValue / -1 lève une System.OverflowException que le code environnant soit checked ou non, parce que l'instruction de division du runtime .NET elle-même échoue sur cette entrée précise au niveau matériel -- il n'existe aucune réponse débordée silencieusement sur laquelle elle pourrait se replier, contrairement à l'addition ou la multiplication. C'est ce qui rend la capture de l'exception après coup strictement pire que la vérifier en amont : l'erreur s'est déjà produite, sans condition, au moment où un bloc catch la verrait.

Pourquoi les deux modes d'échec reçoivent deux valeurs d'énumération différentes

b == 0 et a == int.MinValue && b == -1 sont des questions entièrement différentes avec des réponses entièrement différentes -- l'une concerne le diviseur seul, l'autre une combinaison précise de dividende et de diviseur. Rapporter les deux comme le même statut (ou capturer une exception générale et faire correspondre chaque cas à DivideByZero parce que c'est le nom le plus familier) fait perdre une information qu'un appelant pourrait raisonnablement vouloir : « il n'y a pas de réponse mathématique » et « la réponse existe mais ne tient pas dans 32 bits » sont des problèmes différents, et un appelant qui décide comment réagir a intérêt à savoir lequel des deux c'est.

Pourquoi l'ordre des deux vérifications n'a en réalité pas d'importance ici

b == 0 et b == -1 s'excluent mutuellement -- aucune entrée ne peut déclencher les deux vérifications, donc les deux if pourraient être échangés sans changer le comportement de la fonction sur quelque entrée que ce soit. Ils sont écrits avec la vérification du zéro en premier ici simplement parce que c'est le cas le plus familier à lire en premier, pas parce que l'ordre porterait un poids logique quelconque.

Coût

O(1) -- deux comparaisons et, sur le chemin ordinaire, une division.
