Muter des structs à l'intérieur d'une liste

Solution détaillée

Cette page contient la réponse complète et explique pourquoi chaque partie s'y trouve.

Le code

public static void IncrementAll(List<Counter> counters)
{
    for (int i = 0; i < counters.Count; i++)
    {
        var c = counters[i];
        c.Increment();
        counters[i] = c;
    }
}

Pourquoi counters[i].Increment() compile et ne fait rien

List<T>.this[int] est une propriété, et lire une propriété signifie appeler son accesseur et recevoir ce qu'il retourne. Pour un type d'élément struct, ce qu'il retourne est une copie de la valeur stockée en interne -- les structs n'ont pas d'identité comme les objets en ont une, donc « la struct à l'indice i » et « une copie de la struct à l'indice i » sont, une fois lues, des valeurs indiscernables, sans lien persistant avec le tableau propre de la liste. Appeler Increment() directement sur le résultat de l'indexeur mute cette copie -- à laquelle rien d'autre ne fait référence, et qui est jetée dès que l'instruction se termine -- tandis que le stockage réel de la liste ne change jamais. Aucun diagnostic ne se déclenche parce que rien ici n'est réellement illégal : le code fait exactement ce qu'il dit, muter une valeur, sauf que la valeur en question n'est reliée à rien de durable.

Pourquoi trois instructions séparées, pas une seule

Seules deux opérations dans la version corrigée touchent jamais le stockage réel de la liste : counters[i] à droite d'une affectation (l'accesseur, qui lit une copie) et counters[i] = c (le mutateur, qui écrit une valeur). Tout ce qui arrive à c entre les deux -- ici, un appel à Increment() -- opère purement sur la copie locale, et n'est préservé que parce que la ligne suivante réécrit explicitement cette locale dans l'emplacement d'où elle venait. Omettez l'affectation finale et la mutation est correctement calculée puis abandonnée, exactement comme dans la version en une ligne que ceci remplace.

À quoi cela ressemblerait avec une classe à la place

Si Counter était déclarée comme une class plutôt qu'une struct, counters[i] retournerait une référence vers l'unique objet partagé à cette position -- et counters[i].Increment() fonctionnerait exactement comme la version naïve l'espérait ici, parce qu'il n'y aurait qu'un seul objet Counter par élément, pas une copie fraîche à chaque lecture. C'est précisément pourquoi ce piège est spécifique aux types valeur : il ne s'agit pas de l'indexeur de `List` qui serait inhabituel, il s'agit de ce que signifie « lire une valeur hors d'une collection » quand le type d'élément est une struct plutôt qu'une classe.

Coût

O(n) dans le nombre de compteurs -- une lecture, une mutation et une écriture par élément, toutes en O(1).
