Mutating Structs Inside a List

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

public static void IncrementAll(List<Counter> counters)
{
    for (int i = 0; i < counters.Count; i++)
    {
        var c = counters[i];
        c.Increment();
        counters[i] = c;
    }
}

Why counters[i].Increment() compiles and does nothing

List<T>.this[int] is a property, and reading a property means calling its getter and receiving whatever it returns. For a struct element type, what it returns is a copy of the value stored internally -- structs do not have identity the way objects do, so "the struct at index i" and "a copy of the struct at index i" are, once read out, indistinguishable values with no lingering connection back to the list's own array. Calling Increment() directly on the indexer's result mutates that copy -- which nothing else refers to, and which is thrown away the moment the statement ends -- while the list's actual storage never changes. No diagnostic fires because nothing here is actually illegal: the code does exactly what it says, mutate a value, the value in question just is not connected to anything durable.

Why three separate statements, not one

Only two operations in the fixed version ever touch the list's real storage: counters[i] on the right of an assignment (the getter, reading a copy out) and counters[i] = c (the setter, writing a value in). Everything that happens to c in between -- here, one call to Increment() -- operates purely on the local copy, and is only preserved because the very next line explicitly writes that local back into the slot it came from. Skip the final assignment and the mutation is computed correctly and then discarded, exactly as it was in the one-liner this replaces.

What this would look like with a class instead

If Counter were declared as a class instead of a struct, counters[i] would return a reference to the one shared object at that position -- and counters[i].Increment() would work exactly as the naive version here hoped it would, because there would be only one Counter object per element, not a fresh copy on every read. That is precisely why this trap is specific to value types: it is not about `List`'s indexer being unusual, it is about what "read a value out of a collection" *means* when the element type is a struct rather than a class.

Cost

O(n) in the number of counters -- one read, one mutation and one write per element, all O(1).
