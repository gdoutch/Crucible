Maximum de fenêtre glissante

Solution détaillée

Cette page contient la réponse complète et explique pourquoi chaque partie s'y trouve.

Le code

public static int[] SlidingWindowMaximum(int[] values, int windowSize)
{
    var result = new int[values.Length - windowSize + 1];
    var deque = new LinkedList<int>();   // indices ; valeurs décroissantes de l'avant vers l'arrière

    for (int i = 0; i < values.Length; i++)
    {
        while (deque.Count > 0 && deque.First.Value <= i - windowSize)
        {
            deque.RemoveFirst();
        }
        while (deque.Count > 0 && values[deque.Last.Value] <= values[i])
        {
            deque.RemoveLast();
        }
        deque.AddLast(i);

        if (i >= windowSize - 1)
        {
            result[i - windowSize + 1] = values[deque.First.Value];
        }
    }
    return result;
}

Pourquoi chaque indice est ajouté et retiré de la deque au plus une fois

Chaque indice entre dans la deque exactement une fois, via AddLast. À partir de là, il en sort d'exactement une des deux façons : évincé de l'arrière par une valeur ultérieure au moins aussi grande avant même d'atteindre l'avant, ou évincé de l'avant une fois que la fenêtre a glissé au-delà de lui. Dans les deux cas, une fois parti, il est parti pour de bon -- rien ne réajoute jamais un indice. C'est ce qui borne le travail total sur toute la fonction : n insertions et au plus n suppressions, plutôt que les O(n · windowSize) que coûterait un nouveau parcours de chaque fenêtre.

Pourquoi la vérification d'éviction est <=, pas <

Un indice dont la valeur est simplement à égalité avec celle qui vient d'arriver est déjà redondant : la nouvelle survivra plus longtemps dans la fenêtre (elle est arrivée plus tard, donc elle en sortira plus tard), donc l'ancienne valeur, à égalité, ne peut plus jamais redevenir le seul maximum une fois que la plus récente existe à ses côtés. Évincer sur <= garde la deque aussi petite que les valeurs distinctes « qui pourraient encore compter », plutôt que d'accumuler des indices de valeur égale qu'un < strict laisserait s'y installer sans être relus. Les deux versions calculent le bon maximum -- une égalité ne change pas quelle valeur est la plus grande -- mais seule la version en <= garde la taille de la deque bornée par la forme des données plutôt que par le nombre d'ex æquo qui s'y trouvent.

Pourquoi l'éviction avant se produit avant l'éviction arrière

Les deux vérifications s'exécutent à chaque itération, dans cet ordre, parce qu'elles répondent à des questions différentes sur des extrémités différentes de la deque : « la fenêtre a-t-elle dépassé cet indice » (avant) n'a rien à voir avec « la valeur de cet indice est-elle devenue redondante » (arrière), et faire la vérification avant en premier garantit qu'un indice obsolète n'est jamais lu par erreur comme le maximum courant de la fenêtre, même pour la seule itération où cela aurait autrement pu survivre.

Coût

O(n) au total -- chacun des n éléments est empilé dans la deque exactement une fois et retiré au plus une fois, de l'une ou l'autre extrémité, deux opérations en O(1) sur une LinkedList<T>. À comparer aux O(n · windowSize) d'un nouveau parcours de chaque fenêtre depuis zéro.
