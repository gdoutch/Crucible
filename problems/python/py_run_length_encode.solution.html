Run-Length Encoding

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Carry two pieces of state — the character the current run is made of, and how long it is — and walk the string. A character equal to the run extends it; anything else ends the run, which is emitted before a new one starts from the current character.

The whole difficulty is that runs are emitted by their successor, and the last run has no successor.

The code

def encode(text):
    """Return the run-length encoding of `text`."""
    if not text:
        return ""

    parts = []
    run_char = text[0]
    run_length = 1

    for char in text[1:]:
        if char == run_char:
            run_length += 1
        else:
            parts.append(f"{run_char}{run_length}")
            run_char = char
            run_length = 1

    parts.append(f"{run_char}{run_length}")
    return "".join(parts)

The line after the loop

parts.append(f"{run_char}{run_length}") appears twice, and it has to. Inside the loop it emits a run that a different character has just ended. After the loop it emits the run that the end of the string ended.

Leave the second one out and every output is missing its final run. "aaabbc" becomes "a3b2"; "z" becomes "". Notice that the tests would still show something plausible — the output is well-formed, just truncated — which is what makes this bug worth practising.

The alternative is to append a sentinel that cannot appear in the input and let the loop's own else branch flush the last run. That works for bytes with a reserved value; for arbitrary text there is no character you can safely reserve, so the explicit flush is the honest version.

Seeding from text[0]

run_char has no sensible "nothing yet" value that is also a character, so the function reads the first character directly and iterates over text[1:]. That requires there to be a first character, which is what if not text: return "" guarantees — the guard is load-bearing, not decorative.

not text rather than len(text) == 0 is the Python idiom, and it reads as "if there is no text".

text[1:] copies the string. For the inputs here that is irrelevant; for a very large one you would iterate over indices instead, or use itertools.islice(text, 1, None), which slices lazily.

Result "a1A1a2". == on characters is exact, so a and A are different and the run breaks — no case-folding anywhere, which is the specification.

Why the counts are not capped

The run longer than nine test — twelve as producing "a12" — pins down that the count is written as a decimal number, not as a single digit. The f-string does this without being asked; a solution that deliberately splits long runs into chunks of nine has invented a rule the problem does not have.

It is a real rule in some formats: fixed-width RLE, where each count occupies one byte, genuinely must break runs at 255. Worth knowing that the variant exists, and worth not implementing it here.

An aside on the format itself: this encoding is not always a compression. "abc" encodes to "a1b1c1", twice the length. RLE only wins on data with long runs — scanned documents, simple bitmaps — which is why real formats either mark runs explicitly or fall back to storing literals.

"".join(parts)

Python strings are immutable, so result += piece allocates a new string and copies the old contents every time — O(n²) over the whole output. Collecting into a list and joining once is O(n).

CPython has an optimisation that makes += on strings fast when the left operand has no other references, so in practice the naive version is often fine. It is an implementation detail of one interpreter, and join is both faster everywhere and clearer about intent.

Cost

O(n) time — one pass, one comparison per character — and O(n) space for the output, which is unavoidable since the output can be longer than the input.

The library version

from itertools import groupby

def encode(text):
    return "".join(f"{char}{len(list(group))}"
                   for char, group in groupby(text))

itertools.groupby is exactly this problem: it yields consecutive runs of equal items. It handles the empty string (no groups, empty join) and the final run (a group like any other) without special cases — the flush disappears because groupby does it for you.

This is the answer to write at work and the wrong answer here, where the point is the state machine. Note the len(list(group)): group is an iterator that shares its position with the outer one, so it must be consumed before the next group is requested.

Wrong turns worth recognising

Forgetting the final flush. Covered above, and it is the bug this problem exists to teach. Every output is missing its last run.

Omitting the count for runs of one. "abc" → "abc" is the space-saving variant of RLE and is not what is asked. The one character fixed case ("z" → "z1") settles it.

Comparing with the previous character instead of the run character. On this problem they are the same thing, since a run is by definition consecutive — but the run variable is the one that says what you mean, and it survives changes to the grouping rule.

Indexing past the end. Loops written as for i in range(len(text)) with a text[i + 1] lookahead raise IndexError on the last character. Iterating over the characters themselves removes the opportunity.
