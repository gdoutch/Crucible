Balanced Brackets

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Brackets nest, and nesting is last-in-first-out: the bracket you must close next is always the one you opened most recently. A stack models that exactly. Push every opener; on every closer, the thing you pop must be its partner.

This is not a toy correspondence — it is why a stack is the data structure underneath every recursive-descent parser, and why the call stack is called that.

The code

def is_balanced(text):
    """Return True if the brackets in `text` are balanced."""
    closing = {")": "(", "]": "[", "}": "{"}
    stack = []

    for char in text:
        if char in "([{":
            stack.append(char)
        elif char in closing:
            if not stack or stack.pop() != closing[char]:
                return False

    return not stack

The three failure modes, and where each is caught

FailureExampleCaught by
A closer with nothing open) not stack — inside the loop
A closer for the wrong opener(], ([)] stack.pop() != closing[char] — inside the loop
An opener never closed(, ((( return not stack — after the loop

The third one is the one people leave out. A string of nothing but openers never reaches a comparison, so nothing inside the loop can reject it. Ending with return True passes every test except that one.

Short-circuiting is doing real work

if not stack or stack.pop() != closing[char]:

Python's or evaluates its right side only when the left is falsy. So when the stack is empty, stack.pop() is never called — and it must not be, because popping an empty list raises IndexError.

Reverse the two operands and the input ) crashes with IndexError: pop from empty list instead of returning False. Crucible reports that as ERROR with the traceback, which at least points at the line — but the fix is ordering, not a try.

Note also that stack.pop() mutates. It appears once in the condition, which is fine; writing the check as two separate comparisons that each pop would consume two entries per closer.

Why the dict maps closer → opener

{")": "(", "]": "[", "}": "{"} is keyed by the closing bracket, which buys two things from one structure:

  • elif char in closing — the membership test is the "is this a closing bracket?" question, since dict membership checks keys.
  • closing[char] — the opener it demands, ready to compare against whatever was popped.

Mapping the other way (opener → closer) would need a separate way to recognise closers, or a reverse lookup by value.

Walking the interesting case

([)] — the input that defeats counting:

charKindStack beforeWhat happens
(opener[]push → ['(']
[opener['(']push → ['(', '[']
)closer['(', '['] pop gives [, but ) needs ( → False

The counts are perfectly balanced — one of each bracket, openers before closers. Only the stack notices that the [ opened after the ( and so must close before it.

The empty string

The loop never runs, the stack is empty, and not [] is True. Vacuously balanced, no special case. This is the payoff of ending with return not stack rather than a separate check.

Ignoring everything else

The if / elif chain has no else, so any character that is neither an opener nor a closer simply falls through. Letters, spaces, digits — all invisible to the algorithm. That is the specification, and it is also what makes this the skeleton of a real syntax checker, which cares about brackets and hands everything else to another layer.

Cost

O(n) time — one pass, and the push/pop/lookup are all constant time — and O(n) space in the worst case, which is a string of nothing but openers.

The space cannot be improved in general: ((([[[{{{ genuinely requires remembering nine things. If there were only one bracket type, a counter would do — and that is the difference between a regular language and a context-free one, in one example.

Wrong turns worth recognising

return True at the end. Leaves unclosed brackets undetected. The single most common bug in this problem.

Repeatedly removing "()", "[]" and "{}" from the string. It works — keep replacing until nothing changes, then check the string is empty of brackets — and it is O(n²) with a hidden trap: you must ignore the non-bracket characters, which a naive replace chain does not.

Tracking a depth counter per bracket type. Three counters that must all end at zero. It accepts ([)], because it records how many of each are open but not the order they were opened in.
