State Machine From a Diagram

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Turn a picture into a function. Given a state and an event name, return the state the diagram's arrow leads to — or -1 if the diagram draws no arrow for that pair.

Open the diagram first. This problem is comprehension before it is coding.

Count before you write

Five states, six event names: thirty possible pairs. The diagram draws six arrows. So four fifths of your function's behaviour is "no", and only a fifth is "yes".

That ratio should decide the shape of your code. Anything that enumerates the noes is going to be four times longer than it needs to be, and every one of those branches is a place to make a mistake that the diagram cannot help you spot.

A diagram is a table

Every arrow is three facts — where it starts, what it is labelled, where it ends. Six arrows is six rows:

from        event      to
---------   --------   ---------
Draft       submit     Review
Review      reject     Draft
...

Write that table down as data — an array of small structs — and let one loop search it. Then the function has exactly one return -1, at the bottom, meaning "no row matched", and the code can be read side by side with the picture, row against arrow.

This is the habit the problem exists to build. Under review — and under certification — "here is the table, check it against the diagram" is an argument someone can actually complete. "Here are twenty-four nested ifs, convince yourself" is not.

Three things C will trip you on

  • event is a const char *. So event == "submit" compares two pointers and is essentially always false. You want strcmp(event, "submit") == 0 — and note that strcmp returns 0 for equal, so the == 0 is not optional.
  • The enum is shared with the harness. Copy it exactly. The two files are compiled separately and only agree because both declarations say the same thing, so reordering the states silently renumbers them.
  • -1 is the refusal. Not state, not 0. Returning state unchanged looks reasonable and is wrong: DRAFT is 0, so a refusal in Draft would be reported as a successful move to Draft.

The cases that catch people

  • Archived is a dead end. No arrow leaves it, so every event there is refused. If your table has no row starting at Archived, you get this for free.
  • An event name that is not on the diagram at all — frobnicate — is refused like any other unmatched pair. It is not an error and it must not disturb the state.
  • The same event can appear on more than one arrow. There is no arrow labelled submit out of Review, but there is one out of Draft. Matching on the event alone is not enough; the pair is what identifies an arrow.
Still stuck? A bigger nudge 
struct arrow {
    int from;
    const char *event;
    int to;
};

static const struct arrow ARROWS[] = {
    { DRAFT, "submit", REVIEW },
    /* ...the other five, straight off the diagram... */
};

int transition(int state, const char *event)
{
    size_t count = sizeof ARROWS / sizeof ARROWS[0];

    for (size_t i = 0; i < count; i++) {
        if (/* this row's from and event both match */) {
            return ARROWS[i].to;
        }
    }
    return -1;
}

sizeof ARROWS / sizeof ARROWS[0] is the array's length, computed by the compiler. It only works where the array's real type is visible — inside this file, on a real array. Passed to another function it would decay to a pointer and the same expression would quietly give you nonsense.

Check yourself before you press Go

  • No events at all → no output.
  • approve from Draft → REFUSED, and the state is still Draft afterwards.
  • The full happy path reaches Archived.
  • Anything after archive is refused.
  • Count your table's rows. Six?
