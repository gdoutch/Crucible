Trace From a Sequence Diagram

Diagram

The specification. Everything the tests check is on this picture.

sequenceDiagram
    participant Client
    participant OrderService
    participant Inventory
    participant PaymentGateway
    participant Notifier

    Client->>OrderService: place
    OrderService->>Inventory: reserve

    alt out of stock
        Inventory-->>OrderService: unavailable
        OrderService-->>Client: unavailable
    else in stock
        Inventory-->>OrderService: reserved

        loop at most 3 attempts, stopping at the first acceptance
            OrderService->>PaymentGateway: charge
            alt accepted
                PaymentGateway-->>OrderService: accepted
            else declined
                PaymentGateway-->>OrderService: declined
            end
        end

        alt payment accepted
            OrderService->>Notifier: confirm
            OrderService-->>Client: confirmed
        else every attempt declined
            OrderService->>Inventory: release
            OrderService-->>Client: declined
        end
    end

Not drawn? The block above is the diagram's source — the same text that is in the problem statement — and rendering it needs a script this page fetches from a CDN. Offline, read it as text: A->>B: m is a call and A-->>B: m is a return.

Reading the notation

On the diagramMeansYou call
A->>B: m, solid arrowhead A calls B send("A", "B", "m")
A-->>B: m, dashed line A returns to B reply("A", "B", "m")
alt … else … end Exactly one branch runs if / else
loop … end The body repeats while the label's condition holds for with a break

The three shapes the trace can take

Fragments nest, and nesting is scope. Everything from charge onwards sits inside the in stock branch, so a request that cannot be reserved never reaches the gateway — whatever the decline count says.

  1. Out of stock — four messages, and the payment fragment is never entered.
  2. In stock, some attempt accepted — the loop runs once per attempt and stops on the acceptance rather than always going round three times. Then the notifier is told and the client is confirmed.
  3. In stock, all three declined — the loop exhausts its three attempts, the reservation is released, and the client is told it was declined. That release is easy to miss: unwinding a fragment is as much a part of the diagram as entering it.

The one message that is not on the diagram twice

Client->>OrderService: place is the trigger, and you emit it yourself — the harness records what you send and prints it, and does not add anything of its own. The last message of every run is the matching OrderService-->>Client return, whichever branch produced it.
