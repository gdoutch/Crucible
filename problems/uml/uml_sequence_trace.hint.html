Trace From a Sequence Diagram

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Read the diagram top to bottom and emit the messages it would send, in order, for the scenario you are given. Nothing is returned — you call send and reply, and the harness prints what you recorded.

Open the diagram first. There is no puzzle here beyond reading it accurately.

The translation is mechanical

DiagramCode
solid arrow A->>B: m send("A", "B", "m")
dashed arrow A-->>B: m reply("A", "B", "m")
alt / elseif / else
loopfor … break
nestingindentation

That last row is the one to take seriously. A fragment's boundary is a scope. If the diagram draws the payment exchange inside the in stock branch, then your code puts it inside the corresponding if — and a request with nothing in stock never reaches the gateway, whatever the decline count happens to be.

Three things to get right

1. Solid and dashed are different

A call is not a return. They print differently, so mixing them up fails loudly rather than subtly — but it is easy to do when you are transcribing quickly, because the direction of a reply is back the way the call came, and it is tempting to write the participants in the order you read them on the call.

2. The loop stops early

The label says "at most 3 attempts, stopping at the first acceptance". So it is not three iterations; it is up to three. With declines = 0 there is exactly one charge in the trace.

Which means you also need to know, after the loop, how it ended — by acceptance or by exhaustion — because the fragment below the loop branches on that.

3. The unwind is part of the diagram

When all three attempts fail, the reservation made at the top has to be released before the client is told. It is easy to read a diagram for its happy path and miss the arrow that puts things back.

Python's for has an else clause that runs only if the loop finished without a break — which is exactly "the loop exhausted its attempts". It is an option, though a plain flag is clearer to most readers.

Work out one trace by hand first

Take in_stock = True, declines = 1 and write down the messages on paper before you write any code. You should get nine, and the fourth and sixth should both be charge. If your count differs, the mistake is in your reading of the diagram and no amount of coding will fix it.

Still stuck? A bigger nudge 
def place_order(send, reply, in_stock, declines):
    send("Client", "OrderService", "place")
    send("OrderService", "Inventory", "reserve")

    if not in_stock:
        # two messages, then nothing else happens at all
        return

    reply("Inventory", "OrderService", "reserved")

    accepted = False
    for attempt in range(3):
        send("OrderService", "PaymentGateway", "charge")
        if attempt < declines:
            ...        # declined; go round again
        else:
            ...        # accepted; record it and stop
            break

    if accepted:
        ...
    else:
        ...

attempt < declines is the whole of the gateway's behaviour: attempts 0 .. declines-1 are declined and the next one is accepted. With declines = 3 that condition is true for all three attempts, the break never runs, and accepted is still False at the bottom.

Check yourself before you press Go

  • no 0 and no 3 produce identical output — four lines.
  • yes 0 has exactly one charge.
  • yes 3 has three charge lines and a release.
  • Every trace ends with a message to Client.
  • Participant names spelled exactly as the diagram spells them — PaymentGateway, one word.
