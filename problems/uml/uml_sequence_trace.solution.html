Trace From a Sequence Diagram

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Walk the diagram from top to bottom. Each arrow is one call; each fragment is one control structure; nesting on the page is nesting in the code. Done faithfully, the function ends up looking like the picture rotated ninety degrees.

The code

def place_order(send, reply, in_stock, declines):
    """Walk the diagram top to bottom, one fragment at a time."""
    send("Client", "OrderService", "place")
    send("OrderService", "Inventory", "reserve")

    if not in_stock:
        reply("Inventory", "OrderService", "unavailable")
        reply("OrderService", "Client", "unavailable")
        return

    reply("Inventory", "OrderService", "reserved")

    accepted = False
    for attempt in range(3):
        send("OrderService", "PaymentGateway", "charge")
        if attempt < declines:
            reply("PaymentGateway", "OrderService", "declined")
        else:
            reply("PaymentGateway", "OrderService", "accepted")
            accepted = True
            break

    if accepted:
        send("OrderService", "Notifier", "confirm")
        reply("OrderService", "Client", "confirmed")
    else:
        send("OrderService", "Inventory", "release")
        reply("OrderService", "Client", "declined")

Fragment by fragment

The two messages above every fragment

place and reserve are outside the outer alt, so they happen on every path. Every one of the eight scenarios starts with the same two lines.

The outer alt, and the early return

The out-of-stock branch is handled first and returns, which is a flattening of the diagram rather than a change to it — the alternative is to put the entire rest of the function inside an else and indent it. Both are faithful; the early return keeps the nesting shallow enough to read.

This is where the out of stock, declines ignored test bites. The gateway sits inside the in-stock branch, so no 3 must produce exactly what no 0 produces. A solution that reads the diagram as a flat list of messages and gates each one separately gets a spurious charge here.

The loop, and why it is not three iterations

The label reads "at most 3 attempts, stopping at the first acceptance", so the loop needs both a bound and an exit. range(3) is the bound; break is the exit.

attempt < declines is the gateway's whole behaviour. Attempts 0 to declines - 1 are declined and the next one succeeds:

declinesAttempts madeOutcome
01accepted on the first
12accepted on the second
23accepted on the third
33never accepted — the loop exhausts

When declines is 3 the condition is true for 0, 1 and 2, the break never runs, and accepted is still False below. That single comparison covers all four columns without a special case.

The flag

accepted exists because the fragment below the loop branches on how the loop ended, and Python does not otherwise tell you. The idiomatic alternative is for … else:

for attempt in range(3):
    send("OrderService", "PaymentGateway", "charge")
    if attempt >= declines:
        reply("PaymentGateway", "OrderService", "accepted")
        break
    reply("PaymentGateway", "OrderService", "declined")
else:
    send("OrderService", "Inventory", "release")
    reply("OrderService", "Client", "declined")
    return

send("OrderService", "Notifier", "confirm")
reply("OrderService", "Client", "confirmed")

The else runs only when the loop was not broken out of, which is exactly "no attempt was accepted". It is shorter and it is a construct many readers have to stop and remember. The flag is the better answer in code someone else maintains.

The unwind

release is the arrow that puts back what reserve took. Missing it is the most common error on this problem, because a diagram read for its happy path does not draw attention to the branch that cleans up.

In real systems that arrow is the difference between a failed checkout and stock that is reserved forever. It is worth noticing that the diagram tells you about the bug — the information was there to be read.

Why the harness owns send and reply

They are passed in rather than imported, so your file has no say in what a message looks like or where it goes. That is the same arrangement as the harness owning main in the C problems: the thing being observed cannot alter the observation.

It also makes the exercise about the order of the calls and nothing else — no formatting to get wrong, no output to buffer.

Cost

O(1). At most eleven messages, whatever the input. Worth saying because it makes the point that this problem has no algorithm in it at all: the entire difficulty is reading the specification correctly, which is true of a great deal of real work.

Wrong turns worth recognising

Always running three attempts. range(3) with no break produces three charge lines even when the first is accepted. The loop's label is part of the specification.

Charging when out of stock. Reading the diagram as a checklist rather than a nesting. The two no cases exist to catch exactly this.

Using send for the returns. The dashed arrows are replies. Six of the eleven possible messages are dashed, so this shows up immediately — but it is worth knowing the distinction is real: a return belongs to the call that caused it, and drawing it as a call implies an independent message the receiver has to be prepared for.

Emitting the reply from the wrong end. Inventory --> OrderService: reserved flows from Inventory back to OrderService — the reverse of the call that provoked it. Copying the participant order from the call line gets it backwards.
