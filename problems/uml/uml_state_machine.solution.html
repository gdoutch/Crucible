State Machine From a Diagram

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Transcribe the diagram as data, then write one loop that searches it. Six arrows become six rows; every pair that matches no row is a refusal. The code ends up structurally identical to the picture, which is the property worth having — you can check it arrow by arrow, and so can a reviewer.

The code

#include <stddef.h>
#include <string.h>

enum doc_state { DRAFT, REVIEW, APPROVED, PUBLISHED, ARCHIVED };

struct arrow {
    int from;
    const char *event;
    int to;
};

/* One row per arrow on the diagram, in the order the diagram draws them. */
static const struct arrow ARROWS[] = {
    { DRAFT,     "submit",  REVIEW    },
    { REVIEW,    "reject",  DRAFT     },
    { REVIEW,    "approve", APPROVED  },
    { APPROVED,  "revise",  DRAFT     },
    { APPROVED,  "publish", PUBLISHED },
    { PUBLISHED, "archive", ARCHIVED  },
};

int transition(int state, const char *event)
{
    size_t count = sizeof ARROWS / sizeof ARROWS[0];

    for (size_t i = 0; i < count; i++) {
        if (ARROWS[i].from == state
            && strcmp(ARROWS[i].event, event) == 0) {
            return ARROWS[i].to;
        }
    }
    return -1;
}

Why the table is the answer and not just an answer

The if-chain version works. It is also longer, and it has a property the table does not:

if (state == DRAFT && strcmp(event, "submit") == 0)   return REVIEW;
if (state == REVIEW && strcmp(event, "reject") == 0)  return DRAFT;
/* ... */
return -1;

Nothing stops a seventh line appearing that no arrow authorises, and nothing makes the omission of a sixth visible. With the table, the reviewer's job is to count rows and read three columns. That is a check someone can actually finish, and finishing it is the difference between a review and a glance.

The same argument scales. A production state machine is often a two-dimensional array indexed by [state][event], generated from the model rather than typed. The reason is identical: the artefact under review should have the same shape as the specification.

The refusal is the default, not a case

Thirty state–event pairs; six arrows. The single return -1 after the loop covers all twenty-four of the rest — including combinations nobody enumerated and combinations that do not exist, like frobnicate.

That is a real safety property in miniature: an unlisted input takes the refusing path rather than an undefined one. The alternative shape, where each refusal is written out, fails open the moment someone adds a state and forgets a row.

Archived costs nothing

The diagram draws Archived --> [*] and nothing else. There is no row in the table whose from is ARCHIVED, so every lookup from there falls through to -1. The terminal state needed no code, because "no outgoing arrows" is exactly "no rows".

The C details

strcmp, and its return value

event == "submit" compares a pointer with the address of a string literal. It is legal C, it compiles without a warning on most settings, and it is false for every input the harness can produce. strcmp returns zero when the strings are equal — it answers "how do these order", not "are these the same" — so the == 0 is load-bearing. Dropping it inverts the test.

The array-length idiom

sizeof ARROWS / sizeof ARROWS[0] is the total byte size divided by the size of one element, computed at compile time. It is safe here because ARROWS is a real array in scope. Pass an array to a function and the parameter is a pointer, where the same expression silently becomes "pointer size divided by element size" — usually 8/16, so 0. That is why the count is computed here and not somewhere else.

Sharing the enum

Your file and the harness are separate translation units. They agree that APPROVED is 2 only because both declare the same enum in the same order — the same arrangement as struct node in Reverse a Linked List. Reorder your copy and the code compiles, links, and prints the wrong state names.

The harness appends STATE_COUNT to its copy, which does not disturb the other five values because it comes last. It uses it to bounds-check what you return, so a nonsense state is reported as INVALID rather than read off the end of the name table.

Cost

O(rows) per event — six string comparisons at worst, which for a diagram this size is not worth improving. A machine with hundreds of transitions would index a [state][event] array after mapping the event name to an integer once, turning the lookup into O(1). The shape of the answer would not change; only the search would.

Wrong turns worth recognising

Returning state on a refusal. It reads as "stay where you are", which is what the machine does — but the harness cannot then tell a refusal from a self-transition, and it prints Draft where REFUSED belongs. Worse, the diagram has no self-transitions at all, so the two are genuinely different facts.

Switching on the event first. A switch over event names with a nested check on the state works, and it is organised against the wrong axis: the diagram is drawn as states with arrows leaving them, so a reader comparing the two has to transpose it in their head.

Reading the arrows backwards. Approved --> Draft: revise means from Approved to Draft. It is the one arrow on the diagram that points back up the page, and it is the one most often entered the wrong way round.
