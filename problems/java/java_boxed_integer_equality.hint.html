Comparing Boxed Integers Without ==

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

Compare values, not references

int count = 0;
for (int i = 0; i < values.size(); i++) {
    for (int j = i + 1; j < values.size(); j++) {
        if (values.get(i).equals(values.get(j))) {
            count++;
        }
    }
}
return count;

Why a small-number test would not have caught this

`values.get(i) == values.get(j)` compiles -- `Integer` is a reference type, and `==` between two references is always legal, it just means "same object", not "same value". The trap is that it also often *looks* correct: the JLS requires `Integer.valueOf` to cache and reuse a single object for every value from `-128` to `127`, so two `Integer`s in that range holding equal values genuinely are the same object, and `==` correctly returns `true` by coincidence. Outside that range, autoboxing is free to (and typically does) create a fresh `Integer` object every time, so two boxed `1000`s are two different objects with equal values -- and `==` between them is `false`.

`.equals()` compares the actual `int` values stored inside, regardless of whether the two `Integer` objects happen to be the same instance or not -- there is no range where it needs help from anything else.
