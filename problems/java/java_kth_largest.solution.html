Kth Largest With a Bounded Min-Heap

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

import java.util.PriorityQueue;

public class Solution {
    public static int kthLargest(int[] values, int k) {
        PriorityQueue<Integer> heap = new PriorityQueue<>();
        for (int v : values) {
            heap.offer(v);
            if (heap.size() > k) {
                heap.poll();
            }
        }
        return heap.peek();
    }
}

Why a min-heap, capped at size k, finds the k-th *largest*

After processing the whole array this way, the heap holds exactly the `k` largest values seen -- every time a value would have pushed the heap past size `k`, the current smallest member of the heap was evicted, which only ever removes a value that is not larger than everything else currently kept. What remains, `k` elements deep, is the top-`k` by construction. The smallest element *among those k* -- which is exactly what `heap.peek()` reports, because the heap is ordered smallest-first -- is by definition the k-th largest of the whole array: there are exactly `k - 1` elements in the heap larger than it (or equal, for ties), and everything evicted along the way was smaller than or equal to something that made the final cut.

Why the eviction check is `> k`, not `>= k`

The heap needs to *reach* size `k` before evicting anything, not stop one short of it. `heap.size() > k` only trips once the heap has grown to `k + 1` -- meaning it had already spent one iteration holding exactly `k` elements -- so the very next eviction brings it right back to `k`. `>= k` would start evicting as soon as the heap first reaches size `k`, before that k-th element has had a chance to actually be part of the "currently held" set, and the heap would never settle at holding the intended `k` values.

Why `peek()`, not iterating the heap directly

A `PriorityQueue`'s internal array satisfies the heap property (each parent is `<=` its children) but is not fully sorted -- iterating it with a `for`-each, or converting it to a `List`, visits elements in whatever order the internal array happens to hold them, which is not sorted order beyond the very first element. `peek()` is guaranteed to return the minimum specifically, which is the one element this function actually needs to read.

Cost

O(n log k) in the length of `values` -- each of the n elements does one `offer` and, past the first `k`, one `poll`, both O(log k) on a heap bounded at size `k` rather than size n.
