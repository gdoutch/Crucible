A Stack That Tracks Its Own Minimum

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

import java.util.ArrayDeque;
import java.util.Deque;

public class Solution {
    private Deque<Integer> values = new ArrayDeque<>();
    private Deque<Integer> mins = new ArrayDeque<>();

    public void push(int value) {
        values.push(value);
        if (mins.isEmpty() || value <= mins.peek()) {
            mins.push(value);
        }
    }

    public void pop() {
        int removed = values.pop();
        if (!mins.isEmpty() && removed == mins.peek()) {
            mins.pop();
        }
    }

    public int top() {
        return values.peek();
    }

    public int getMin() {
        return mins.peek();
    }
}

Why the tie check has to be `<=`

`mins` is not "the history of every distinct minimum" -- it is "one entry for every value on `values` that is currently tied for the minimum", which is what lets `pop()` decide correctly whether removing the top of `values` should also affect `mins`. Pushing `2` when `2` is already the minimum has to add a *second* `2` onto `mins`, specifically so that popping one of the two `2`s off `values` only removes one of the two matching entries on `mins`, leaving the other to correctly report `2` as still the minimum. Using `<` instead of `<=` treats the second `2` as "not a new minimum" and skips recording it -- so `mins` ends up under-counting how many copies of the current minimum are actually on the stack, and a single `pop()` can remove `mins`'s only remaining record of a value that is still present on `values`.

Why `pop()` checks equality before touching `mins`

Only a value that is *currently* the minimum has any entry on `mins` to remove. `removed == mins.peek()` is precisely that check: if the value coming off `values` matches what `mins` currently reports as the minimum, one matching entry comes off `mins` too, keeping the two stacks in exact step; if the removed value was never the minimum, `mins` was never tracking it in the first place; and popping it unconditionally instead would desynchronise the two stacks the first time a non-minimum value is removed.

Why `getMin()` and `top()` are both simple `peek()`s

Because `mins.peek()` is always kept equal to the true minimum of whatever is currently on `values` -- by construction, at every push and every pop -- reading it is a plain O(1) lookup with no scanning involved. `top()` reads `values.peek()` the same way, for the same reason: both stacks are always accurate as of the most recent operation, never recomputed lazily.

Cost

O(1) for every one of `push`, `pop`, `top` and `getMin` -- each does a bounded number of `Deque` operations, none of which scan the stack's contents.
