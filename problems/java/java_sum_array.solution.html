Sum an Array Without Overflowing

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

public class Solution {
    public static long sumArray(int[] values) {
        long total = 0;
        for (int v : values) {
            total += v;
        }
        return total;
    }
}

Why `total` is `long` from its very first line

`total += v` runs once per element, and every one of those additions happens in whatever type `total` was declared as. If that type is `int`, each addition is 32-bit -- and unlike some other languages, Java has no "checked" mode to opt into for `int` arithmetic at all: overflow always wraps silently, for `+` exactly as much as for anything else. By the time a later `(long) total` would try to widen the result, the wrong value has already been computed and stored -- there is nothing left to recover. Declaring `long total = 0;` up front means every addition is a 64-bit addition from the start, with roughly nine quintillion of headroom rather than about two billion -- comfortably enough for any sum this function could realistically be asked to produce.

Why `int v` inside the loop is not itself a problem

Each individual `values[i]` genuinely does fit in an `int` -- the problem is only ever the running *total* of many of them, never a single element. Reading each element as `int` and immediately widening it during the `+=` into the already-`long` `total` is correct and exactly what happens here; there is no need to declare the loop variable itself as `long`.

Why an empty array needs no special case

`total` starts at `0`, and a `for`-each loop over an empty array simply never executes its body -- the function returns `0` without an explicit check, which is exactly what the sum of nothing should be.

Cost

O(n) in the length of `values` -- one pass, one addition per element, no allocation.
