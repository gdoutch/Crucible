Balanced Brackets With an ArrayDeque

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

import java.util.ArrayDeque;
import java.util.Deque;

public class Solution {
    public static boolean isBalanced(String text) {
        Deque<Character> openBrackets = new ArrayDeque<>();
        for (char c : text.toCharArray()) {
            if (c == '(' || c == '[' || c == '{') {
                openBrackets.push(c);
            } else if (c == ')' || c == ']' || c == '}') {
                if (openBrackets.isEmpty()) {
                    return false;
                }
                char top = openBrackets.pop();
                if ((c == ')' && top != '(') ||
                    (c == ']' && top != '[') ||
                    (c == '}' && top != '{')) {
                    return false;
                }
            }
        }
        return openBrackets.isEmpty();
    }
}

Why `Deque`, not `java.util.Stack`

`Stack` is one of the original, pre-collections-framework classes -- it extends `Vector`, which means every operation (including ones this function never needs, like random-access indexing) inherits `Vector`'s synchronization overhead, paid on every single call regardless of whether more than one thread is ever involved. `Deque`, implemented here by `ArrayDeque`, provides the same `push`/`pop`/`peek` stack operations with none of that overhead, which is exactly why the JDK's own documentation for `Stack` recommends `Deque` for new code. Nothing about the algorithm changes between the two -- only which class provides it.

Why the empty check comes before `pop()`

`ArrayDeque.pop()` and `.peek()` throw `NoSuchElementException` on an empty deque -- a genuine, documented, catchable exception, unlike some other languages' equivalent operations, but still not something this function is allowed to let escape: its contract is to *return* `false` for a closing bracket with nothing open to match, not to throw. Checking `openBrackets.isEmpty()` first is what turns "there is nothing to pop" into a normal `false` return instead of a thrown exception.

Why the final check is on the deque, not on anything seen while scanning

`"(()"` never encounters a closing bracket that disagrees with what is open -- there simply are not enough closing brackets to reach the point of disagreement. Nothing about scanning left to right ever notices that; the only place it shows up is that the deque still has an unclosed `'('` on it once `text` runs out. That is exactly what `return openBrackets.isEmpty();` checks: not "did I ever see a mismatch", but "is there anything still waiting to be closed".

Cost

O(n) in the length of `text` -- each character is looked at once, and each bracket does at most one push or one pop.
