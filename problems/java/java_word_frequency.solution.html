Word Frequency Without a Null Pointer Exception

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

import java.util.Map;
import java.util.Scanner;
import java.util.TreeMap;

public class Solution {
    public static Map<String, Integer> wordFrequency(String text) {
        Map<String, Integer> counts = new TreeMap<>();
        Scanner scanner = new Scanner(text);
        while (scanner.hasNext()) {
            String word = scanner.next();
            counts.put(word, counts.getOrDefault(word, 0) + 1);
        }
        return counts;
    }
}

Why `get` throws and `getOrDefault` does not

`Map<String, Integer>.get(key)` returns `Integer` -- a reference type -- and its documented behaviour for a missing key is to return `null`, not to throw anything itself. The exception happens one step later, at the point something tries to *use* that `null` as a number: `null + 1` requires unboxing the `Integer` to a primitive `int` to perform the addition, and there is no `int` value that `null` could correctly unbox to, so the unboxing itself throws `NullPointerException`. `getOrDefault(key, default)` sidesteps this entirely by returning the supplied default -- a genuine, already-primitive- compatible `0` -- whenever the key is absent, so the addition that follows never has a `null` to contend with regardless of whether `word` is new or already counted.

Why `Map.merge` would also work

`counts.merge(word, 1, Integer::sum)` is the same idea expressed differently: insert `1` if `word` is not present, otherwise combine the existing value and `1` using the given function (`Integer::sum` here). Either `getOrDefault` or `merge` avoids ever calling `get` on its own and trusting the result to be non-null -- the common thread is that both provide their own fallback for a missing key, rather than assuming presence.

Why the words come out sorted

`TreeMap` keeps its keys in their natural ordering (ascending, for `String`) -- iterating it, the way the harness that calls this function does to print the result, visits keys lexicographically without this function needing to sort anything itself. A `HashMap` would have made no such promise.

Cost

O(n log k) where n is the number of words in `text` and k the number of distinct ones -- each `TreeMap` access (`getOrDefault` plus `put`) is an O(log k) tree operation.
