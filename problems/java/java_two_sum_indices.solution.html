Two Sum, Indices, in One Pass

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

import java.util.HashMap;
import java.util.Map;

public class Solution {
    public static int[] twoSumIndices(int[] values, int target) {
        Map<Integer, Integer> seen = new HashMap<>();
        for (int i = 0; i < values.length; i++) {
            int complement = target - values[i];
            if (seen.containsKey(complement)) {
                return new int[] { seen.get(complement), i };
            }
            seen.put(values[i], i);
        }
        return new int[] { -1, -1 };
    }
}

Why the map is checked before the current element is recorded

Reversing the two lines -- `seen.put(values[i], i);` first, the `containsKey` check second -- introduces exactly one bug, but it is a specific and easy-to-miss one: when `target == 2 * values[i]`, the complement being searched for is `values[i]` itself, and if it was just inserted into the map on this same iteration, the lookup finds it, reporting `{ i, i }` -- one element "paired" with itself, not two distinct elements. Checking first means `seen` only ever holds indices from iterations that have already completed, so any match it returns is guaranteed to be a genuinely different, earlier index.

Why the returned pair is already in `{ smaller, larger }` order

Because the map is only ever queried for a complement *before* the current index is added, any hit it returns necessarily came from some earlier iteration -- `seen.get(complement)` is always `< i`. The pair `{ seen.get(complement), i }` is therefore already ordered correctly with no comparison needed to sort the two indices afterward.

Why repeated values need no special handling

`seen.put(values[i], i)` overwrites any earlier index already stored for that same value with the more recent one -- which is fine, because either index is a valid "earlier occurrence" for anything that matches it going forward. Nothing about a value appearing more than once needs to be detected or handled separately; the map's own put-overwrites-existing behaviour already does the right thing.

Cost

O(n) in the length of `values` -- one hash-map lookup and one insert per element, both O(1) average.
