Comparing Boxed Integers Without ==

Worked solution

This page contains the complete answer and explains why each part of it is there.

The code

import java.util.List;

public class Solution {
    public static int countEqualPairs(List<Integer> values) {
        int count = 0;
        for (int i = 0; i < values.size(); i++) {
            for (int j = i + 1; j < values.size(); j++) {
                if (values.get(i).equals(values.get(j))) {
                    count++;
                }
            }
        }
        return count;
    }
}

Why `==` is sometimes right and sometimes wrong for the exact same code

`Integer.valueOf(int)` -- what autoboxing calls under the hood for `Integer i = 5;` and the like -- is required, by the Java Language Specification itself, to return the *same* cached `Integer` instance for every value in `-128..127`. That is not an implementation detail that happens to hold on one JVM; it is a guarantee every conformant JVM must honour. Two `Integer`s both holding `5`, both produced by autoboxing, are therefore guaranteed to be `==` to each other -- reference equality and value equality coincide, for that range, by specification. Outside `-128..127`, the JLS makes no such promise: `Integer.valueOf` is free to allocate a new object every time (and in practice, it does), so two `Integer`s holding the same large value are ordinary, distinct objects with no reason to be `==`. The bug in a `==`-based solution is not that it is "sometimes flaky" -- it is entirely deterministic, and entirely a function of whether the values involved happen to fall inside or outside one specific, documented range.

Why `.equals()` has no such range to worry about

`Integer.equals(Object)` is implemented to compare the wrapped `int` values directly, with no reference to which object either `Integer` happens to be. Two `Integer`s holding equal values are `.equals()` to each other whether they are the same cached object, two separately allocated objects, or anything else -- there is no boundary anywhere in `int`'s range where the answer could change based on identity.

The alternative: unboxing before comparing

values.get(i).intValue() == values.get(j).intValue() also works, for a related reason: `intValue()` returns a primitive `int`, and primitive `==` in Java has only ever meant "these two numbers are equal" -- there is no such thing as reference identity for a primitive. The trap is specific to `==` between two *references*, not to the `==` operator in general.

Cost

O(n²) in the length of `values` -- every pair of indices is checked once. A hash-based count (grouping by value first) could do this in O(n), but the point of this exercise is the comparison itself, not the algorithm around it.
