4-bit Adder With Carry

Worked solution

This page contains the complete answer and explains why each part of it is there.

The whole thing

library ieee;
use ieee.std_logic_1164.all;
use ieee.numeric_std.all;

entity solution is
    port (
        a    : in  std_logic_vector(3 downto 0);
        b    : in  std_logic_vector(3 downto 0);
        cin  : in  std_logic;
        sum  : out std_logic_vector(3 downto 0);
        cout : out std_logic
    );
end entity solution;

architecture rtl of solution is
    signal wide : unsigned(4 downto 0);
begin
    wide <= resize(unsigned(a), 5) + resize(unsigned(b), 5) + cin;
    sum  <= std_logic_vector(wide(3 downto 0));
    cout <= wide(4);
end architecture rtl;

One internal signal, one addition, two ways of reading the answer back out of it.

Walking it through

Take a = "1111" (15), b = "0001" (1), cin = '0':

stepvalue
resize(unsigned(a), 5)01111
resize(unsigned(b), 5)00001
sum, as a 5-bit unsigned10000 (16)
wide(3 downto 0) → sum0000
wide(4) → cout1

Output "00001" -- confirmed against a real GHDL run for exactly this input.

Why five bits, not four

Four bits can represent 0 through 15. The largest possible result here -- 15 + 15 + 1 = 31 -- needs five. resize(unsigned(a), 5) pads a 4-bit unsigned value out to five bits by adding zeros above the existing ones, which changes nothing about what number it represents; it just gives the addition somewhere to put a result larger than either operand alone. Add two 5-bit values (plus a 1-bit cin, which numeric_std aligns at the low end for free) and the sum itself is exactly wide enough for every possible answer, 0 through 31, to fit without wrapping.

wide(3 downto 0) is then sum -- the low four bits, which is also exactly what a plain 4-bit addition would have given, wrapped. wide(4), the one bit a 4-bit addition had nowhere to put, is cout.

The trap: computing sum and cout from two different widths

unsigned(a) + unsigned(b), kept at 4 bits, gives the right sum and no way to get cout. 4-bit wraparound and 4-bit truncation are the same operation, so the low four bits of a 4-bit addition already equal the low four bits of the correct 31-bit-safe answer -- sum alone would look right in every test. It is cout that has nowhere to come from: the information "did this overflow" was thrown away the moment the addition happened at 4 bits, and no amount of inspecting the 4-bit result afterwards gets it back. A submission that computes sum this way and ties cout to '0' passes every case that does not overflow and fails every one that does.

cin is part of the same sum, not an afterthought

7 + 8 is 15, which fits -- but 7 + 8 + 1 is 16, which does not. If cin is added to an already-truncated 4-bit sum after the fact, rather than folded into the same 5-bit addition as a and b, this exact case comes out wrong: the truncation has already happened by the time cin gets a chance to push the total over 15.

Cost

O(n) gate delay in the width of the operands -- a real ripple-carry adder's carry genuinely does propagate bit by bit, which is the "ripple" in the name and the reason wider adders use a carry-lookahead structure instead. At 4 bits the difference is not worth building; numeric_std's "+" already describes whichever adder structure the synthesis tool judges best for the target.
