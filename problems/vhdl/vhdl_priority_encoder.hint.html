4-bit Priority Encoder

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Not "which bits are set" -- which one, by a fixed ranking: bit 3 outranks bit 2 outranks bit 1 outranks bit 0. Whichever of those is the highest set bit is the whole answer; every lower set bit is ignored for the purpose of index, though it still counts towards valid.

The shape of it

A priority chain like this reads naturally as a ladder, checked from the top down:

if data(3) = '1' then
    -- bit 3 wins
elsif data(2) = '1' then
    -- bit 2 wins, since bit 3 did not
elsif data(1) = '1' then
    -- ...
elsif data(0) = '1' then
    -- ...
???
end if;

Four conditions, checked in priority order, each one only reached because every condition above it was false.

The trap: what happens after the last elsif

All four conditions can be false at once -- when data = "0000" -- and an if/elsif ladder with nothing after the last elsif simply does nothing for that case. The design still elaborates. It still runs. It just never assigns index or valid for that one input, and "never assigned" is not the same as "assigned zero" -- ask GHDL what an output nothing ever drove reads as, and the honest answer is 'U', not '0'.

The fix is a final else, with its own explicit values for both outputs -- index is specified to read "00" here, not left as "don't care", so there is one correct answer to match rather than an genuinely unconstrained one.

Check yourself before you press Go

  • 0000 → 000. The case every branch above falls through to -- try this one first, since it is the one a missing else gets wrong while every other case still looks fine.
  • 0110 → 101. Bits 1 and 2 are both set; the answer is 2's index, not 1's -- the lower bit does not get ignored entirely, it just loses the tie for index.
  • 1111 → 111. Every bit set, and only the top one's priority shows up in the answer.
