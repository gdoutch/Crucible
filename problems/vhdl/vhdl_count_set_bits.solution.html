Count Set Bits

Worked solution

This page contains the complete answer and explains why each part of it is there.

The whole thing

library ieee;
use ieee.std_logic_1164.all;
use ieee.numeric_std.all;

entity solution is
    port (
        value : in  std_logic_vector(7 downto 0);
        count : out std_logic_vector(3 downto 0)
    );
end entity solution;

architecture rtl of solution is
begin
    process (value)
        variable total : integer range 0 to 8;
    begin
        total := 0;
        for i in value'range loop
            if value(i) = '1' then
                total := total + 1;
            end if;
        end loop;
        count <= std_logic_vector(to_unsigned(total, count'length));
    end process;
end architecture rtl;

One process, sensitive to value alone, so it re-evaluates exactly when there is something new to look at and never depends on simulation time beyond that.

Walking it through

Take value = "10110000" — bits 7, 5 and 4 are set:

value'range is 7 downto 0 because that is how the port itself is declared — the loop walks the bits in that order, but addition does not care about order, so it would give the same total counting the other way too.

Why a variable, not a signal

total is a process variable: it updates the instant the assignment runs, so the loop can read back what it just added on the very next iteration. A signal only takes its new value at the end of the process (or after a wait), so a running total kept in a signal would still be reading last cycle's count on every iteration but the first — the classic signal-vs-variable trap, and exactly why an accumulator inside a loop is one of the few places VHDL style actively prefers a variable.

Turning a count back into count

total is a plain integer; the port is a std_logic_vector. to_unsigned(total, count'length) — from ieee.numeric_std — produces an unsigned of exactly the target width, and std_logic_vector(...) is the ordinary type conversion (not a function call — unsigned and std_logic_vector are both arrays of std_logic underneath) that lands it on the port. count'length rather than a hand-typed 4 means this line does not need to change if the port ever did.

The trap: a latch by omission

Every path through the process assigns count exactly once. The loop always runs to completion and the assignment sits after it unconditionally, so there is no way to reach the end of the process without a fresh value having been computed. An earlier draft that instead did if total > 0 then count <= ...; end if;, with nothing for the total = 0 case, would leave count holding whatever it last held on that input — right by accident the first time a test runs zero through it, from the testbench's own signal initial value being (others => '0'), and wrong the moment two all-zero-ish cases run back to back with something nonzero in between.

The alternative without a loop

Concurrent, no process at all — each bit is widened to a one-bit unsigned and the eight are added as numbers:

count <= std_logic_vector(resize(
    unsigned'(("0000000" & value(7))) +
    ("0000000" & value(6)) + ("0000000" & value(5)) + ("0000000" & value(4)) +
    ("0000000" & value(3)) + ("0000000" & value(2)) + ("0000000" & value(1)) +
    ("0000000" & value(0)),
    count'length));

Uglier to read and no different once synthesised — a synthesis tool turns the loop version into the same adder tree. The loop earns its place here because it says what is meant instead of how the adders happen to be arranged.

Cost

As hardware: an 8-input adder tree, O(log n) gate delay in the width of the input rather than O(n) — nothing here runs one bit at a time the way a software loop would. The VHDL for loop only looks sequential; it unrolls into eight parallel terms at elaboration, not eight clock cycles.

A wrong turn worth recognising

Reaching for a clock that was never offered. A process with clk in its sensitivity list, or a wait until rising_edge(clk), has nothing to synchronise with here — the testbench drives value once and waits a fixed 1 ns, no clock signal exists on either side of the port map, and a clocked description will simply never produce a result in time. This problem is deliberately scoped to combinational logic; a sequential version of the same idea would need a testbench that drives a real waveform over several cycles per test case, which is a different kind of problem from this one.
