4-bit Adder With Carry

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Ordinary addition, plus one extra output that only ever matters some of the time: cout is '1' exactly when a + b + cin needed a fifth bit that a 4-bit sum does not have room for.

Getting from bits to arithmetic

a and b arrive as std_logic_vector, which has no "+" of its own. ieee.numeric_std is where addition lives for these types -- convert with unsigned(...), add, convert back with std_logic_vector(...) for the parts that leave through a std_logic_vector port.

The trap: where does the extra bit go?

unsigned(a) + unsigned(b), both declared 4 bits wide, gives back a 4-bit answer -- numeric_std does not grow the result to fit; it wraps, the same way the real 4-bit register this describes would. For an input like 15 + 1, wrapped-to-4-bits is 0, which is in fact the correct sum -- 16 truncated to 4 bits really is 0. The problem is that the bit which made it 16 rather than 0 is now gone. Nothing left in a 4-bit value can tell you afterwards whether a carry happened.

The fix is ordering: get the answer somewhere wide enough to still hold the carry before anything gets truncated down to 4 bits for sum. resize(unsigned(a), 5) pads a 4-bit unsigned value out to 5 bits (with zeros, since it is unsigned) without changing what number it represents -- do that to both operands before adding, and the top bit of a 5-bit result is exactly the carry you are looking for.

Check yourself before you press Go

  • 0111 0001 0 (7 + 1) → 10000: sum 1000, cout = 0. Fits.
  • 1111 0001 0 (15 + 1) → 00001: sum wraps to 0000, and cout = 1 is the only place the 16 shows up. A solution with cout tied to '0' gets the case above right and this one wrong.
  • 0111 1000 1 (7 + 8, plus cin) → also 00001: neither operand alone overflows, but cin tips it over 15. cin has to be part of the same widened sum, not added on afterwards.
