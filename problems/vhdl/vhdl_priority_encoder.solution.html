4-bit Priority Encoder

Worked solution

This page contains the complete answer and explains why each part of it is there.

The whole thing

library ieee;
use ieee.std_logic_1164.all;

entity solution is
    port (
        data  : in  std_logic_vector(3 downto 0);
        index : out std_logic_vector(1 downto 0);
        valid : out std_logic
    );
end entity solution;

architecture rtl of solution is
begin
    process (data)
    begin
        if data(3) = '1' then
            index <= "11";
            valid <= '1';
        elsif data(2) = '1' then
            index <= "10";
            valid <= '1';
        elsif data(1) = '1' then
            index <= "01";
            valid <= '1';
        elsif data(0) = '1' then
            index <= "00";
            valid <= '1';
        else
            index <= "00";
            valid <= '0';
        end if;
    end process;
end architecture rtl;

Five branches for four bits -- one per bit, in priority order, plus the branch that catches every condition failing at once.

Walking it through

Take data = "0110" -- bits 1 and 2 are set, bit 3 is not:

conditiondata(3)='1'?data(2)='1'?taken?
if data(3)false--no, fall through
elsif data(2)--trueyes

The process stops at the first true condition -- data(1) and data(0) are never even inspected once data(2) matches. index <= "10", valid <= '1', output "101" -- confirmed against a real GHDL run for exactly this input.

Why a chain and not, say, a case

A case data is statement would need one choice per possible 4-bit pattern -- sixteen of them, or ranges of them -- because case picks exactly one branch by matching the whole value, with no notion of "this bit outranks that one". The if/elsif ladder is a better fit precisely because priority is the ordering of the conditions: checking data(3) first and returning immediately if it is set is what "bit 3 outranks everything else" means as code.

The trap: the branch that is easy to never write

Four elsifs cover four bits being set. Nothing covers none of them being set, unless something explicitly does. Delete the final else here and the design still elaborates, still runs, and gets every case with at least one bit set exactly right -- because those cases were never the problem. data = "0000" is the one input that reaches the end of the ladder with every condition false, and with no else to catch it, index and valid simply never get driven for that case. GHDL's answer for a signal nothing ever assigned is 'U' -- not '0', not silence, an actual reportable value meaning "undefined" -- and std_logic_textio.write prints it exactly as honestly as it prints a '0' or a '1': the output comes out "UUU".

This is the same shape of bug as leaving one path through an if without an assignment in Count Set Bits -- a real synthesis tool reads exactly this pattern as "keep the old value", which is what a latch is. Here, in simulation, with nothing to hold over from a previous run, "the old value" is simply whatever the signal started at: undefined.

Cost

O(n) gate delay in the number of priority levels -- each elsif depends on every condition above it having already been evaluated, so a 4-input priority encoder is four levels deep where the earlier Binary to Gray Code problem's independent bits were all one level. That dependency is not incidental here; it is the entire point -- it is what "priority" means as a circuit.
