Binary to Gray Code

Worked solution

This page contains the complete answer and explains why each part of it is there.

The whole thing

library ieee;
use ieee.std_logic_1164.all;

entity solution is
    port (
        bin  : in  std_logic_vector(3 downto 0);
        gray : out std_logic_vector(3 downto 0)
    );
end entity solution;

architecture rtl of solution is
begin
    gray(3) <= bin(3);
    gray(2) <= bin(3) xor bin(2);
    gray(1) <= bin(2) xor bin(1);
    gray(0) <= bin(1) xor bin(0);
end architecture rtl;

Four independent concurrent assignments. Each one depends on at most two bits of bin, so all four settle in parallel -- there is no ordering between them for the simulator, or the synthesised hardware, to get right or wrong.

Walking it through

Take bin = "1010" (decimal 10):

gray bitformulavalue
3bin(3)1
2bin(3) xor bin(2)1 xor 0 = 1
1bin(2) xor bin(1)0 xor 1 = 1
0bin(1) xor bin(0)1 xor 0 = 1

gray = "1111" -- every bit came out set, confirmed against a real GHDL run sweeping all 16 possible inputs against this exact architecture.

Why this is the conversion

The defining property of Gray code is that consecutive values differ in exactly one bit. bin(i+1) xor bin(i) is exactly "does the binary count change at this position when it rolls from n to n+1" -- a binary counter's bit i flips exactly when every bit below it was 1, which is the same condition as "bit i+1 is about to flip too". XOR-ing each bit with its upstream neighbour cancels that shared flip out, leaving only the single bit position where the *net* change actually happens.

Read down either column and every row differs from its neighbour by exactly one bit -- including the wraparound from 1111 back to 0000, which is what makes this specifically the reflected Gray code rather than merely "some" one-bit-at-a-time ordering.

The trap: which bit is "above"

The shift direction is not symmetric, and getting it backwards still compiles. Swap the formula to gray(i) <= bin(i) xor bin(i-1) -- XOR-ing with the neighbour below instead of above -- and every port is still the right width, every index is still in range, and the design still elaborates and runs. Checked against all 16 inputs, that version agrees with the correct one on exactly one of them: "0000", where every bit is zero regardless of which neighbour you look at. Every other input comes out wrong.

The tell: the correct formula for gray(0) reaches up to bin(1); it never reaches for something below bit 0, because there is nothing below bit 0. A version that XORs bin(0) with bin(3) (wrapping around) or leaves gray(0) as a bare copy of bin(0) has gone looking for a neighbour in the wrong place.

Cost

O(1) gate delay -- one XOR gate deep, independent of the vector width, since every output bit depends on at most two input bits rather than on each other.
