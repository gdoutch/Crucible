Even Parity Bit

Worked solution

This page contains the complete answer and explains why each part of it is there.

The whole thing

library ieee;
use ieee.std_logic_1164.all;

entity solution is
    port (
        data   : in  std_logic_vector(7 downto 0);
        parity : out std_logic
    );
end entity solution;

architecture rtl of solution is
begin
    parity <= xor data;
end architecture rtl;

One concurrent signal assignment. No process, no loop, no if -- the whole circuit is one operator.

Why XOR is the operator that answers this

XOR of two bits is '1' exactly when they differ, which is the same fact as "an odd number of the two inputs were '1'". That fact is preserved as XOR is chained: after XOR-ing together n bits, the running result is '1' exactly when an odd number of those n bits were '1', regardless of which ones or in what order. XOR every bit of data together and what comes out the other end is exactly "does data hold an odd number of ones" -- which is exactly the definition of the even parity bit.

Four ones -- an even number -- and the running XOR lands back on 0. Confirmed against a real GHDL run for exactly this input: parity = '0'.

The reduction operator

xor data is unary xor -- VHDL-2008's reduction form, one of a handful of operators (and, or, nand, nor, xor, xnor) that can be written with one operand, a one-dimensional array, instead of two. Written out the long way, the same circuit is:

parity <= data(7) xor data(6) xor data(5) xor data(4)
        xor data(3) xor data(2) xor data(1) xor data(0);

Both compile to the same tree of two-input XOR gates. The reduction form is not a shortcut in the sense of skipping work -- it is the same circuit -- it is a shortcut in the sense that there is no bit index left to get wrong, no seventh term to forget when the vector happens to be wider next time.

Cost

As hardware: an 8-input XOR tree, O(log n) gate delay in the width of the input, not O(n) -- the same shape as the adder tree behind Count Set Bits' addition, and for the same reason: nothing here happens one bit at a time in real time, the whole reduction settles in parallel.

A wrong turn worth recognising

Treating "no bits set" as a special case. parity <= '0' when data = "00000000" else '1'; passes the all-zero case by coincidence and is wrong for almost everything else -- it says "odd" for every nonzero input, including "11111111", which has eight ones and needs parity = '0' exactly like all-zero does. The bug reads as plausible because zero is the most obvious case to think about first; the fix is remembering that parity is a property of the count, not of whether the count is zero.
