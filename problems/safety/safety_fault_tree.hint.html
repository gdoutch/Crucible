Smallest Cut Set of a Fault Tree

What the number means

Before the code, be sure what you are computing. A cut set is a set of basic events that together cause the top event. The smallest one is the fewest simultaneous failures the system can be destroyed by.

If that number is 1, some single component takes the whole system down on its own — a single point of failure, and the finding that stops a design review. If it is 2, you have genuine dual redundancy somewhere. This is the headline number of a fault tree analysis, and it is the reason anyone draws one.

The recursion writes itself from the semantics

Ask, for each kind of node: what is the cheapest way to make this node fail?

NodeFails whenCheapest way
GATE_BASICthis component fails one event — itself
GATE_ORany input fails pick the cheapest child, and ignore the others
GATE_ANDall inputs fail you have to pay for every child

Three cases, one line each. The base case is the basic event — it has no children, so the recursion cannot go past it, and every branch of the tree ends in one.

Sanity-check the arithmetic on paper

Draw these four and work out the answer before you write code:

  • OR(basic, basic) — two components, either one kills you. 1.
  • AND(basic, basic) — both must fail together. 2.
  • AND(OR(a,b), OR(c,d)) — two channels in series, each with two ways to fail. 1 + 1 = 2.
  • OR(AND(a,b), c) — this is the interesting one. Work it out.

That last one comes to 1, and it is why the exercise exists. All the redundancy in the AND branch counts for nothing while c sits beside it and can fail alone. A great many real designs look exactly like this — a redundant subsystem with a single shared power supply, sensor or connector next to it.

Reading the input structure

The harness parses stdin and hands you an array. You never touch stdin yourself.

struct gate {
    int kind;          /* GATE_BASIC, GATE_AND or GATE_OR */
    int input_count;   /* how many of `inputs` are used */
    int inputs[8];     /* indices into the same array */
};

inputs[i] is an index, not a pointer. To visit a child you recurse on gates[node->inputs[i]] — or, more neatly, pass the index down and let the callee do the lookup, which is why the signature takes top rather than a node.

Copy the enum and the struct exactly as the problem gives them. Your file and the harness are compiled separately and agree on the layout only because the two declarations match.

Why the recursion is guaranteed to stop

Two promises in the statement do the work, and it is worth knowing which does what:

  • Every child's index is greater than its parent's. So you can never come back to a node you are already inside — no cycles, no infinite descent.
  • No basic event appears twice. This one is not about termination; it is what makes AND allowed to simply add. If two branches shared an event, their cut sets would overlap and the sum would count it twice.

For the OR, seed your running minimum with the first child rather than with some large sentinel and loop from the second. Every gate has at least one input, so the first child always exists — and a sentinel like INT_MAX that never gets replaced is a bug waiting for an empty gate.

Check yourself before you press Go

  • A tree that is one basic event → 1.
  • AND of three basics → 3.
  • The OR(AND(a,b), c) shape → 1, with SINGLE POINT OF FAILURE after it.
  • Does your OR handle a gate with one input?
  • Does anything overflow or recurse forever on the deepest random tree?
