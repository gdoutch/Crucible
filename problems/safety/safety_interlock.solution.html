Level Crossing Interlock

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Two safety properties, two outputs, and each output is derived from the property that constrains it rather than from a picture of the scenarios. Done that way the controller is six lines and has no cases in it — every scenario in the test suite, including the awkward ones, falls out of the same two rules.

The code

enum signal_aspect    { SIGNAL_GREEN, SIGNAL_RED };
enum barrier_position { BARRIER_UP, BARRIER_MOVING, BARRIER_DOWN };

void crossing_command(int approaching, int in_crossing, int barrier,
                      int *signal_out, int *target_out)
{
    if (approaching > 0 || in_crossing > 0) {
        /* Any train anywhere: stop the road and get the barrier down. This
         * one branch also covers a train arriving mid-raise. */
        *signal_out = SIGNAL_RED;
        *target_out = BARRIER_DOWN;
        return;
    }

    /* Clear. Start raising -- but the signal follows where the barrier
     * actually is, not where it is going, which is the whole of S2. */
    *target_out = BARRIER_UP;
    *signal_out = (barrier == BARRIER_UP) ? SIGNAL_GREEN : SIGNAL_RED;
}

The one line that matters

*signal_out = (barrier == BARRIER_UP) ? SIGNAL_GREEN : SIGNAL_RED;

The signal is keyed off the barrier's observed position, not off the absence of trains and not off the target that was just commanded. Replace it with the obvious version —

*signal_out = SIGNAL_GREEN;      /* wrong: no trains, so green */

— and the run fails the moment the last train leaves, because at that instant the barrier is still fully down. The monitor reports the road signal is green with the barrier not up, and it reports it on the very event where the controller became complacent.

This is the difference between commanding a state and observing one. A controller that believes its own outputs is a controller with no feedback, and in a real crossing the barrier can also jam, be struck, or lose power halfway. Reading the position rather than assuming it is what makes the rule survive all of those.

Why the danger branch needs no cases

approaching > 0 || in_crossing > 0 is doing more work than it looks:

  • A train is approaching — start lowering, two ticks before it can possibly arrive.
  • A train is in the crossing — keep it down.
  • A train appears while the barrier is rising — the condition is true again, the target flips back to BARRIER_DOWN, and the next tick reverses the barrier from wherever it had got to. No code was written for this.
  • Two trains, one entering — approaching drops to 1, not 0, so the condition is still true. Counts rather than flags is what buys this.

Enumerating scenarios instead would mean twelve combinations of three inputs, several of which are unreachable, and any of which can be got wrong individually. Deriving from the properties gives one branch.

Walking the case that exposes the bug

The signal must wait for the barrier: approach tick tick enter exit tick

#EventapprcrossbarrierCommand

1approach10UPRED DOWN
2tick10MOVINGRED DOWN
3tick10DOWNRED DOWN
4enter01DOWNRED DOWN
5exit00DOWNRED UP
6tick00MOVINGRED UP

Rows 5 and 6 are the whole point. The crossing is clear, so the barrier is commanded up — but it is at DOWN and then MOVING, so the signal stays red. The naive controller emits GREEN UP at row 5 and is caught immediately.

Row 4 is the other one to notice: enter moves the train from the approach section into the crossing, so approaching falls to 0 while in_crossing rises to 1. A condition that tested only approaching would release the barrier with a train on it.

Where the safety monitor lives

S1 and S2 are checked in harness.c, after every decision, and nothing in solution.c can reach them. That is the same arrangement as the harness owning main, and for a stronger reason: a controller that also grades itself is not being tested.

It is worth noticing what kind of check this is. The expected output does not merely assert that a particular scenario produces particular commands — it asserts that a property held over the whole run. That is model-based testing, and it is the technique this domain actually uses: generate traces, drive the implementation, and have an independent monitor decide whether an invariant ever broke.

The randomised cases are where it earns its keep. Every generated scenario guarantees at least two ticks between a train being seen and it arriving, so a correct controller is always safe — and any train arriving at a moment the author did not picture is exactly the case that catches an incomplete controller.

The unsurvivable case, and why it is in the suite

The barrier cannot teleport is approach enter — a train in the crossing two events after it was first seen, with no tick in between. The barrier is physically incapable of moving, so the run is unsafe whatever is commanded, and the expected output ends:

UNSAFE at event 2 (enter): a train is in the crossing with the barrier not down

It discriminates nothing about the controller's safety, and it is in the suite for a different reason: it proves the monitor can fire. A safety check that has never been observed to fail is indistinguishable from one that is wired up wrong, and a suite where every case passes tells you nothing about which of the two you have. In certified work this is a required activity — you inject the fault and demonstrate the detection.

Cost

O(1) per event: two comparisons and two writes, no allocation, no state. Worth stating because for an interlock it is a safety property in its own right — the response time is bounded and identical on every path, which is what lets a real system guarantee it will decide before the next scan.

Wrong turns worth recognising

Keying the signal off the trains. Covered above. It is the bug the problem is built around, and it fails on the first raise of every scenario.

Keying the signal off the target instead of the position. A subtler version: green if target == BARRIER_UP. It is wrong for the same reason and fails in the same place, because the target becomes UP two ticks before the barrier does.

Waiting for confirmation before lowering. Some designs refuse to lower until the signal has been red for a tick, to warn drivers first. Reasonable in general, and here it costs a tick the barrier does not have — the generated scenarios allow exactly two, which is the full lowering time and no more.

Treating the counts as booleans. in_crossing == 1 instead of > 0, or decrementing something yourself. The world's state belongs to the harness; you are handed a reading of it and asked for a decision.

Leaving an output unwritten on some path. The harness sets both to -1 before calling you, so a missed assignment surfaces as INVALID signal -1 rather than as a stale value that happens to be right most of the time.
