Smallest Cut Set of a Fault Tree

Worked solution

This page contains the complete answer and explains why each part of it is there.

The idea

Structural recursion over the tree, with one rule per node kind, each read straight off what the gate means:

NodeSemanticsSmallest cut set
basic eventfails on its own1
ORany one input suffices min over children
ANDall inputs required sum over children

The whole difficulty is believing that min and sum are enough. They are, for a tree — and the section on shared events below is about what happens when it is not one.

The code

enum gate_kind { GATE_BASIC, GATE_AND, GATE_OR };

struct gate {
    int kind;
    int input_count;
    int inputs[8];
};

int smallest_cut_set(const struct gate *gates, int top)
{
    const struct gate *node = &gates[top];

    if (node->kind == GATE_BASIC) {
        return 1;
    }

    if (node->kind == GATE_AND) {
        /* Every input has to fail, and no basic event is shared between
         * them, so the sets are disjoint and the sizes simply add. */
        int total = 0;
        for (int i = 0; i < node->input_count; i++) {
            total += smallest_cut_set(gates, node->inputs[i]);
        }
        return total;
    }

    /* OR: any one input is enough, so the cheapest child wins. */
    int smallest = smallest_cut_set(gates, node->inputs[0]);
    for (int i = 1; i < node->input_count; i++) {
        int size = smallest_cut_set(gates, node->inputs[i]);
        if (size < smallest) {
            smallest = size;
        }
    }
    return smallest;
}

Why the OR seeds from the first child

The alternative is to start at some large sentinel:

int smallest = INT_MAX;                 /* needs <limits.h> */
for (int i = 0; i < node->input_count; i++) { ... }

It works, and it hides a decision. If input_count were ever 0 the loop would not run and INT_MAX would be returned as a cut set size — a nonsense number that then propagates upwards, and if it reaches an AND, overflows on the addition.

Seeding from inputs[0] states the assumption that every gate has at least one input, and the statement guarantees it. Where a guarantee exists, code that depends on it visibly is better than code that quietly papers over its absence with a wrong answer.

Walking the interesting case

Redundancy beside a single point of failure — OR(AND(b, b), b):

The AND branch needs two failures. The bare basic event beside it needs one. The OR takes the cheaper, and the answer is 1 — SINGLE POINT OF FAILURE.

This is the whole reason the analysis is quantitative rather than a matter of looking at the diagram. The design contains dual redundancy, and someone will say so in a review. The number says it buys nothing while anything beside it can fail alone.

The assumption that makes AND a sum

Adding the children is only correct when no basic event appears in more than one branch. The problem guarantees a tree, so it is correct here — and it is worth knowing exactly what breaks without that guarantee, because real fault trees violate it constantly.

Consider AND(a, a) — the same component feeding both inputs. The sum says 2. The truth is 1: a failing satisfies both inputs at once, so {a} is a cut set of size one. The sum has counted one component as two.

That configuration is exactly what a fault tree is drawn to find — the shared power rail behind two "independent" channels, the common connector, the single clock. Real tools therefore compute cut sets, not sizes: the set for a basic event is {{a}}, for an OR it is the union of its children's sets, and for an AND it is the pairwise union of every combination, after which sets that contain another set are discarded. The number of cut sets can grow exponentially, which is why the standard algorithms (MOCUS and its descendants) exist and why the general problem is NP-hard.

Restricting this exercise to a tree collapses all of that into min and sum. Knowing which assumption you are trading on is the point — an engineer who reaches for this recursion on a DAG will get an answer that is too optimistic, which in safety work is the dangerous direction to be wrong in.

Structural recursion

The function's shape follows the data's shape: one branch per kind, and the recursive calls mirror the child edges. There is no explicit termination argument to construct, because the base case is a node kind with no children and every path down the tree reaches one.

The index ordering — every child's index greater than its parent's — is what makes the structure a tree rather than a graph, and so rules out a cycle taking the recursion round forever. Note that the code never checks this; it is a precondition the harness establishes. That is a legitimate division of responsibility, and it is worth being explicit that it is one.

Cost

O(n) in the number of nodes: each is visited once, because each has exactly one parent. Stack depth is O(depth of the tree), which for the 256-node cap here is trivially safe.

On a DAG with shared subtrees the same code becomes exponential, since a shared node is recomputed once per path that reaches it. Memoising on the node index fixes that and returns it to O(n) — though as above, on a DAG the arithmetic is wrong regardless of how fast it is computed.

Wrong turns worth recognising

Swapping min and sum. The easiest slip on this problem, and the diagnosis is quick: if OR(a, b) comes out as 2, you have them the wrong way round. Anchor it on the meaning — OR is the easy way to fail, so it must produce the smaller number.

Counting nodes instead of basic events. Gates are not components; they are structure. Only leaves contribute to a cut set, which is why GATE_BASIC is the only case that returns a literal.

Recursing on the child index as if it were a node. smallest_cut_set(gates, node->inputs[i]) is right; smallest_cut_set(&gates[node->inputs[i]], 0) is not — it re-bases the array so every subsequent index is measured from the wrong place. The indices are absolute, into one array that never moves.
