Count Set Bits

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

How many of the 32 bits in ecx are 1. Sometimes called the population count, or Hamming weight.

x86 has had a popcnt instruction since 2008, and popcnt eax, ecx is the entire problem in one line. It passes every test here. It also skips the exercise, which is the loop and the flags — so shift the bits out yourself, the same way the hardware instruction was invented to stop people doing.

The idea in one sentence

Look at the lowest bit, add it to a running count, shift everything down by one, and stop when there is nothing left.

"Nothing left" is the useful part. You do not need to count to 32: once the value has been shifted down to zero, every remaining bit is a zero and there is nothing more to find. A value of 1 costs one iteration rather than thirty-two.

Two ways to look at the lowest bit

ApproachHow
Mask it off Copy the value into a scratch register, and it with 1, and add that to the count. Adds zero or one, so no branch is needed at all.
Let the shift tell you shr puts the bit it shifted off the bottom into the carry flag. jc jumps if it was set, jnc if it was not.

Both are fine. The second is the more assembly-flavoured of the two — the bit you need to know about has already been captured as a side effect of the shift you were going to do anyway, so nothing extra has to be computed to find it.

The trap: shr and sar are not the same

sar on a value with the top bit set never reaches zero. Both instructions shift right; they differ in what they feed in at the top. shr — the logical shift — feeds in zeros. sar — the arithmetic shift — copies the existing top bit down, because that is what preserves the value of a signed number when you halve it.

The value here is unsigned. Shift 0xFFFFFFFF with sar and it stays 0xFFFFFFFF for ever, so a loop that runs "until the value is zero" never ends. Crucible times each case out separately, so the symptom is TIMEOUT on the all ones and top bit set cases while the small values pass — which is a very recognisable signature once you have seen it once.

The shape of the loop

    ; count = 0
next:
    ; if the value is zero, we are done
    ; shift the low bit out
    ; if that bit was a 1, add one to the count
    ; go back to next
done:
    ret

The test at the top rather than the bottom is what makes count_set_bits(0) return 0 without doing any work. test ecx, ecx followed by jz is the idiomatic way to write it.

Still stuck? A bigger nudge

Using the carry flag, the body is three instructions and two of them are jumps:

.code
count_set_bits PROC
    xor eax, eax            ; count = 0
next:
    test ecx, ecx
    jz done                 ; no bits left
    shr ecx, 1              ; the bit that fell off is now in CF
    ; two lines here: skip the increment when CF was clear,
    ; otherwise count it — then jump back to next either way
done:
    ret
count_set_bits ENDP
end

The neat version needs no explicit "skip" label: jnc next goes straight back round when the bit was zero, so the inc eax that follows only ever runs when it was one.

Check yourself before you press Go

  • 0 → 0, having never entered the body.
  • 7 → 3, and it took three iterations, not thirty-two.
  • 2147483648 (the top bit alone) → 1, after 32 shifts.
  • 4294967295 (all ones) → 32. If this one hangs while the others pass, you wrote sar.
