Index of the Largest Element

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

Where the largest value is, not what it is. Those are different answers and the difference is the whole problem: you have to carry the largest value seen so far in order to compare against it, and separately remember the index it came from, because that is what you return.

Three registers, three jobs

HoldsSuggestedNotes
best index so fareax Keep the answer in the return register and there is nothing to move at the end.
best value so farr9d Only exists to be compared against.
current indexr8d Used both to index memory and to test against edx.

rax, rcx, rdx and r8–r11 are all scratch, so none of these needs saving. Reach for rbx or rsi and you have taken on a push/pop obligation for no reason.

Where to start the loop

There are two workable openings, and one of them is meaningfully easier:

  • Seed from element 0, then loop from 1. The best value starts as values[0] and the best index as 0, so every comparison in the loop is a real comparison against a real element.
  • Seed with "the smallest possible int", then loop from 0. Tidier-looking, but you have to write 80000000h and be right about it, and it quietly assumes no element can equal INT_MIN.

The first needs the count guard anyway — which you need regardless, because of the empty array — so it costs nothing extra. Take it.

The trap: the tie

"First one wins" is decided entirely by which comparison you branch on. Replace the current best only when the new value is strictly greater, and the first of two equal maxima keeps the title. Replace on greater-or-equal and every later duplicate overwrites it, so you return the last index instead.

Concretely: with 1 7 3 7 2 the answer is 1. A solution that answers 3 on that case and is right on every other case has exactly this bug.

The other trap: signed comparison

ja and jg are not interchangeable. x86 has two complete families of conditional jumps, and the difference is how they read the top bit:

  • jg, jge, jl, jle — signed. Used after comparing values that can be negative.
  • ja, jae, jb, jbe — unsigned. The top bit is just another magnitude bit.

These are ints. Use the unsigned family and -1 compares as 0xFFFFFFFF — about four billion — so the most negative element is confidently reported as the largest. The all negative test case exists to catch precisely this, and it is the case that separates code that happens to work from code that is right.

The shape of it

    ; answer = -1
    ; if count <= 0, jump to the end (answer is already -1)
    ; best index = 0, best value = values[0], i = 1
next:
    ; if i >= count, jump to the end
    ; load values[i]
    ; if it is not strictly greater than the best, skip the update
    ; best value = it, best index = i
skip:
    ; i = i + 1, go back to next
done:
    ret

Note that the -1 is set up before the guard, so the empty-array path needs no code of its own — it just falls through to ret with the right answer already in eax.

Still stuck? A bigger nudge 
.code
index_of_max PROC
    mov eax, -1
    test edx, edx
    jle done
    xor eax, eax                        ; best index = 0
    mov r9d, dword ptr [rcx]            ; best value = values[0]
    mov r8d, 1                          ; start comparing at element 1
next:
    cmp r8d, edx
    jge done
    mov r10d, dword ptr [rcx + r8*4]    ; values[i]
    ; two lines missing here: compare against the best, and skip
    ; the update unless it is strictly greater
    mov r9d, r10d
    mov eax, r8d
skip:
    inc r8d
    jmp next
done:
    ret
index_of_max ENDP
end

The missing comparison is between r10d and r9d, and the jump that follows it lands on skip. Choosing which condition to jump on is the tie rule and the signedness question, both at once — get those two right and the rest is already here.

Check yourself before you press Go

  • Empty array → -1, with nothing loaded through rcx.
  • Largest first → 0. Nothing later displaced it.
  • Largest last → the final index. The loop really did reach the end.
  • 1 7 3 7 2 → 1, not 3.
  • All negative → the least negative one, not index 0.
