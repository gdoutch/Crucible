Sum an Array

Hint

A nudge in the right direction. The full answer is on the worked-solution page, so nothing below gives it away.

What you are being asked for

A running total across count consecutive 32-bit integers starting at rcx. It is a four-line loop. Almost all of the difficulty is in the first two lines, before the loop starts.

Where the arguments are

The harness calls your procedure as sum_array(values, count), and Microsoft's x64 convention puts the first two arguments in rcx and rdx:

HoldsRegisterWhy that width
valuesrcx A pointer — 64 bits, so the whole register.
countedx An int — 32 bits, so the low half of rdx.
your answereax An int comes back in the low half of rax.

Mixing the widths up is the classic first mistake. rdx holds count in its low 32 bits, but the top 32 are not guaranteed to be anything in particular — so compare against edx, not rdx.

Reaching element i

The elements are four bytes each and laid out end to end, so element i begins 4 * i bytes after the start. You do not have to compute that yourself: an x86 memory operand can do it in the instruction.

dword ptr [rcx + r8*4]

Read that right to left: take the index in r8, multiply by the scale factor 4, add the base in rcx, and read dword ptr — four bytes — from the address that gives. The legal scale factors are 1, 2, 4 and 8, which is exactly the set of sizes you would want for a char, a short, an int and a pointer.

Use the full 64-bit r8 in the address even while you compare its low half r8d against edx. Addresses are 64-bit; an index is not. Writing to r8d zeroes the upper half of r8 for you, so the two stay consistent without any extra work — which is a genuine convenience of the 32-bit forms, not an accident to rely on nervously.

The shape of the loop

    ; total = 0
    ; if count <= 0, skip everything
    ; i = 0
next:
    ; total += values[i]
    ; i = i + 1
    ; if i < count, go back to next
done:
    ret

Three registers do all of it: one for the total, one for the index, and rcx/edx as they arrived. All of rax, rcx, rdx and r8–r11 are yours to overwrite without asking, so there is nothing to push and nothing to pop.

The trap: the empty array

When count is 0, values is a null pointer. The harness passes NULL rather than an allocation of nothing, which means a loop written to run its body once before checking — the do-while shape — reads address zero and the case comes back ERROR: access violation instead of 0.

So test count before the first load. In assembly the usual way to test a register against zero is test edx, edx followed by a conditional jump: test sets the flags exactly as cmp edx, 0 would, in a shorter instruction. Use a signed condition — the count is an int.

Still stuck? A bigger nudge 
.code
sum_array PROC
    xor eax, eax            ; total = 0 — and the answer for an empty array
    test edx, edx
    jle done                ; nothing to add; eax is already right
    xor r8d, r8d            ; i = 0
next:
    ; one instruction here: add values[i] into the total
    inc r8d
    cmp r8d, edx
    jl next
done:
    ret
sum_array ENDP
end

One line is missing, and it is the memory operand shown further up. Note that xor eax, eax is doing double duty: it initialises the total, and it is already the correct answer if the count turns out to be zero — which is why the guard can jump straight to done without setting up anything first.

Check yourself before you press Go

  • Empty array → 0, and nothing was read through rcx.
  • One element → that element, so the loop ran exactly once.
  • Values that cancel to zero → 0, which is a real total and not a sign that something was skipped.
  • All negative → a negative total, so you used jl rather than jb when comparing the index, and add rather than anything unsigned-flavoured on the values.
