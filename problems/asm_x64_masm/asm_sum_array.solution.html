Sum an Array

Worked solution

This page contains the complete answer and explains why each part of it is there.

The whole thing

; int sum_array(const int *values, int count)
.code
sum_array PROC
    xor eax, eax                        ; total = 0
    test edx, edx
    jle done                            ; count <= 0: nothing to add
    xor r8d, r8d                        ; i = 0
next:
    add eax, dword ptr [rcx + r8*4]     ; total += values[i]
    inc r8d
    cmp r8d, edx
    jl next                             ; while i < count
done:
    ret
sum_array ENDP
end

Eight instructions, no stack, no prologue. The C compiler would produce something broadly similar for the same function at -O0, and something rather more clever at -O2 — but this is the shape the source is describing.

Walking it through

Take the array [10, -3, 7], so rcx points at the 10 and edx is 3:

Ateaxr8dReadsThen
entry??— xor eax, eax → 0
guard0—— 3 > 0, so no jump
next (1st)00[rcx + 0] = 10 eax = 10, i = 1, 1 < 3 → loop
next (2nd)101[rcx + 4] = -3 eax = 7, i = 2, 2 < 3 → loop
next (3rd)72[rcx + 8] = 7 eax = 14, i = 3, 3 < 3 is false → fall through
done143—ret

Three iterations for three elements, and the loop exits on the comparison rather than on running off the end of anything.

Why xor eax, eax rather than mov eax, 0

They do the same thing. xor of a register with itself is always zero, and it is the idiom you will see in every compiler's output, for two reasons worth knowing:

  • It is shorter. xor eax, eax encodes in two bytes; mov eax, 0 takes five, because the zero is stored in the instruction as a full 32-bit constant.
  • The processor recognises it. A zeroing xor is special-cased in hardware as "this register now holds zero", with no dependency on whatever the register held before — so it does not have to wait for an earlier instruction that was still computing the old value.

Here it also happens to set up the return value for the empty-array case, which is what lets the guard below it jump straight to ret.

The guard, and why it comes first

values is NULL when count is 0. The harness does not allocate a zero-length array; it passes a null pointer, exactly as a real caller would. A loop that reads before it checks — the do-while shape, where the test is at the bottom — dereferences address zero on the very first instruction of the body, and Crucible reports access violation rather than a wrong number.

test edx, edx ANDs the register with itself, discards the result and keeps only the flags — which is the same set of flags cmp edx, 0 would produce, in a two-byte instruction instead of a three-byte one. jle then covers 0 and, for free, any negative count a future caller might pass.

jle and not jbe: the count is a signed int. The unsigned conditions (ja, jb, jbe…) read the sign bit as part of the magnitude, so a count of -1 would look like about four billion and the guard would let it through.

The memory operand

add eax, dword ptr [rcx + r8*4]

One instruction that indexes, scales, adds, loads and accumulates. The general form of an x86 address is [base + index*scale + displacement], where the scale is 1, 2, 4 or 8 — the sizes of the types you would actually want to index — and the address arithmetic happens in the addressing hardware rather than costing instructions of its own.

dword ptr is not decoration. eax already implies a 4-byte operand here, so MASM would accept the line without it, but naming the width at the point of the access is worth the six characters: it is the only thing in the instruction that says how much memory is being touched, and on a line where the destination is not a fixed-width register MASM genuinely cannot guess.

The index lives in r8 as a 64-bit value because addresses are 64-bit, while inc r8d and cmp r8d, edx work on its low half to match the 32-bit count. That mixture is safe because writing any 32-bit register zeroes the upper 32 bits of its 64-bit parent — xor r8d, r8d really does clear the whole of r8. It is a deliberate rule of x86-64 rather than a quirk, and it is why 32-bit forms are the default in compiler output even on a 64-bit machine.

Cost

O(n) time, one pass, and O(1) space — three registers and no stack frame at all. Nothing was pushed, so nothing has to be popped, and ret can be the last instruction with no epilogue in front of it.

Two wrong turns worth recognising

Checking the count at the bottom of the loop. It reads naturally — add, advance, test, repeat — and it is correct for every input except the empty array, where it reads through a null pointer before it ever reaches the test. This is the same bug in every language; assembly just makes the consequence louder.

Comparing r8 against rdx. The count arrived in edx, and the top half of rdx is whatever the caller left there. Compare the halves that were actually defined.
