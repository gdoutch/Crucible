Count Set Bits

Worked solution

This page contains the complete answer and explains why each part of it is there.

The whole thing

; int count_set_bits(unsigned int value)
.code
count_set_bits PROC
    xor eax, eax                ; count = 0
next:
    test ecx, ecx
    jz done                     ; no bits left to look at
    shr ecx, 1                  ; low bit falls into the carry flag
    jnc next                    ; it was 0 -- nothing to count
    inc eax
    jmp next
done:
    ret
count_set_bits ENDP
end

Six instructions in the loop and no scratch register beyond the count. The argument register ecx is destroyed as we go, which is entirely allowed — it is a scratch register, the caller expects nothing of it after the call, and consuming it is cheaper than copying it somewhere first.

Walking it through

Take value = 6, which is 110 in binary:

Atecx (binary)CFeaxThen
entry110—0not zero, so shift
after 1st shr1100 jnc taken — back to the top
after 2nd shr111 CF set, so inc ran
after 3rd shr012 CF set, so inc ran
top of loop0—2 jz done — finished

Three iterations for a three-bit number, and the answer is 2. The loop is driven by the value running out, not by a counter reaching 32, so the work is proportional to the position of the highest set bit rather than to the width of the register.

The carry flag is the whole trick

shr ecx, 1 does two things: it halves the register, and it leaves the bit that fell off the bottom in the carry flag. That second effect is free — the shift had to happen regardless — so the bit is already available to branch on without any masking, comparing or copying.

Then jnc next reads oddly at first, because the loop's back edge is doing the work of an if:

  • Bit was 0 → carry clear → jump straight back to the top. The inc is simply never reached.
  • Bit was 1 → carry set → fall through to inc eax, then jmp next back to the top.

Written as an explicit "if the bit was set, increment" it would need its own skip label and one more instruction. Folding the common case into the branch you already had is a habit worth picking up; it is why compiled output so often looks jumbled compared to the source it came from.

shr, not sar

This is the one that hangs. sar shifts right arithmetically, replicating the sign bit downward so that a signed value keeps its sign when halved: -8 shifted right becomes -4, not some large positive number. That is exactly right for a signed quantity and exactly wrong here.

Applied to 0xFFFFFFFF, sar produces 0xFFFFFFFF again, and does so for ever: the loop's exit condition is never met, the case is killed at the timeout, and the result is TIMEOUT on the two cases with the top bit set while every small value passes. The value here is unsigned int, so shr — the logical shift, feeding in zeros — is the one that matches the type.

The alternative without a branch

Masking the low bit instead of branching on it is just as valid, and avoids one jump per iteration:

next:
    test ecx, ecx
    jz done
    mov r8d, ecx
    and r8d, 1              ; 0 or 1
    add eax, r8d            ; add it either way -- no branch
    shr ecx, 1
    jmp next

It costs one scratch register and one more instruction in the body, but every iteration takes the same path. On a modern processor that can matter: a branch whose direction depends on the data is a branch the predictor cannot learn, and the bits of an arbitrary number are about as unpredictable as data gets. For a loop this short it is not worth measuring, but the reasoning is the same one behind cmov and behind popcnt existing at all.

Cost

O(k) where k is the position of the highest set bit — at most 32 iterations, and often far fewer. O(1) space: one register for the count, and the argument register consumed in place.

There are faster ways. value & (value - 1) clears the lowest set bit, so looping on that runs once per set bit rather than once per bit position, and the SWAR bit-twiddling version counts all 32 in a fixed dozen instructions with no loop at all. And then there is popcnt, which is one instruction because someone eventually put this exact loop into silicon.

A wrong turn worth recognising

Counting to 32 instead of shifting to zero. A fixed 32-iteration loop gives the right answer for every input, so the tests will not catch it — but it does the maximum work for count_set_bits(1), and it hides the more useful observation that the loop's real bound is the data, not the register width.
