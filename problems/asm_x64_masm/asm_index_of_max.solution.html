Index of the Largest Element

Worked solution

This page contains the complete answer and explains why each part of it is there.

The whole thing

; int index_of_max(const int *values, int count)
.code
index_of_max PROC
    mov eax, -1                         ; the empty-array answer
    test edx, edx
    jle done                            ; count <= 0: nothing to look at
    xor eax, eax                        ; best index = 0
    mov r9d, dword ptr [rcx]            ; best value = values[0]
    mov r8d, 1                          ; i = 1
next:
    cmp r8d, edx
    jge done                            ; while i < count
    mov r10d, dword ptr [rcx + r8*4]    ; values[i]
    cmp r10d, r9d
    jle skip                            ; strictly greater only: ties keep
    mov r9d, r10d                       ; the earlier index
    mov eax, r8d
skip:
    inc r8d
    jmp next
done:
    ret
index_of_max ENDP
end

Walking it through

The tie case, 1 7 3 7 2, where the answer is 1:

ivalues[i]vs bestAction best valueeax
———seed from element 0 10
177 > 1update 71
233 ≤ 7skip 71
377 ≤ 7skip 71
422 ≤ 7skip 71

Row i = 3 is the one that matters. The second 7 is equal to the best, not greater than it, so jle skip is taken and eax keeps the earlier index. That single flag condition is the entire "first occurrence wins" rule — there is no separate code for it anywhere.

jle is doing two jobs at once

It is worth being explicit about how much rides on that one mnemonic, because both of this problem's real bugs live there:

Written asTiesNegativesVerdict
jle skipfirst wins ✓signed ✓ correct
jl skiplast wins ✗signed ✓ fails tie keeps the earlier index
jbe skipfirst wins ✓unsigned ✗ fails all negative
jb skiplast wins ✗unsigned ✗ fails both

All four assemble. All four are plausible at a glance. Only one is right, and the two test cases named in that table are there to tell you which mistake you made rather than merely that you made one.

Why the unsigned version is so convincing. cmp does not know or care whether its operands are signed — it subtracts and sets flags, and every flag it could possibly need is set every time. The jump chooses an interpretation. So jbe after comparing -9 and -2 reads them as 0xFFFFFFF7 and 0xFFFFFFFE, decides -9 is the smaller of the two, and is perfectly consistent about it — consistently wrong for an int. On an array of positives it agrees with jle on every single input, which is why this bug survives casual testing.

Why eax holds the answer the whole way through

mov eax, -1 is the first instruction, before anything has been examined, so the empty-array case needs no branch of its own: the guard jumps to done and ret returns a value that was already correct. Then xor eax, eax overwrites it with 0 once we know there is at least one element, and from that point eax is simply "the best index so far".

Keeping the answer in the return register for the whole procedure — rather than tracking it somewhere else and moving it at the end — means there is no final mov to forget, and no path out of the procedure that could return a stale value. Every ret is correct by construction because there is only one, and everything that reaches it has maintained the invariant.

Seeding from element 0

The loop starts at i = 1 because element 0 has already been taken as the incumbent. The alternative — start the best value at 80000000h (INT_MIN) and loop from 0 — removes the seed but adds a magic constant, and quietly relies on no element ever being equal to INT_MIN, since such an element would not be strictly greater than the seed and would leave the index at whatever it was initialised to.

Seeding from real data has no such assumption. It needs the count guard, but the null-pointer case demanded that anyway.

Cost

O(n) time, one pass, O(1) space: four registers, no stack frame, no prologue, no epilogue. There is no way to do better than one pass — you cannot know the largest element without having looked at all of them.

Two wrong turns worth recognising

Returning the value instead of the index. Easy to drift into, because the value is the thing you are actively comparing and the index is only along for the ride. If largest is last gives 9 where 3 was expected, this is what happened.

Comparing r8d against rdx, or indexing with r8d. The count arrived in edx and the upper half of rdx is undefined, so compare the 32-bit halves — and memory operands need the full 64-bit r8, since addresses are 64-bit. Writing r8d zeroes the top of r8 automatically, which is what makes using both forms of the same register safe here rather than merely lucky.
